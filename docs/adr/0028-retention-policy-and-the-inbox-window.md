# 0028. Retention policy, and an inbox window that outlasts redelivery

- Status: Accepted
- Date: 2026-10-20
- Deciders: Lee Jia Le

## Context
The earlier plans left tables that only grow: processed `OutboxMessages` and their `OutboxMessageConsumers`, `InboxMessages`, `platform.IdempotencyKeys`, and each module's expired codes, tokens, challenges, tickets and notifications. Plan 5 deletes them on a schedule (the scheduler is [ADR 0026](0026-recurring-jobs-on-our-own-scheduler.md)). Deleting is where mistakes cost data: a delete that is too eager removes evidence or breaks a guarantee, and one that is unbounded locks a table.

Two rows are not just clutter. An abandoned outbox message (it ran out of attempts) is a dead letter that an operator must see, not a processed row. And an inbox row is the proof that a consumer already handled an event: if it is deleted while the outbox can still redeliver that event, the consumer runs twice.

## Options considered
1. **Delete everything older than one global age.** Simple, but one number cannot fit an expired verification code (days) and a notification (months), and it would delete dead letters and shorten the inbox window.
2. **Keep rows until a human prunes them.** Nothing is lost, and nothing is safe: the tables grow without bound.
3. **A retention per kind of data, with batched deletes, the rules that protect dead letters and the inbox written down and validated.**

## Decision
We chose option 3.

- **Every delete is a loop of `DELETE TOP (@batch)`.** A run deletes at most `Jobs:MaxBatchesPerRun` batches (100) of `Retention:BatchSize` rows (1000) and stops early when a batch comes back short, so a run is bounded and a backlog drains over several runs. Each batch is its own statement and transaction, and runs with `NOCOUNT OFF` so the row count the loop reads is never suppressed by a session default.
- **A row goes only when strictly older than `now - retention`.** The clock is `TimeProvider`. Every predicate has a supporting index (a filtered one where the column is mostly null), and a test reads the execution plan of the largest.
- **A retention of `null` or `0` turns that job off.** A negative value fails validation on start.
- **The defaults** (the full table is in `docs/superpowers/specs/2026-10-19-platform-services-design.md`, section 3.2): outbox and inbox rows 7 days after `ProcessedAt`, daily (`{Context}OutboxCleanup`, `{Context}InboxCleanup`); `IdempotencyKeys` past `ExpiresAt`, hourly (`IdempotencyKeysCleanup`, which has no retention value: only `Jobs:IdempotencyKeysCleanup:Enabled` turns it off); each module's own table by its own rule (verification codes and MFA challenges hourly, tokens, sessions, devices and notifications daily). Everything not marked hourly runs daily. Building blocks read `Retention:*`; modules read `{Module}:Retention:*`.
- **Dead letters stay.** The outbox job deletes only rows with a `ProcessedAt` before the cutoff. An abandoned message (`ProcessedAt IS NULL` and `AttemptCount >= MaxAttempts`) is never deleted by it; the job reports how many there are in the gauge `platform.outbox.abandoned{context}` on the `TemplateName.Platform` meter, after every run, even when the retention is off.
- **The consumers of a message go with it.** No foreign key joins `OutboxMessageConsumers` to `OutboxMessages`, so each batch deletes the consumers of the messages it deleted in the same transaction.
- **The inbox window must outlast redelivery.** The outbox retries a failed message 5 s, 30 s, 2 min and 10 min after attempts 1 to 4, and 1 h after every later attempt, until `Outbox:MaxAttempts` (default 5, up to 100) is reached. With the default the retries span 12 min 35 s and the 1 h step is never used; each attempt beyond the fifth adds an hour (`OutboxRetryPolicy.RetryWindow`). `Retention:Inbox` is validated on start in two ways: a value above zero and below one day is an error (a day outlasts the default and every `MaxAttempts` up to 28, whose retries span 23 h 12 min 35 s), and a value that is not longer than the retry window of the configured `Outbox:MaxAttempts` is an error too (29 attempts need more than a day, 100 attempts need just under 4 days; the default of 7 days covers every allowed value). So a late retry can never meet a deleted inbox row and run its consumer twice, as far as the schedule goes: the retry window counts only the backoff delays, not the polling lag (`Outbox:PollingInterval`) after each delay or the lease re-claims after a crash (`Outbox:LeaseDuration`), so near the one-day floor there is no margin for them. The validator is registered by `AddInfrastructureCommon`, so it applies to every host that calls it, not only to hosts with an inbox. A deployment that raises `Outbox:MaxAttempts` far must raise `Retention:Inbox` with it; the host refuses to start otherwise. Zero or `null` switches the inbox cleanup off, which is safe.
- **Auth audit logs are not deleted by default**, and refresh-token reuse detection lasts as long as the used token does. The cleanup deletes a refresh token `Auth:Retention:RefreshTokens` (30 days) after its own `ExpiresAt`. While a used token still exists, presenting it answers `auth.refresh_token_reused` and revokes the session (if the session is still active and its security stamp matches); once the cleanup has deleted it, the same token answers `auth.invalid_refresh_token` and revokes nothing. The token is still refused, but the theft signal is lost; a deployment that wants it for longer raises the retention ([Auth module](../modules/auth.md#cleanup)).

## Consequences
- Positive: tables stay bounded without a run ever holding a long lock; the dead letters an operator must act on survive and are counted; the one invariant between two cleanups (the inbox outlasts the outbox) is enforced where the value is read.
- **A processed outbox row is gone after a week.** What happened to a message older than that is no longer in the database; the audit trail is the Audit module's job (Plan 5b), not the outbox's.
- **Changing the outbox retry schedule changes the window.** The start-up check reads the schedule from `OutboxRetryPolicy`, so a longer schedule raises the retention it demands without a further change. The fixed one-day minimum in `RetentionOptions` is only a lower bound, not derived from the schedule.
- **A backlog drains slowly by design.** 100 batches of 1000 is 100000 rows per run per job; a larger backlog takes several daily runs unless `Jobs:{Name}:Interval` is shortened for a while.
- **The gauge shows the last run, not now.** It is set after each (daily) run on the instance that ran it, and that instance reports it until the next run should have replaced it (the job's interval plus `Jobs:LeaseDuration` and `Jobs:TickInterval`), then nothing; the other instances report nothing. A dashboard or alert therefore takes the maximum of the most recent reports per `context` across instances, never the sum, and does not expect every instance to report.
- Follow-up actions: the Auth and Notifications cleanup jobs (done: [Auth module](../modules/auth.md#cleanup), [Notifications module](../modules/notifications.md#cleanup)); an archive target for audit logs, decided with the Audit module (Plan 5b).
