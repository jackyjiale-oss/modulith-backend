# 0019. Notification templates are Scriban files embedded in the declaring assembly

- Status: Accepted
- Date: 2026-10-09
- Deciders: Lee Jia Le

## Context
The Notifications module (Plan 3) renders every message the template sends: a subject, a plain-text body and an HTML body for email, a title and a body in-app, in the recipient's language (`en`, `ms` or `zh-Hans`, blueprint review Section 8). Blueprint Section 10.4 asks for templates per type, channel and language in Scriban syntax with a shared email layout, and Section 11.3 sketches a templates table that an admin editor (Section 10.4) would maintain. This plan has no admin editor (decision D16) and declares notification types in code (D7, no types table). The values put into a template come from users (a display name) or are secrets (a single-use link, ADR 0020), so rendering must not let a value change the markup or reach anything outside the message, and a template must never be able to show a secret in a subject or an in-app text. Review 8 (I9) asks CI to prove that every template exists in every language.

## Options considered
1. Templates as database rows (blueprint Section 11.3): editable at run time and versioned in the table, but they need seeding and a migration for every wording change, the rows can drift from the code that supplies the variables, nothing in CI can check them, and the editor and preview that would justify them are out of scope.
2. Razor views (RazorLight or ASP.NET Core's Razor rendering outside MVC): familiar C# syntax and HTML encoding by default, but a template is C# code with the full runtime in reach (file system, reflection, services), compiling views at run time is heavy, and the maintained runtime-compilation libraries are thin. A template that can run any code is a poor fit for text that translators edit.
3. Scriban files embedded as resources in the assembly that declares the type: one file per type, channel, culture and part, plus an email layout per culture; reviewed in pull requests, versioned by git, shipped inside the build, and checked by unit tests.

## Decision
We chose option 3 (decision D8 of Plan 3), with `Scriban` 7.5.0 (BSD-2-Clause, licence text verified in the repository at the release commit; no usage or maintenance fee: the project asks only for voluntary sponsorship; the `licenses` CI job passes).

- **Files.** `Templates/Email/{type}.{culture}.{subject|text|html}.scriban` and `Templates/InApp/{type}.{culture}.{title|body}.scriban` in the project of the `INotificationTypeSource` that declares the type, embedded with `<EmbeddedResource Include="Templates\**\*.scriban" />`, so the manifest name is `{assemblyName}.Templates.{Email|InApp}.{type}.{culture}.{part}.scriban`. The email layouts are `Templates/Email/_layout.{culture}.html.scriban` in the Notifications module.
- **Lookup.** `EmbeddedTemplateStore` (singleton) reads a part from `NotificationCatalog.TemplateAssemblyOf(type)` in the requested culture, else in `en` (an unsupported culture goes straight to `en`), and parses each resource once. A template that exists but does not parse is an error, never a reason to fall back.
- **Model.** A template sees only strings: the variables supplied for the notification plus `product_name` (`Notifications:Templates:ProductName`). Each part is rendered with a fresh `ScriptObject` in a `TemplateContext` with no built-in functions (so no `include`, `date.now` or `object.eval`), no template loader, `StrictVariables`, no .NET members of values, `LoopLimit` 1,000, `RecursiveLimit` 20, an output limit and `CultureInfo.InvariantCulture`. Before rendering, the variables the template mentions (collected from its syntax tree: every global name read, assigned, looped over or declared, since an assignment that never runs must not hide a read; a template's own names are `$` locals) are compared with the ones supplied, so a missing variable fails with its name. `this`, the whole model, is always refused: it would read every secret without naming one.
- **Encoding.** Values are data and are never parsed as templates. For `html` parts every value is `WebUtility.HtmlEncode`d before it enters the model, so a template cannot forget; the layout receives the rendered body as `content` unencoded, and the subject and the product name encoded. Subjects and in-app titles become one line (line breaks and other control characters turn into spaces) of at most 300 characters.
- **Errors.** Every failure is a `TemplateRenderException(typeCode, channel, culture, reason)`. The reason names resources, parts and variable names, never a value; a run-time failure keeps only the position and the exception type, because the engine's message can quote a value. The delivery worker treats it as permanent.
- **Completeness.** Unit tests (`TemplateCompletenessTests`) check, for every registered type: every part of every default channel in every culture, the same placeholders in every culture as in `en`, only declared variables and `product_name`, secret variables only in the email text and HTML (D4), and no embedded template without a declared type or layout. The checker is itself tested against a source with planted problems.

## Consequences
- Positive: template changes are reviewed and versioned like code; a missing translation, a mistyped placeholder or a secret in a subject fails CI instead of a delivery; no seeding, no migration and no table for templates; a template cannot read files, call .NET code or run away; a forgotten encoding cannot inject HTML.
- Negative / trade-offs accepted: changing wording needs a build and a deploy; nobody can edit a template at run time; templates cannot format values (no built-in functions), so callers pass numbers and dates already formatted for the recipient's culture and time zone; `html` values are encoded for element text and quoted attributes only, so a template must not put a value in an unquoted attribute, a `<script>` or a `style`, and a link variable must come from trusted code (Auth builds its links); the `ms` and `zh-Hans` texts, including the layouts, are drafts until a native speaker reviews them.
- Follow-up actions: native review of the `ms` and `zh-Hans` templates (Plan 3, Part C1); database-stored, editable templates with an admin editor and preview can come later behind the same `INotificationRenderer`, with the completeness checks run when a template is saved.
