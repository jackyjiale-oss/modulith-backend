# 0010. Cursor (keyset) pagination; Data API builder not used as the API layer

- Status: Accepted
- Date: 2026-10-07
- Deciders: Lee Jia Le

## Context
List endpoints serve two kinds of client: React admin grids that page forwards and backwards, sometimes with a total, and Flutter screens with infinite scroll that only ever ask for "more". The blueprint (Section 6, "Pagination") proposed `page`/`pageSize` offset paging. Offset paging gets slower the deeper the page (`OFFSET 10000` still reads and discards 10 000 rows) and returns duplicates or skips rows when rows are inserted or deleted between two requests, which is the normal case for a list of leave requests that people keep submitting. The review also weighed Microsoft's Data API builder (DAB), which exposes tables and views as REST/GraphQL endpoints from configuration and paginates with cursors itself (blueprint review, Section 9).

## Options considered
1. Offset pagination (`page`, `pageSize`, `OFFSET … FETCH`) — simplest to implement and lets clients jump to page N; but cost grows with depth and pages shift under concurrent writes.
2. Data API builder as the API layer — list endpoints from configuration in minutes, with cursor paging built in; but writes go straight to tables, bypassing the aggregates, domain events, outbox, audit and soft-delete interceptors; any configured table in any schema becomes reachable, breaking module boundaries; it has its own error format instead of ProblemDetails with `code` and localized `detail`; and it is a second service to deploy, secure and monitor.
3. Our own endpoints with cursor (keyset) pagination — each list is a query handler, but paging cost stays flat at any depth for indexed sort orders, pages are stable under concurrent inserts and deletes, and every module rule (boundaries, soft delete, errors, i18n) still applies.

## Decision
We chose option 3; offset pagination is not offered, and DAB is not the API layer. The design follows review Section 9.3 (P1 to P8).

- **Request and response (P1, P2).** Query parameters `pageSize` (default 20, 1 to 100, else `400 validation.failed` with `errors.pageSize`), `cursor`, `sort` and `includeTotalCount`, plus the endpoint's filters. The response is `CursorPage<T>`: `{ items, pageSize, nextCursor, previousCursor, totalCount? }`. A cursor is `null` when there is no page in that direction; `totalCount` is present only when requested, because it costs an extra `COUNT_BIG(*)` (P5).
- **Cursor (P3, P6).** `CursorCodec` writes base64url JSON `{ "v": 1, "d": direction, "s": sort signature, "f": filter hash, "k": [key values] }`. The filter hash is the first 16 bytes of SHA-256 of the endpoint's canonical filter text (`employeeId=…;status=…`). Clients treat the token as opaque. A token that is malformed, longer than 1 024 characters, of another version, or whose values don't convert to the sort fields' types gets `400 pagination.invalid_cursor`; one issued for a different sort or filters gets `400 pagination.cursor_mismatch` instead of silently wrong pages. Cursors are not signed: tampering only moves the caller's own position, because filters and authorization are applied server-side and every value is a SQL parameter, and signing would need a Data Protection key ring shared by all instances.
- **Sort (P4).** `sort` is comma-separated allow-listed names, `-` meaning descending (`-createdAt`, `startDate,-createdAt`). Each endpoint declares its `SortField`s (API name, bracketed SQL column constant, CLR type); the columns are non-nullable. `SortSpecification.Parse` rejects unknown or repeated names with `400 pagination.invalid_sort` (`params.allowed` lists the names) and always appends the unique `Id` with the direction of the last term, so the order is total. Column text in SQL comes only from these constants, never from input.
- **SQL (P8).** `KeysetSqlBuilder` produces the expanded row comparison `(([CreatedAt] < @k0) OR ([CreatedAt] = @k0 AND [Id] < @k1))` (`<` for descending terms, `>` for ascending), the matching `ORDER BY`, and `Take = pageSize + 1`; the extra row says whether another page exists without a second query. A backward cursor flips the comparisons and the order, and `CursorPageBuilder` re-reverses the rows. `DateTime` key values are sent as `datetime2`, and cursor values are taken from the fetched rows as SQL Server stored them (milliseconds, `datetime2(3)`), never recomputed in .NET, so the next comparison matches exactly. Dapper read handlers still repeat `IsDeleted = 0` (ADR 0006).
- **Indexes (P7).** Every allowed sort has a supporting index `(filter columns…, SortColumn, Id)`; reviewing a migration includes checking this. The Sample module's leave request list has `(EmployeeId, CreatedAt, Id)`, `(CreatedAt, Id)` and `(StartDate, Id)` (migration `AddLeaveRequestListIndexes`). Those indexes cover the single-field sorts and `employeeId` with `-createdAt`; a multi-term sort (`startDate,-createdAt`) or `employeeId` with `sort=startDate` is not covered and falls back to a scan plus a top-N sort. A module either allow-lists only the sorts and filter combinations its indexes cover, or adds the indexes.
- **No page numbers (P5).** An endpoint that truly needs to jump to page N must justify it in its own ADR.
- **Where DAB could still fit.** An optional, post-v1 read-only sidecar over dedicated SQL views for reporting, back-office lookups or AI agents (DAB's SQL MCP server), with its own read-only database login, never writing, and not part of the template's generated output.

The building blocks live in `TemplateName.Application.Common.Pagination` (public, shared by every module): `CursorPageRequest`, `CursorPage<T>`, `CursorDirection`, `SortField`, `SortSpecification`, `Cursor`, `CursorCodec`, `KeysetQuery`, `KeysetSqlBuilder`, `CursorPageBuilder` and `PaginationErrors`, whose messages are in `CommonErrorMessages` (Web.Common) in `en`, `ms` and `zh-Hans`. Application.Common now references Dapper, for `DynamicParameters` in `KeysetQuery`.

## Consequences
- Positive: for indexed sort orders, page cost is the same at any depth; no duplicates or skips while rows are inserted, deleted or share a sort value; one `cursor` parameter for both directions; a changed sort or filter is reported instead of returning wrong pages; dynamic `ORDER BY` cannot be injected.
- Negative / trade-offs accepted: no "jump to page N" and no page numbers in grids; every sortable field needs an index, and sortable columns must be non-nullable; each list is a hand-written query handler instead of configuration; a cursor stops working when the sort or filters change, and an empty page reached with a cursor (the rows beyond it were deleted or left the filter meanwhile) carries only the cursor back the way it came, built from the incoming cursor's position, so the row at that position is not shown again; `totalCount` is an extra query.
- Follow-up actions: the post-v1 backlog keeps the optional DAB reporting sidecar; tenant filters (later plans) become part of each list's filter and canonical filter text.
