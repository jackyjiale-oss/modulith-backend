# 0009. Error codes as the contract, `detail` localized at the HTTP boundary from `.resx`

- Status: Accepted
- Date: 2026-10-07
- Deciders: Lee Jia Le

## Context
The API serves React and Flutter clients in Malaysia, whose users read English, Malay or Simplified Chinese. The blueprint (Section 7.14) gave localization two lines: "`Accept-Language` support; error messages resolved from resource files by error `code`". That leaves open which languages are supported, what is translated and what is not, where the translation happens, how a request's language reaches code that runs inside the exception handler, what background work (outbox handlers) uses, and how missing translations are caught. The blueprint review (Section 8, decisions I1 to I10) settles these.

## Options considered
1. Clients translate everything; the server returns codes only — wording changes need no backend deploy; but simple clients (scripts, admin tools, logs) then show nothing readable.
2. The server returns a localized message only — easy for clients that just display text; but clients cannot reword or reformat it, and a code is still needed to react to an error programmatically.
3. Both: a stable `code` with named `params` that clients can translate themselves, plus a `detail` that the server localizes from `Accept-Language` for clients that simply display it. Messages live in `.resx` files, one set per assembly that defines error codes.
4. Option 3 with messages in a database or a JSON file — editable without a build; but it loses `IStringLocalizer`, satellite assemblies, culture fallback and IDE editors, and puts module text outside the module.

## Decision
We chose option 3.

- **Contract (I1).** Every ProblemDetails keeps its stable `code` (`leave.not_found`) and adds `params` (for example `{ "id": "…" }`) when the error has parameters. Only `detail` follows `Accept-Language`. Codes, `params`, enum values (`"Pending"`) and property names are never localized. `Error.Parameters` go to clients, so they never hold secrets or personal data.
- **Languages (I2).** UI cultures `en` (the neutral resource and the default), `ms` and `zh-Hans`. Region cultures fall back through .NET's parent chain (`zh-CN` and `zh-SG` get `zh-Hans`, `ms-MY` gets `ms`); anything unsupported or malformed (`fr-FR`, `!!!;q=abc`) gets English, never an error.
- **Only the UI culture varies (I3).** `RequestLocalizationOptions` has `SupportedCultures = [en]` and `SupportedUICultures = [en, ms, zh-Hans]`, the `Accept-Language` provider only, `FallBackToParentUICultures` and `ApplyCurrentCultureToResponseHeaders` (responses carry `Content-Language`, except those written by the exception handler; see Consequences). Formatting (`ToString()`, numbers, dates in messages, logs and SQL parameters) is the same for every caller. Built by `ApiLocalizationExtensions.CreateRequestLocalizationOptions` from the `Localization` section (`DefaultCulture`, `SupportedUICultures`); a configured list replaces the default list rather than being appended to it.
- **Resources (I4).** Each assembly that defines error codes has a marker class `{Area}ErrorMessages` in `Resources/` with `{Area}ErrorMessages.resx` (English), `.ms.resx` and `.zh-Hans.resx` beside it; the keys are the error codes. Today: `CommonErrorMessages` (Web.Common: `validation.failed`, `request.malformed`, `server.unexpected_error`, `rate_limit.exceeded`, `http.{400,401,403,404,405,415}`, `pagination.*` from ADR 0010), `InfrastructureErrorMessages` (Infrastructure.Common: `concurrency.conflict`, `idempotency.*`) and `SampleErrorMessages` (`leave.*`). The marker classes are `internal`; `IStringLocalizerFactory` and `ResourceManager` need only the `Type`. `AddErrorMessages<TResource>()` (Application.Common) registers a set; `AddWebCommon`, `AddInfrastructureCommon` and each module's `Add{Module}Module` call it. `IErrorMessageLocalizer` asks the sets in registration order, replaces `{name}` placeholders from the parameters (formatted with the current culture, which is always `en`), leaves unknown placeholders untouched, and returns the English fallback when no set has the code.
- **One place (I5).** Domain errors and the building blocks' error writers (the global and concurrency exception handlers, the idempotency middleware, the rate limiter) set `code` and an English default `detail`. `ProblemDetailsOptions.CustomizeProblemDetails` replaces `detail` with the localized message for `code` and `params`, falling back to the English detail or the title. Nothing else translates. In Development the global exception handler puts the exception text in an `exceptionDetails` extension; `detail` stays the generic, localized message in every environment.
- **Middleware order (I6).** `UseApiLocalization` is pipeline slot 1a, before `UseExceptionHandler`. Culture is async-local: set inside the exception-handler middleware, it would not be visible to the handler, and 500 and malformed-body responses would come back in English. A test moves the middleware and watches `Exception_handler_responses_are_localized` fail.
- **Background work (I7).** `UseApiLocalization` sets `CultureInfo.DefaultThreadCurrentCulture` and `DefaultThreadCurrentUICulture` to `DefaultCulture`, so outbox handlers and jobs never pick up the server's regional settings. Work done for a specific user (notifications, Plan 3) passes that user's locale explicitly.
- **Fail fast (I8).** `ApiLocalizationOptions` is validated on start: `DefaultCulture` must be in `SupportedUICultures`, and every name must pass `CultureInfo.GetCultureInfo(name, predefinedOnly: true)`. A container without ICU (invariant globalization) stops at boot instead of serving English everywhere.
- **Completeness (I9).** `TranslationTests` (architecture tests) fail when a translation misses or adds a key, uses different `{placeholders}` than the English text, or when an `Error` declared in a module's `*Errors` class (or a building block's) has no English entry. The error catalogue (`ErrorCatalog`) reads static fields, properties and factory methods of `*Errors` classes.
- **Validation messages (I10).** FluentValidation localizes its own messages from `CurrentUICulture`. It has no `ms` and only `zh-CN`, which a `zh-Hans` UI culture never reaches, so `ValidationMessageTranslations` (a `LanguageManager`) adds `ms` and `zh-Hans` text for the validators in use and the common ones, with FluentValidation's placeholders unchanged. FluentValidation keeps one process-wide language manager (`ValidatorOptions.Global.LanguageManager`); `AddApiLocalization` sets it. Every host sets the same translations, so building several hosts in one process (integration tests) is harmless.
- **Drafts.** The `ms` and `zh-Hans` texts carry `<comment>Draft – needs native review</comment>` until a native speaker has reviewed them, which is a release task (CONTRIBUTING, Section 5).

## Consequences
- Positive: clients can rely on `code` and `params` and still show a ready-made message; each module keeps its text in its own assembly (ADR 0001); culture fallback, satellite assemblies and resx editors come with .NET; missing translations fail CI; formatting never depends on the caller's language.
- Negative / trade-offs accepted: every new error code needs three resx entries; the building blocks' English defaults exist both in code and in the neutral resx (the code copy is only the fallback); FluentValidation's language manager is global state; a message changes only with a deploy; `Content-Language` is not sent on responses written by the exception handler, because that middleware clears the response headers before handling.
- Follow-up actions: Plan 2 adds a `locale` claim provider ahead of `Accept-Language` and `AuthErrorMessages`; Plan 3 renders notifications in the recipient's locale; Plan 5 varies cached localized responses by `Accept-Language`; Plan 6 ships ICU in the image; a native speaker reviews the `ms` and `zh-Hans` drafts before v1.0.
