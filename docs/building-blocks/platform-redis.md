# Platform.Redis (`TemplateName.Platform.Redis`)

## Purpose

The optional Redis project ([ADR 0027](../adr/0027-optional-redis-through-one-project.md)). With `Caching:Provider = redis` it makes Redis the shared second level (L2) of `HybridCache`, so a permission set loaded by one API instance is served to the others without a database read, it counts the fixed-window rate limits in Redis, so every instance shares one count per client ([Rate limiting](#rate-limiting)), and it is SignalR's backplane, so a live push made on one instance reaches the user's connections on every instance ([SignalR backplane](#signalr-backplane)); with any other provider it registers nothing. It holds the one Redis connection of the instance, the circuit that keeps a Redis outage away from requests, and the readiness check `redis`. Redis is never required: the default provider is `memory`, and with Redis down the API keeps serving from the database, limits in memory per instance and delivers in-app notifications to the inbox without the live push.

It depends on Infrastructure.Common (the `Caching` options), Web.Common, Application.Common, SharedKernel, `StackExchange.Redis`, `Microsoft.Extensions.Caching.StackExchangeRedis` and `Microsoft.AspNetCore.SignalR.StackExchangeRedis` (all MIT). **Only the host references it** (`LayeringTests.Only_the_host_references_Platform_Redis`), so a solution that will never use Redis deletes the project and its packages go with it ([below](#remove-the-project-from-a-generated-solution)).

Code: `src/BuildingBlocks/TemplateName.Platform.Redis/`.

After `FailureThreshold` consecutive failures the circuit is open for `BreakDuration` (time from the application's `TimeProvider`) and `TryBeginCall` refuses every call. After the break the circuit is half-open: **one** call, the probe, goes to Redis while every other caller still skips it until the probe reports; its success closes the circuit and resets the count, its failure opens it for another break at once. It logs one warning per outage window (from the circuit opening until the next success, however many breaks that takes) and one information line when Redis answers again. Every asynchronous call is bounded: one that has not finished after `CommandTimeout` (measured with the application's `TimeProvider`) is given up and counted as a failure. While the circuit is open it does not call Redis at all, and when half-open only its probe does. It does not report to the circuit or take its probe. |

## Configuration

`Caching:Provider` belongs to Infrastructure.Common ([infrastructure-common](infrastructure-common.md#caching)); the keys below are read only when it is `redis`. All of them are listed with defaults in [API host: `Caching`](../services/api.md#caching).

| Key | Default | Validation (on start, provider `redis` only) | Meaning |
|---|---|---|---|
| `ConnectionStrings:Redis` | empty | required | A StackExchange.Redis configuration string, for example `localhost:6379` or `redis.internal:6380,password=…,ssl=true`. A password belongs in user secrets or the environment (`ConnectionStrings__Redis`). `abortConnect` and the timeouts in it are overridden (below). |
| `Caching:Redis:InstanceName` | `TemplateName:` | required | The prefix of every key, so applications can share one server, and of the backplane's channels (`{InstanceName}signalr`). |
| `Caching:Redis:FailureThreshold` | `3` | 1 to 100 | Consecutive failed Redis calls that open the circuit. |
| `Caching:Redis:BreakDuration` | `00:00:30` | `00:00:01` to `01:00:00` | How long Redis is skipped once the circuit opens. |
| `Caching:Redis:CommandTimeout` | `00:00:00.500` | `00:00:00.050` to `00:00:30`, and shorter than `BreakDuration` (so a call cannot outlive a break and free the probe slot while a second probe runs) | The connect, synchronous and asynchronous timeouts of the connection, and the bound the cache, the rate limiters and the readiness check put on every asynchronous call (and on each `PING`): the most a request or a check waits, per Redis call, for a Redis that does not answer before the call counts as a failure. The SignalR backplane relies on the connection's timeouts alone ([SignalR backplane](#signalr-backplane)). The heartbeat, on which StackExchange.Redis checks for timed-out commands, is shortened to it (at most one second), and while the connection is down commands fail at once (`FailFast`) instead of queueing for the reconnect. Without a short timeout a dead Redis would add seconds to every request until the circuit opens. |

A host whose `Caching:Provider` is `redis` but which does not call `AddPlatformRedis` fails on start (`Caching:Provider is redis, but no distributed cache is registered`) instead of caching in memory only without saying so.

### The shared connection

The instance has one `IConnectionMultiplexer`, created and owned by the container, which disposes it when the host stops. The cache, the rate limiters, the readiness check and the SignalR backplane use it. A limiter holds only the connection's `IDatabase` handle and never closes or disposes it, so the ASP.NET Core rate limiter can create and dispose limiters per partition freely. `RedisCache.Dispose` closes and disposes the connection it got from its factory, so the decorator never disposes the inner `RedisCache` (`CachingProviderTests.Disposing_the_cache_does_not_close_the_shared_connection`). SignalR's `RedisHubLifetimeManager.Dispose` does the same to the connection its `ConnectionFactory` returned (it calls `Dispose` on it; a test proved it before the fix), so the factory returns a `BorrowedConnection` over the shared one, on which `Dispose`, `DisposeAsync`, `Close` and `CloseAsync` do nothing (`SignalRBackplaneTests.Disposing_the_backplane_does_not_close_the_shared_connection`). Its `Dispose` also calls `UnsubscribeAll` on the connection's subscriber, which is harmless: only the backplane subscribes, and the host is stopping. For the same reason the StackExchange.Redis AppContext switch `Microsoft.AspNetCore.Caching.StackExchangeRedis.UseForceReconnect` must stay off: with it on, `RedisCache.OnRedisError` releases (closes) the connection after errors, which would close the shared connection under the other users.

**When it connects.** At host start, not on the first request. With a hub mapped (the template maps `/hubs/notifications`), `MapHub` creates the hub's `RedisHubLifetimeManager`, which connects at once through its `ConnectionFactory`; without one, the ASP.NET Core rate-limiting middleware reads `RateLimiterOptions` when the request pipeline is built (in its constructor, as the host starts), which resolves the limiter factory and with it the connection. The connect is synchronous: with Redis down the host still starts (`abortConnect=false`) but waits for it first, up to StackExchange.Redis's `ConnectRetry` (3) attempts of `ConnectTimeout` (`CommandTimeout`) each. Measured with Valkey stopped and the default 500 ms: between 0.1 s (connection refused at once) and 1.1 s of the start; 0.6 s with a 200 ms `CommandTimeout`.

## Keys

`{InstanceName}{module}:{entity}:{id}`, with no tenant (the template has none). The module writes `{module}:{entity}:{id}`; `InstanceName` is added by the Redis cache. Today there is one cache entry: the Auth module's permission set, `auth:perm:{userId}` in the module, `TemplateName:auth:perm:{userId}` in Redis ([Auth module](../modules/auth.md#permission-checks)). A module adding a cached entry follows the same shape, so two modules never collide and `redis-cli --scan --pattern 'TemplateName:auth:*'` finds one module's keys.

The rate limiters write `{InstanceName}rl:{policy}:{partitionKey}`: `TemplateName:rl:global:ip:203.0.113.7`, `TemplateName:rl:global:user:{sub}`, `TemplateName:rl:auth-strict:ip:::1` (an IPv6 address keeps its colons), `TemplateName:rl:notifications-hub-tickets:user:{sub}`. The value is the count of the current window and the key expires with the window, so `redis-cli --scan --pattern 'TemplateName:rl:*'` lists the windows in use and nothing is left behind.

## Degradation

Redis is a cache here, so losing it costs speed, not correctness (spec section 4):

| When | What happens |
|---|---|
| Redis is down when the host starts | The host starts (`abortConnect=false`), after waiting for the connect ([When it connects](#the-shared-connection)); the multiplexer keeps reconnecting in the background. Readiness is `Degraded`. |
| Redis stops answering while the host runs | While the connection is down (refused, reset) an L2 call fails at once (`FailFast`); while it still looks up but Redis does not answer, the call is given up after `CommandTimeout`. Either way it answers a miss (a read) or is dropped (a write, refresh, remove). The value comes from the database. After `FailureThreshold` consecutive failures the circuit opens and requests stop waiting on Redis altogether for `BreakDuration`. One warning is logged for the outage. |
| Readiness during the outage | `/health/ready` answers **200 `Degraded`**, not 503 `Unhealthy`, at once during a break of the circuit and within `CommandTimeout` otherwise: the instance still serves, and a load balancer must not drain every instance for a cache outage. Alert on `Degraded` instead. |
| Redis comes back | The multiplexer reconnects by itself. When the break is over, one probe call goes to Redis (the others still miss to the database until it reports); its success closes the circuit and an information line is logged, its failure starts another break. Readiness does not ping during a break, so it stays `Degraded` for up to `BreakDuration` after Redis is back; from the end of the break it pings again and turns `Healthy` on the first `PING` that succeeds. |
| Rate limits during the outage | Each request is counted by the instance's in-memory window of the same limit (one per partition, kept until its window is over), so every instance limits on its own and a client gets up to **instances × limit** until Redis is back. With the circuit closed a request waits at most `CommandTimeout` per Redis call (not at all while the connection is down, `FailFast`); the `auth-strict` routes and the hub ticket route run the global limiter and their own one after the other, so up to twice that while Redis hangs. During a break it does not call Redis. When Redis answers again the count continues from what Redis holds; the requests counted in memory meanwhile are not added to it. |
| Live pushes during the outage | The in-app delivery still succeeds: the delivery ends `Sent` and the inbox row exists. The push itself fails (at once while the connection is down, after the command timeout while Redis hangs), and `SignalRInAppNotificationPusher` logs a Warning and carries on; with the backplane even a connection on the delivering instance gets nothing live, because every push goes through Redis. New hub connections are closed with an error right after the handshake; open ones stay open. When Redis is back, pushes reach every instance again, with no restart ([SignalR backplane](#signalr-backplane)). |
| A removal fails, or is skipped because the remover's circuit is open | The entry stays in Redis until its own expiration (at most 30 seconds for a permission set). Another instance whose first level expires meanwhile reads the old value from Redis and keeps it for another first-level lifetime, so the stale window is up to about **twice** the lifetime (the remaining Redis time plus one first-level lifetime: about 60 seconds for a permission set). Removals that fail are not retried. |

The first-level cache (`IMemoryCache`, per instance) keeps working throughout, so an instance that has a value keeps using it for its local lifetime whether Redis is up or not.

## Rate limiting

With `redis`, the `global` limiter, `auth-strict` and `notifications-hub-tickets` (every fixed-window policy, through Web.Common's `IFixedWindowLimiterFactory`) count in Redis instead of in memory, so N instances allow one limit per client, not N times it (D5, [ADR 0027](../adr/0027-optional-redis-through-one-project.md)). The limits, windows, partition keys, the 429 `rate_limit.exceeded` problem and `Retry-After` are unchanged ([API host: `RateLimiting`](../services/api.md#ratelimiting)).

- **One script per request.** Each acquire runs this Lua script once (`EVAL`, atomic on the server), with the key as `KEYS[1]` and the permits and the window in milliseconds as `ARGV`; nothing is written into the script, so a partition key such as `ip:::1` cannot change it:

  ```lua
  if tonumber(ARGV[1]) == 0 then                         -- no permit asked for: only read, never create or extend a window
      return { tonumber(redis.call('GET', KEYS[1]) or '0'), redis.call('PTTL', KEYS[1]) }
  end
  local count = redis.call('INCRBY', KEYS[1], ARGV[1])   -- ARGV[1] is 1 for an HTTP request: INCR
  local ttl = redis.call('PTTL', KEYS[1])
  if count == tonumber(ARGV[1]) or ttl < 0 then          -- a new window, or a key that lost its expiry
      redis.call('PEXPIRE', KEYS[1], ARGV[2])
      ttl = tonumber(ARGV[2])
  end
  return { count, ttl }
  ```

  The request is allowed while `count` is within the limit. A refusal carries `Retry-After` from `ttl`, at least one second (the 429 writer rounds it up to whole seconds). Refused requests are counted too, which changes nothing: the window is exhausted until the key expires. The key's expiry is the window, so a window starts at the first request on any instance and rolls over in Redis's time. A key without an expiry (written by hand, or left by a failed `PEXPIRE`) gets one on the next request instead of limiting forever. A request for no permit (`AcquireAsync(0)`, which asks whether any is left; the middleware never makes one) only reads the count and the time to live: `INCRBY` by 0 would create a missing key, and the next real request would then find a count equal to its permits and restart the window.
- **No queue, and `AttemptAcquire`.** As with the in-memory default, a request beyond the limit is refused at once. The synchronous `AttemptAcquire` cannot wait for Redis: during a break of the circuit it answers from the in-memory window; otherwise it refuses without counting and without `Retry-After`, because the ASP.NET Core middleware calls `AttemptAcquire` first and `AcquireAsync` only after a refusal (an answer from memory there would keep every request away from Redis). A permit count above the limit throws, as the built-in limiter does. One visible effect: the middleware counts a request whose `AcquireAsync` did not complete synchronously as queued, so with `redis` the queue metrics `aspnetcore.rate_limiting.queued_requests` and `aspnetcore.rate_limiting.request.time_in_queue` are non-zero (the time is the Redis round trip), although nothing waits in a queue; the lease and rejection counts (`aspnetcore.rate_limiting.requests`, `request_lease.duration`) stay correct.
- **Failure.** Every call goes through `RedisAvailability`, like the cache: a call that fails or has not answered after `CommandTimeout` is recorded as a failure; while the circuit is open (or another caller holds the half-open probe) Redis is not called; in both cases the request is counted by the limiter's in-memory window of the same limit and window. The cost is **instances × limit** while Redis is down ([Degradation](#degradation)). The caller's own cancellation (the request aborted) propagates, is not a Redis failure, is not counted in memory and frees a probe it held.
- **Lifetime.** The ASP.NET Core rate limiter keeps one limiter per partition key and disposes it after about ten seconds idle. A Redis limiter is cheap to create (the `IDatabase` handle and the key; its in-memory window only once it needs one) and reports itself idle only when no call is in flight and its in-memory window, if any, holds no permits, so a partition is never dropped with a count that only that instance knows.

## SignalR backplane

With `redis`, `AddPlatformRedis` calls `AddSignalR().AddStackExchangeRedis()`, so SignalR's `RedisHubLifetimeManager` replaces the in-memory one for every hub (today the Notifications hub, `/hubs/notifications`). A push made on one instance (`Clients.User(userId)` from the delivery worker that delivered the notification) is published to Redis, and every instance with a connection of that user sends it on: the live push reaches all of the user's tabs, whichever instance each is connected to (D13; `RedisBackplaneTests.A_push_made_on_host_A_reaches_a_client_connected_to_host_B`). Hub tickets stay in SQL, and their per-user limit is the shared `notifications-hub-tickets` window ([Rate limiting](#rate-limiting)), so negotiate and the WebSocket may hit different instances. The hub, its clients and its contract do not change; without Redis the in-memory lifetime manager pushes to the delivering instance's connections only, as before.

- **One connection.** The backplane's `RedisOptions.ConnectionFactory` returns the instance's shared connection (as a `BorrowedConnection`, [The shared connection](#the-shared-connection)), so it opens no connection of its own and shares the connection's timeouts and `FailFast`. `RedisOptions.Configuration` is set to the same settings, so what the backplane logs is true; it does not connect with them.
- **Channels.** SignalR names its channels `{hub type}:user:{userId}`, `{hub type}:connection:{connectionId}`, `{hub type}:all`, `{hub type}:internal:groups` and so on. Handed a connection, it cannot prefix them itself, so the prefix is the connection's `ChannelPrefix`, set to `{InstanceName}signalr` whatever the connection string says; StackExchange.Redis writes it in front of every channel, with no separator: `TemplateName:signalrTemplateName.Modules.Notifications.Infrastructure.Hubs.NotificationsHub:user:{userId}`. Two applications on one server therefore never hear each other's pushes, and `redis-cli PUBSUB CHANNELS 'TemplateName:signalr*'` lists this application's channels. Only the backplane uses pub/sub on the connection. StackExchange.Redis's own configuration channel (`__Booksleeve_MasterChanged`, which clients use to announce a primary change in a replicated set-up) gets the prefix too; every instance of the application has the same prefix, so they still hear each other.
- **No circuit.** The backplane is SignalR's code: it calls the connection directly, not through `RedisAvailability`, so a Redis outage neither opens the shared circuit nor is skipped by it. It is bounded by the connection itself instead: while the connection is down a publish fails at once (`FailFast`), and while Redis hangs it fails with a timeout after `CommandTimeout`, noticed on the next heartbeat (measured with a paused Valkey and the default 500 ms: 0.49 s to 1.0 s per push).
- **Redis down.** A push fails and `SignalRInAppNotificationPusher` logs a Warning with the exception type only and returns. That is one Warning per failed push for as long as the outage lasts, not one per outage window (the circuit's single warning covers the cache only, which the backplane does not use); a busy instance logs a line for every notification it delivers. The pusher's `catch` is deliberately broad: it takes any exception the send throws (a Redis exception or a timeout, whatever type the client library throws), because a push is best effort and must never fail the delivery, and it lets only the caller's own cancellation through. The delivery is not affected (it is `Sent`, its inbox row exists) and `InAppChannel`'s own 5-second bound never comes into play (`RedisBackplaneTests.Valkey_stopped_a_notification_still_delivers_and_its_inbox_row_exists`). Every push goes through Redis, the delivering instance's own connections included, so none is pushed live during the outage; the inbox has them all. A new hub connection cannot subscribe to its channels, and the server closes it with an error right after the handshake (the client reconnects later); open connections stay open.
- **Redis back.** StackExchange.Redis subscribes the open connections again when it reconnects, and an instance started while Redis was down subscribes its connections as they open, so `Clients.User` pushes cross instances again without a restart (`RedisBackplaneTests.After_Valkey_comes_back_pushes_cross_instances_again`). A notification delivered during the outage is not pushed afterwards.
- **Limit: a manager that is created while Redis is down.** SignalR's `RedisHubLifetimeManager` (a singleton, created when the first hub connection or the first push on that instance needs it) sets up its host-wide subscriptions in its constructor, in a task nobody awaits (`EnsureRedisServerConnection`, read in the installed 10.0.13 package). It stores the connection first and then subscribes, one after the other, to the `all`, group-management, acknowledgement and client-result channels. If the manager is created in an outage, the first subscribe fails, the error is lost with the unobserved task and the other three are never attempted; the connection is already stored, so no later call sets them up again. StackExchange.Redis does restore that first subscription when Redis is back (checked with a scratch program: a subscribe that failed while Redis was down shows one subscriber on the server after the reconnect), but it holds a message queue that nothing reads. That instance then never serves `Clients.All`, group changes made for a connection on another instance, or client results until it is restarted. Nothing in the template is affected: the hub uses only `Clients.User`, whose subscription is made per connection when the connection opens and is restored by the reconnect, and the committed test builds its late host while Redis is down but makes the first connection, which creates the manager, only after Redis is back, so it does not cover this case. A feature that adds `Clients.All`, groups or client results has to account for this: an instance whose manager was created in an outage needs a restart.

## Cross-instance invalidation: the honest limit

`HybridCache.RemoveAsync` clears the entry in Redis and in the first level of the instance that calls it. It does **not** reach the first level of the other instances: nothing tells them. Another instance that read the entry before the removal keeps serving it until its local copy expires. For a permission set that is at most **30 seconds** (`PermissionCache.Lifetime`, both levels): a user who loses a permission can keep using it on another instance for up to 30 seconds after the change. This is the limit the blueprint review (2.7) and [ADR 0016](../adr/0016-server-side-permissions-with-per-user-cache.md) accept; `RedisCacheTests.Invalidating_on_A_is_seen_by_B_after_the_thirty_second_L1_lifetime` pins it to the millisecond. If the removal itself does not reach Redis (Redis failed, or the remover's circuit was open), the window grows to about twice the lifetime, up to 60 seconds: the old set stays in Redis for what is left of its 30 seconds, and an instance that reads it then keeps it for another 30 ([Degradation](#degradation)). Removing the stale window needs pub/sub invalidation of the first level, which is not built (post-v1). Without Redis the same 30 seconds apply, with each instance also reading the database on its own.

## Running Redis locally

Docker Compose has a `valkey` service (Valkey: BSD-3, Redis-protocol compatible; ADR 0027) behind the profile `redis`, published on `127.0.0.1:6379` only (it has no password). Its image tag is pinned and matches `ValkeyFixture.Image` (a test checks it).

```bash
docker compose --profile redis up -d
Caching__Provider=redis ConnectionStrings__Redis=localhost:6379 dotnet run --project src/Host/TemplateName.Api
```

`docker compose up -d` without the profile does not start it.

## Remove the project from a generated solution

A solution that will never use Redis can delete the project; nothing else references it.

1. Delete `src/BuildingBlocks/TemplateName.Platform.Redis/` and its line in `TemplateName.slnx`.
2. In `src/Host/TemplateName.Api`: remove the project reference from the `.csproj`, and the `AddPlatformRedis` call and its `using` from `Program.cs`. Remove `ConnectionStrings:Redis` and `Caching:Redis` from `appsettings.json` (keep `Caching:Provider`; `memory` and `none` still work).
3. In the tests: remove the project reference from `TemplateName.UnitTests` and `TemplateName.ArchitectureTests`; delete `tests/TemplateName.UnitTests/Platform/` and `tests/TemplateName.IntegrationTests/Redis/` and `Infrastructure/ValkeyFixture.cs`; remove `PlatformRedis` from `Assemblies.cs`, `platform-redis` from `DocumentationTests.Every_building_block_has_a_document`, and the test `LayeringTests.Only_the_host_references_Platform_Redis`. Remove the `Testcontainers.Redis` reference from the integration tests.
4. Remove `StackExchange.Redis`, `Microsoft.Extensions.Caching.StackExchangeRedis`, `Microsoft.AspNetCore.SignalR.StackExchangeRedis` and `Testcontainers.Redis` from `Directory.Packages.props`, the `valkey` service from `docker-compose.yml`, this document and its row in `docs/README.md`, then run `dotnet restore --force-evaluate` to update the lock files.

`Caching:Provider = redis` then fails on start with a message naming `AddPlatformRedis`.
