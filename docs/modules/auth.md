## Purpose and boundaries

<!-- What the module owns, what it deliberately does not do, and which other modules it talks to (only through *.Contracts). -->

The sign-in and authorization module: registration with email confirmation, login with lockout, refresh-token rotation with reuse detection, logout, password reset and change, session management, role-based permissions with administration of users, roles and the audit log, and two-step verification (an authenticator app with recovery codes, a step-up before sensitive actions, trusted devices and an administrator's reset). It was built in Plan 2 (auth core) and Plan 4 (multi-factor authentication); [Known limits](#known-limits) lists what it deliberately leaves out or only approximates.

- Owns: users, roles, permissions, sessions, verification codes, two-step verification (methods, recovery codes, sign-in challenges, trusted devices), the auth audit log (the security log; the field-level trail of `User`, `Role`, `RolePermission` and `UserRole` is the [Audit module](audit.md)'s, see [Audited entities](#audited-entities)), the Data Protection key ring and the `auth` schema.
- Does not: send email or any other message itself (it publishes integration events, and the Notifications module renders and delivers the emails, see [Events](#events)), check access tokens against session revocation on every request (ADR 0015), or support usernames, tenants or progressive lockout.
- Talks to: no other module. It exposes the `TemplateName.Modules.Auth.Contracts` project (see [Events](#events)): the integration events a notifying module consumes and `IUserContactDirectory`, which looks up a user's address, name, language and time zone. Auth references no other module.
- Decisions: [ADR 0014](../adr/0014-own-identity-model-with-identity-password-hasher.md) (own identity model), [ADR 0015](../adr/0015-es256-jwt-with-configured-signing-keys.md) (ES256 tokens, configured keys), [ADR 0016](../adr/0016-server-side-permissions-with-per-user-cache.md) (permissions resolved server-side), [ADR 0017](../adr/0017-outbox-secrets-protected-with-data-protection.md) (outbox secrets protected with Data Protection), [ADR 0018](../adr/0018-in-process-integration-events-with-inbox.md) (in-process integration events), [ADR 0020](../adr/0020-secrets-in-cross-module-events.md) (single-use links cross module boundaries encrypted), [ADR 0022](../adr/0022-totp-secrets-and-replay-protection.md) (TOTP and recovery codes), [ADR 0023](../adr/0023-step-up-through-auth-time-and-amr.md) (step-up), [ADR 0024](../adr/0024-mfa-challenge-as-a-hashed-server-side-token.md) (the sign-in challenge) and [ADR 0025](../adr/0025-trusted-devices-bound-to-the-security-stamp.md) (trusted devices).

Code: `src/Modules/Auth/TemplateName.Modules.Auth/`. The host calls `AddAuthModule(configuration)`, maps `MapAuthEndpoints()` on the `/api/v1` group and `MapAuthWellKnownEndpoints()` on the application root (for `/.well-known/jwks.json`), and calls `SeedAuthModuleAsync(cancellationToken)` after the migration step (see [Background processing](#background-processing)). `AddAuthModule` registers the persistence (context, outbox, repositories, audit writer, Data Protection key ring; see [Data](#data)), the security services ([Security services](#security-services)), the access tokens and the JWT bearer handler ([Access tokens](#access-tokens)), the permission checker, its cache and the seeder ([Permission checks](#permission-checks)), every handler and validator, the sign-in settings, the counters of its meter ([Observability](#observability)) and its error messages. `MapAuthEndpoints` maps four groups: the self-service `auth` group (`Endpoints/AuthEndpoints.cs`), `admin/auth/users` (`Endpoints/AdminUserEndpoints.cs`), `admin/auth/roles` with `admin/auth/permissions` (`Endpoints/AdminRoleEndpoints.cs`) and `admin/auth/audit-logs` (`Endpoints/AdminAuditLogEndpoints.cs`). The flows are described in [Registration](#registration), [Login and current user](#login-and-current-user), [Refresh and logout](#refresh-and-logout), [Sessions and profile](#sessions-and-profile), [Passwords](#passwords), [Multi-factor authentication](#multi-factor-authentication), [User administration](#user-administration) and [Role, permission and audit log administration](#role-permission-and-audit-log-administration).

## Endpoints

<!-- Every endpoint, written as METHOD + full route (e.g. GET /api/v1/{module}/{resources}/{id:guid}), with its success status and error codes. -->

The module's routes are `/api/v1/auth/...` (self-service, tag `Auth`) and `/api/v1/admin/auth/...` (administration, tag `Auth administration`). The JWKS lives at the root, outside `/api/v1`, because verifiers look for it at the well-known path.

Every self-service route below except `GET /api/v1/auth/me`, `PUT /api/v1/auth/me`, `GET /api/v1/auth/sessions`, `DELETE /api/v1/auth/sessions/{id}`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/logout-all`, `POST /api/v1/auth/password/change`, `POST /api/v1/auth/step-up`, `POST /api/v1/auth/mfa/totp/setup`, `POST /api/v1/auth/mfa/totp/confirm`, `GET /api/v1/auth/mfa/methods`, `DELETE /api/v1/auth/mfa/methods/{id}`, `POST /api/v1/auth/mfa/recovery-codes/regenerate`, `GET /api/v1/auth/trusted-devices` and `DELETE /api/v1/auth/trusted-devices/{id}` is anonymous: it says `.AllowAnonymous()` explicitly and has `.RequireRateLimiting(RateLimitPolicies.AuthStrict)` (10 requests per minute per client address by default, shared by all ten `auth-strict` routes, on top of the global limit; 429 `rate_limit.exceeded` with `Retry-After`). The bodies are JSON; a missing or malformed body, or one that fails the validator, is a 400 validation problem (`validation.failed`, with `errors` per field), which says nothing about accounts. The fifteen authenticated self-service routes say `.RequireAuthorization()` explicitly (Ruling R13), so the OpenAPI document shows their bearer requirement, and without a valid access token they answer 401 `http.401`. They are limited by the global limiter (per user); `POST /api/v1/auth/password/change` and `POST /api/v1/auth/step-up` check a password or a code, so they also have `auth-strict` (per client address), which keeps a stolen access token from guessing at the global rate.

**The ten `auth-strict` routes.** Exactly these carry the policy, and they share one budget per client address: the eight anonymous ones that check or send a credential (`POST /api/v1/auth/register`, `/email/confirm`, `/email/resend-confirmation`, `/login`, `/token/refresh`, `/password/forgot`, `/password/reset` and `/mfa/verify`) and the two authenticated ones that check a password or a code (`POST /api/v1/auth/password/change` and `/step-up`). `POST /api/v1/auth/mfa/verify` and `POST /api/v1/auth/step-up` are the routes that take a TOTP or recovery code, so they must keep it (every wrong code also counts toward `Auth:Lockout`, but the per-address limit is the only bound on how fast one address can try); no other MFA route has it. `AuthStrictRoutesTests.Exactly_ten_routes_carry_auth_strict_among_them_mfa_verify_and_step_up` reads the host's endpoint metadata and fails when a route gains or loses the policy, so a change here is a change to this list and to [API host](../services/api.md#ratelimiting). Their window is counted per instance by default and in Redis, shared by every instance, with `Caching:Provider = redis` (key `{InstanceName}rl:auth-strict:ip:{address}`, [platform-redis](../building-blocks/platform-redis.md#rate-limiting)).

The administration routes each require their own permission with `.RequirePermission(...)` (Ruling R13; without a valid access token 401 `http.401`, without the permission 403 `http.403`) and are limited by the global limiter only. Every one names the caller as the acting administrator (the token's `sub`). See [User administration](#user-administration) and [Role, permission and audit log administration](#role-permission-and-audit-log-administration) for the rules behind each.

## Domain model

<!-- Aggregates, their invariants and life cycle. Draw state machines as a Mermaid stateDiagram-v2. -->

`User` (`Domain/Users/`) is the first aggregate and `Role` (`Domain/Roles/`) the second; `UserSession` (`Domain/Sessions/`) the third and `VerificationCode` (`Domain/Verification/`) the fourth; the audit log entry `AuthAuditLog` (`Domain/Audit/`) is a plain entity. A user is identified by its email, kept trimmed (`Email`) and upper-case (`NormalizedEmail`, the form used for lookups and the unique index). It owns its password history (`PasswordHistoryEntry`) and its role assignments (`UserRole`), and it is audited and soft-deleted.

- **Registration:** `User.Register(email, displayName, locale, passwordHash, now)` creates an active, unconfirmed user with a new `SecurityStamp` and the time zone `UTC`. A user created by an administrator has no `PasswordHash` (valid; the history is then empty); a non-null hash is the first history entry.
- **Email confirmation:** `ConfirmEmail` is idempotent; only the first call raises `EmailConfirmedDomainEvent`. `EnsureCanSignIn` refuses a suspended user (`auth.account_inactive`) and an unconfirmed one (`auth.email_not_verified`).
- **Lockout:** `RecordFailedSignIn` counts failures; at the configured threshold it sets `LockoutEnd` to `now + duration` and raises `UserLockedOutDomainEvent`. The account is locked while `now < LockoutEnd`, so it is open again exactly at `LockoutEnd`. A failure after the lockout expired starts a new count; a failure while locked changes nothing. A successful sign-in, a password change and `Reinstate` clear the failures and the lockout.
- **Password:** `ChangePassword` rotates `SecurityStamp`, appends the new hash to the history and keeps at most `historyCount` entries including the current one (the oldest are dropped). The reuse check itself runs in the application layer against the history. `UpgradePasswordHash` stores a new hash of the **same** password (a rehash after a successful verification with weaker parameters): only `PasswordHash` changes, not the stamp, the history, `PasswordChangedAt` or the sign-in state, and no event is raised; a user without a password throws `InvalidOperationException`.
- **Suspension:** `Suspend` rotates `SecurityStamp` (so issued tokens stop matching) and is idempotent; `Reinstate` makes the account active again and is idempotent.
- **Registration attempts:** `NoteRegistrationAttempt` raises `RegistrationAttemptedDomainEvent` and changes no state, so the registration answer stays the same for known and unknown addresses.
- **Roles:** `AssignRole` and `RemoveRole` are idempotent. A user refers to a role by id (`UserRole`); the `Role` aggregate is described below.

`UserStatus` (`Domain/Users/`) is persisted by its numeric value, so a new state is appended and existing values are never renumbered.

```mermaid
stateDiagram-v2
    [*] --> Active: register
    Active --> Suspended: suspend
    Suspended --> Active: reinstate
```

`Role` (`Domain/Roles/`) is a named set of permissions, audited and soft-deleted, with a `RowVersion` for optimistic concurrency. `Permission` is a plain entity (`Code`, `Module`, `Name`, `Description`, `IsDeprecated`); `RolePermission(RoleId, PermissionId)` is a grant.

- **Names:** `Role.Create(name, description, now)` trims the name and stores `NormalizedName` (upper-case, the form for the unique index); a blank name is a programming error (`ArgumentException`), because the application validator rejects it first.
- **System roles:** `SystemRoles` names `SuperAdmin`, `Admin` and `User`. `Role.CreateSystem` builds them for the seeder. A system role cannot be renamed (`UpdateDetails`) or deleted (`MarkDeleted`): both answer `auth.system_role_protected`. `IsSuperAdmin` is true for the system role whose `NormalizedName` is `SUPERADMIN`, whatever the spelling it was created with; a custom role never is. `MarkDeleted` checks the rule and, for a custom role, also drops its grants (a deleted role grants nothing, and a new role that takes its name starts empty); the delete handler removes the role from the repository afterwards and the save interceptor performs the soft delete. The name and description limits are `Role.MaxNameLength` (100) and `Role.MaxDescriptionLength` (500), shared by the validators and the columns.
- **Permission set:** `SetPermissions` replaces the set, ignores duplicates and is idempotent; it is refused for `SuperAdmin` (`auth.system_role_protected`), whose set the seeder keeps equal to every declared permission through `SyncPermissions` (same replacement, no protection, internal use only).
- **Permissions:** a permission that is no longer declared is deprecated (`SetDeprecated`), never deleted, so existing grants stay readable.

### Permissions

Codes are `module.resource.action` in snake case. Each module declares its own through `IPermissionSource` (see [Application.Common](../building-blocks/application-common.md)), registered as a singleton; the Auth module declares these in `Application/AuthPermissions.cs` and `AuthPermissionSource` (module `auth`, English names), which `AddAuthModule` registers. The seeder syncs every registered source into `auth.Permissions` (see [Background processing](#background-processing)). A code no source declares any more is deprecated, never deleted, and its grants stay; declaring that code again in code clears `IsDeprecated` and so **reactivates every old grant** of it at once. Remove the grants (or pick a new code) before bringing a withdrawn code back. Other modules declare theirs the same way without referencing this module: the Sample module's `sample.leave_request.view`, `.create` and `.approve` ([Sample module](sample.md#permissions)) the Notifications module's `notifications.delivery.view` and `notifications.delivery.retry` ([Notifications module](notifications.md#permissions)) and the Audit module's `audit.trails.view` ([Audit module](audit.md#endpoints)).

A definition carries a flag, `AdminDefault` (`PermissionDefinition`, default `false`), that says whether the `Admin` role gets the permission by default. The rule is the seeder's: in the run that **inserts** a code whose definition is flagged, `Admin` receives it (added to what `Admin` already holds); a later run never adds it again, so a default an administrator removed stays removed. A code that is only re-declared after it was deprecated is not inserted again, so it is not given to `Admin` again either (its old grants come back with it, as above). A newly created `Admin` role (the first start) gets every flagged code. The seeder does not clear the permission cache: a user whose permission set is cached sees a grant made by a seeding run within 30 seconds (ADR 0016; the host seeds before it serves requests). Flagging is how a module gives `Admin` a default without this module naming the module's permissions. Two consequences to keep in mind when a module flags a code. **Review the flag like a role change:** it gives every `Admin` account a new power, and `Admin` holders may include people who never asked for it. **The flag has no effect on an install that already has the code:** only the run that first inserts a code grants it, so flagging an existing code later changes nothing there (add the grant through the role administration instead). A third effect shows up when a release adds a flagged code to `Admin`: the no-escalation rule means an actor can then assign `Admin` only if they hold the new code too (see [User administration](#user-administration)); the Notifications module's `notifications.delivery.view` and `.retry` did exactly this.

| Code | Allows |
|---|---|
| `auth.user.view` | List users and read their details. |
| `auth.user.create` | Create a user account on behalf of someone. |
| `auth.user.lock` | Suspend and reinstate user accounts. |
| `auth.user.reset_password` | Send a password reset to a user. |
| `auth.user.revoke_sessions` | End the sessions of a user. |
| `auth.user.reset_mfa` | Turn off a user's two-step verification so they can set it up again. |
| `auth.user.assign_roles` | Add and remove the roles of a user. |
| `auth.role.view` | List roles and read their permissions. |
| `auth.role.manage` | Create, change and delete roles and set their permissions. |
| `auth.permission.view` | List the permissions that modules declare. |
| `auth.audit.view` | Read the authentication and administration audit log. |

The Auth defaults of `Admin` are the nine codes flagged `AdminDefault` in `AuthPermissionSource`: the eight it always had and `auth.user.reset_mfa` (Plan 4, D17: "the user lost the device" is a help-desk task `Admin` already does for passwords, `auth.user.reset_password`). `Auth_admin_defaults_are_unchanged` pins them by name and `Admin_role_gets_reset_mfa_by_default` pins the new one on a fresh database. Review the flag like a role change: every `Admin` account gains the power to remove another user's second factor (not a SuperAdmin's, see [User administration](#user-administration)). Like every flagged code it is granted in the run that first inserts it, which on an install that already runs is the **first start after the upgrade**: the seeder inserts `auth.user.reset_mfa` and adds it to the existing `Admin` role (`AuthSeeder.GrantAdminDefaults`, `InsertedAdminDefaults`), so every existing `Admin` account gains the power with no administrator action; a freshly seeded database has it from the start. An install that does not want this removes the code from `Admin` through `PUT /api/v1/admin/auth/roles/{id}/permissions`; it then stays removed, because later runs never add a default again (the rule above).

The seeded system roles hold: `SuperAdmin` every permission that is not deprecated, kept equal to that set on each seeding run; `Admin` the defaults `auth.user.view`, `auth.user.create`, `auth.user.lock`, `auth.user.reset_password`, `auth.user.revoke_sessions`, `auth.user.reset_mfa`, `auth.role.view`, `auth.permission.view` and `auth.audit.view` and, from the Notifications module, `notifications.delivery.view` and `notifications.delivery.retry`, and, from the Audit module, `audit.trails.view`: every permission flagged `AdminDefault`, given when the role is first created and, for a code declared later, only in the run that first inserts it (later changes by administrators are kept); `User` nothing. `Admin` therefore manages accounts but cannot assign roles (`auth.user.assign_roles`), so it can create accounts only with the default `User` role; and the user administration keeps every SuperAdmin account, and the SuperAdmin role itself, out of reach of anyone who is not an active SuperAdmin (see [User administration](#user-administration)). The role administration adds three rules (see [Role, permission and audit log administration](#role-permission-and-audit-log-administration)): `SuperAdmin`'s set cannot be edited, the set of `Admin`, `User` or any custom role can be, and an administrator can newly grant only a permission they hold themselves. The same no-escalation rule (`PermissionGrantRules`) applies when roles are given to users: assigning a role a user does not hold yet, or creating an account with `roleIds`, needs the actor to hold every permission that is not deprecated among those the role grants (403 `auth.permission_grant_not_allowed`), so `auth.user.assign_roles` hands out at most what its holder has (see [User administration](#user-administration)). Upgrade effect: because `Admin` now also holds `notifications.delivery.view` and `notifications.delivery.retry`, an actor who has `auth.user.assign_roles` but not those two codes can no longer assign the `Admin` role (403 `auth.permission_grant_not_allowed`) until they are granted ([Notifications: Permissions](notifications.md#permissions)). The same holds for `auth.user.reset_mfa` (Plan 4, D17), on **every** install, because the first start after the upgrade grants it to `Admin` (unless an administrator removed it from `Admin` since): an actor needs `auth.user.reset_mfa` as well to assign `Admin`. That is the no-escalation rule working as designed: the actor could not otherwise hand out a power they lack. It cannot lock anyone out of administration, but an actor who held `auth.user.assign_roles` and the earlier `Admin` codes without `auth.user.reset_mfa` gets 403 `auth.permission_grant_not_allowed` on that assignment after the upgrade until the code is granted to them (the `Admin` role holders, and every SuperAdmin, already have it). An install that removes the code from `Admin` also removes the requirement.

`UserSession` (`Domain/Sessions/`) is one sign-in on one device, and also the refresh-token family (decision D2: there is no `FamilyId`). Its id is the `sid` claim of the access tokens. It owns its `RefreshToken` chain; a token stores only the SHA-256 hash (`TokenHash`), never the token.

- **Start:** `UserSession.Start(userId, authMethods, deviceName, userAgent, ipAddress, securityStamp, firstTokenHash, slidingLifetime, absoluteLifetime, now)` creates the session and its first token. `SecurityStamp` is a **snapshot** of the user's stamp at sign-in; `ExpiresAt` is absolute (`now + absoluteLifetime`) and sliding refresh never moves it. Tokens expire at `min(now + slidingLifetime, session.ExpiresAt)`, so no token outlives the session. `IsActive(now)` is true while the session is not revoked and `now < ExpiresAt`. The device name, user agent and address are client-supplied, so `Start` cuts them to their columns (`UserSession.MaxDeviceNameLength` 200, `MaxUserAgentLength` 512, `MaxIpAddressLength` 45) instead of letting a long header fail the sign-in (the same `UserSession.Cut` cuts the copies of the device name and user agent that the MFA challenge and the trusted device keep). `Start` also sets `AuthenticatedAt` to `now`: when the user last proved their identity in the session, the `auth_time` of its access tokens once Plan 4 reads it. It is stored in `auth.UserSessions.AuthenticatedAt` (`datetime2(3)`, not null); a session that existed before migration `AddMultiFactorAuthentication` has its `CreatedAt` there (see [Data](#data)).
- **Step-up:** `StepUp(authMethods, now)` sets `AuthMethods` to what the step-up proved (it replaces the sign-in's methods, because `amr` describes the authentication at `AuthenticatedAt`) and `AuthenticatedAt` to `now`; a blank value is an `ArgumentException` and a session that is not active (revoked, or at or past `ExpiresAt`) an `InvalidOperationException`, so a dead session never gets a fresh proof. The caller has verified the factor; nothing calls this yet.
- **New device:** `NoteNewDevice()` raises `NewDeviceSignedInDomainEvent(UserId, SessionId, IpAddress)` and changes nothing; `SessionStarter` decides that the device is new ([New device](#new-device)).
- **Rotate:** `Rotate(presentedTokenHash, newTokenHash, currentSecurityStamp, slidingLifetime, now)` is checked in this order. The caller saves the aggregate on every outcome, because some failures revoke the session.

  | Presented token | Result | Effect on the session |
  |---|---|---|
  | Hash matches no token, or the session is already revoked | `auth.invalid_refresh_token` | None. |
  | Current security stamp differs from the snapshot | `auth.invalid_refresh_token` | Revoked with `PasswordChanged`. |
  | Token already used or revoked | `auth.refresh_token_reused` | Revoked with `TokenReuse` (every token revoked), `RefreshTokenReuseDetectedDomainEvent` raised. |
  | Token or session expired | `auth.refresh_token_expired` | None. |
  | Valid | The new `RefreshToken` | Old token gets `UsedAt` and `ReplacedByTokenId`, `LastSeenAt` moves to `now`. |

  Hashes are compared with `CryptographicOperations.FixedTimeEquals` against every token of the session (no early exit), so timing does not tell which token matched. An unknown token, a token of a revoked session and a stamp mismatch all give `auth.invalid_refresh_token`.
- **ValidateRefresh:** `ValidateRefresh(presentedTokenHash, currentSecurityStamp, now)` runs the checks of `Rotate` in the same order with the same effects on failure, but does not exchange the token; on success it returns the presented token and changes nothing. The refresh handler calls it before claiming the token in the database, then `Rotate`s the same instance (see [Refresh and logout](#refresh-and-logout)). An expired token changes nothing, so presenting it again is still "expired", never reuse.
- **ReportTokenReuse:** `ReportTokenReuse(now)` revokes with `TokenReuse` and raises `RefreshTokenReuseDetectedDomainEvent`, for reuse found outside the aggregate (a database claim lost to another refresh that used the token); `Rotate` and `ValidateRefresh` use it too. A session that is already revoked keeps its reason and raises nothing.
- **Revoke:** `Revoke(reason, now)` ends the session and revokes every token that is not yet revoked. It is idempotent: a second call keeps the first time and reason.
- **AdoptSecurityStamp:** `AdoptSecurityStamp(securityStamp)` replaces the session's stamp snapshot with the user's new stamp, so the session from which the password (or the two-step verification, through `MfaChangeEffects`) was changed keeps refreshing while every other session (still holding the old stamp) is refused. A revoked session is left as it is; a blank stamp is a programming error.

`SessionRevokedReason` is persisted by its numeric value (`Logout` 0, `LogoutAll` 1, `PasswordChanged` 2, `AdminRevoked` 3, `TokenReuse` 4, `Expired` 5, `MfaChanged` 6: the user changed their two-step verification in another session), so a new reason is appended and existing values are never renumbered.

```mermaid
stateDiagram-v2
    [*] --> Active: start
    Active --> Active: rotate
    Active --> Revoked: logout, logout all, password changed, admin revoked, token reuse, MFA changed
    Active --> Expired: absolute expiry reached
    Revoked --> [*]
    Expired --> [*]
```

`VerificationCode` (`Domain/Verification/`) is a single-use code behind an emailed link. `VerificationPurpose` (`EmailVerify = 1`, `PasswordReset = 2`) is persisted by its numeric value, so a new purpose is appended and existing values are never renumbered. Only the SHA-256 hash of the token is stored (`TokenHash`); the repository finds a code by that unique hash, so the domain compares no hashes. The token itself travels only inside the issued event, as `ProtectedToken`: the application encrypts it with Data Protection (ADR 0017) and the event handler decrypts it to build the link. It is never a property of the aggregate.

- **Issue:** `VerificationCode.Issue(userId, purpose, trigger, target, tokenHash, protectedToken, lifetime, createdIp, now)` sets `ExpiresAt = now + lifetime` (a non-positive lifetime is a programming error) and raises `VerificationCodeIssuedDomainEvent`, which carries the `VerificationTrigger` (`SelfService` 0, `CreatedByAdmin` 1, `ForcedByAdmin` 2: who caused the code, kept only in the event). An administrator trigger on anything but a `PasswordReset` code is a programming error (`ArgumentException`). `Target` is the normalized email address. `createdIp` is cut to `VerificationCode.MaxCreatedIpLength` (45).
- **Consume:** `Consume(expected, now)` succeeds once. It fails with `auth.invalid_token` when the purpose differs, or the code is consumed, invalidated or expired. A code is valid up to, not including, `ExpiresAt`. Every cause gives the same error so the answer does not tell which one applied. `CanConsume(expected, now)` answers the same question without changing the code; the handlers check with it, claim the code in the database (`IVerificationCodeRepository.TryConsumeAsync`, see [Data](#data)) and only then `Consume` the instance they hold.
- **Invalidate:** `Invalidate(now)` makes a pending code unusable (a newer code replaces it, or the account state makes it useless). It is idempotent and leaves a consumed code unchanged. `IsPending(now)` is true while the code is neither consumed, invalidated nor expired.

```mermaid
stateDiagram-v2
    [*] --> Pending: issue
    Pending --> Consumed: consume
    Pending --> Invalidated: invalidate
    Pending --> Expired: ExpiresAt reached
    Consumed --> [*]
    Invalidated --> [*]
    Expired --> [*]
```

`AuthAuditLog` (`Domain/Audit/`) is one line of the append-only audit log. It is a plain entity with a `bigint` identity key, not an aggregate, and raises no domain events. `AuthAuditLog.Create(eventType, succeeded, now, userId, failureReason, attemptedIdentifier, sessionId, details)` leaves the client fields empty; the audit writer calls `SetClientInfo(ipAddress, userAgent, traceId)` from the request, which cuts the values to their columns (45, 512 and 64 characters). `AttemptedIdentifier` is cut to 256 characters. `Details` is JSON text that the domain neither validates nor bounds. `MaskIdentifier` makes an identifier safe to log: `alice@example.com` becomes `a****@example.com`, a value without `@` keeps its first character (`a****`), and null or blank gives null.

### Two-step verification domain

Plan 4 adds the two-step verification domain (`Domain/Mfa/`, `Domain/TrustedDevices/`, and members of `User` and `UserSession`). The domain and its persistence (tables, repositories and their atomic claims in [Data](#data), the secret protector in [Security services](#security-services), `Auth:Mfa` in [Configuration](#configuration)) are used by the factor verifier and step-up ([Step-up](#step-up)), by enrollment ([Enrollment](#enrollment)), by the sign-in challenge ([Challenge and verify](#challenge-and-verify)), by trusted devices ([Trusted devices](#trusted-devices)) and by the administrator's reset ([Administration](#administration)). The decisions are listed under [The decisions that shape behaviour](#the-decisions-that-shape-behaviour) and in ADRs 0022 to 0025. Every type is `internal`; the numeric values of the enums are persisted or serialized, so a new value is appended and existing values are never renumbered.

| Type | What it is |
|---|---|
| `UserMfaMethod` (aggregate) | One authenticator app of a user: `Type` (`MfaMethodType.Totp` = 1), `Label` (at most `MaxLabelLength` = 100), `SecretEncrypted` (the output of the Auth secret protector, at most `MaxSecretEncryptedLength` = 512; never the secret), `CreatedAt`, `ConfirmedAt`, `LastUsedAt`, `LastUsedTimeStep` and `IsConfirmed` |
| `RecoveryCode` (entity) | One single-use code of a user: `CodeHash` (SHA-256 of the normalized code, 32 bytes, validated), `CreatedAt`, `UsedAt`. Regenerating replaces the whole set, so there is no batch id |
| `MfaChallenge` (aggregate) | The state between a correct password and a correct second factor: `TokenHash` (32 bytes), `SecurityStamp` (snapshot), `DeviceName` (cut to `UserSession.MaxDeviceNameLength`), `CreatedAt`, `ExpiresAt`, `ConsumedAt`, `FailedAttempts` |
| `TrustedDevice` (aggregate) | A device remembered after a second factor: `TokenHash` (32 bytes), `DeviceName`, `UserAgent` (cut to 512), `SecurityStamp` (snapshot), `CreatedAt`, `ExpiresAt`, `LastUsedAt`, `RevokedAt` |
| `MfaChange` | What changed, carried by `MfaChangedDomainEvent`: `Enabled` 0, `Disabled` 1, `RecoveryCodesRegenerated` 2, `ResetByAdmin` 3, `RecoveryCodeUsed` 4 |

- **`UserMfaMethod`:** `StartTotp(userId, label, secretEncrypted, now)` creates a **pending** method. `RestartSetup(label, secretEncrypted, now)` replaces the secret of a pending method (a user who lost the QR code) and restarts `CreatedAt`; on a confirmed method it throws `InvalidOperationException` (replacing an authenticator means removing it first). `Confirm(timeStep, now)` turns a pending method into a confirmed one, sets `ConfirmedAt` and `LastUsedAt` to `now` and `LastUsedTimeStep` to the verified step, so the same code cannot be used again at once; on a confirmed method it returns `auth.mfa_already_enabled` and changes nothing. A blank label or secret, or one longer than its column, is an `ArgumentException` (the application validator refuses a label first). The aggregate never compares time steps: the replay guard is one conditional update of `LastUsedTimeStep` in the repository (persistence task).
- **`MfaChallenge`:** `Issue(userId, tokenHash, securityStamp, deviceName, lifetime, now)` sets `ExpiresAt` to `now + lifetime`. `CanUse(currentSecurityStamp, now, maxAttempts)` is true only while the challenge is not consumed, `now < ExpiresAt` (so it ends exactly at `ExpiresAt`), `FailedAttempts < maxAttempts` and the user's current stamp equals the snapshot (ordinal comparison), so a password change, an MFA change or a suspension between the two steps ends the challenge. It changes nothing: the wrong-code counter and the consumption are conditional updates in the repository, in the same rule. A token hash that is not 32 bytes, a blank stamp and a lifetime that is not positive are programming errors (`ArgumentException`, `ArgumentOutOfRangeException`).
- **`TrustedDevice`:** `Trust(userId, tokenHash, deviceName, userAgent, securityStamp, lifetime, now)`; `IsUsable(currentSecurityStamp, now)` is true while the device is not revoked, `now < ExpiresAt` and the stamp equals the snapshot (ordinal), so every event that rotates the stamp forgets every device. `MarkUsed(now)` sets `LastUsedAt` and never extends the absolute expiry. `Revoke(now)` is idempotent and keeps the first time.
- **`User`:** `ChangeMfa(change, now)` rotates `SecurityStamp` (ending the other sessions, pending challenges and trusted devices at their next check) and raises `MfaChangedDomainEvent(UserId, Change)`; `RecoveryCodeUsed` is an `ArgumentException` there, and a value that is not defined an `ArgumentOutOfRangeException`. `NoteRecoveryCodeUsed()` raises the same event with `RecoveryCodeUsed` and changes nothing, in particular not the stamp (the code is single-use already, and a rotation would end the session just created). Neither event carries a code, secret or address.

`UserMfaMethod` has two states; the secret is replaced only while it is pending.

```mermaid
stateDiagram-v2
    [*] --> Pending: StartTotp
    Pending --> Pending: RestartSetup
    Pending --> Confirmed: Confirm(timeStep)
    Confirmed --> Confirmed: Confirm refused (auth.mfa_already_enabled)
    Confirmed --> [*]: removed
    Pending --> [*]: removed
```

`MfaChallenge` has no setter for its end states; the repository's conditional updates and the clock decide, and `CanUse` reads them.

```mermaid
stateDiagram-v2
    [*] --> Issued: Issue
    Issued --> Issued: wrong code (FailedAttempts + 1)
    Issued --> Consumed: right code (ConsumedAt)
    Issued --> Expired: now reaches ExpiresAt
    Issued --> Exhausted: FailedAttempts reaches the maximum
    Issued --> StampChanged: user's SecurityStamp changes
    Consumed --> [*]
    Expired --> [*]
    Exhausted --> [*]
    StampChanged --> [*]
```

### Audit events

The event types are the constants of `AuthAuditEvents` (stored as text, never renamed):

- Registration and confirmation: `auth.registered`, `auth.register_duplicate`, `auth.email_confirmed`, `auth.email_confirm_failed`, `auth.confirmation_resent`.
- Sign-in and tokens: `auth.login_succeeded` (with `{"trustedDeviceId":"..."}` in `Details` when a trusted device skipped the challenge), `auth.login_failed`, `auth.locked_out`, `auth.token_refreshed`, `auth.refresh_failed`, `auth.token_reuse_detected`.
- Sessions: `auth.logout`, `auth.logout_all`, `auth.session_revoked`.
- Passwords and profile: `auth.password_forgot_requested`, `auth.password_reset`, `auth.password_reset_failed`, `auth.password_changed`, `auth.password_change_failed`, `auth.profile_updated`.
- Step-up: `auth.step_up_succeeded` and `auth.step_up_failed` (failure reason the error code, or `locked`), each with the session id and the factor tried in `Details` (`{"factor":"password"}`, `"totp"` or `"recovery_code"`; never the code); a wrong proof that locks the account also writes `auth.locked_out`.
- Sign-in challenge: `auth.mfa_challenge_issued` (a correct password of an account with two-step verification; the user id and the masked email, like `auth.login_failed`), `auth.mfa_verified` (with the new session id and `{"factor":"totp"}` or `"recovery_code"` in `Details`, always followed by `auth.login_succeeded` with the same session id) and `auth.mfa_failed` (failure reason `auth.invalid_mfa_code` or `auth.invalid_mfa_challenge`, the challenge's user id when the challenge is known, and the factor tried in `Details`); a wrong code that locks the account also writes `auth.locked_out`. Never a code, a recovery code or the challenge token.
- Two-step verification: `auth.mfa_setup_started` (`Details` `{"methodId":"..."}`), `auth.mfa_enabled`, `auth.mfa_disabled` and `auth.recovery_codes_regenerated` (each `Details` `{"revokedSessionCount":n}`), each with the session id. Cancelling a pending setup writes no row, and a request refused for a missing step-up writes none either. Ids and counts only: never the secret, its protected form, the `otpauth://` URI, a code or a recovery code. A refused setup or confirm writes no row.
- Trusted devices: `auth.trusted_device_added` (written by the verify that remembered the device, with its session id) and `auth.trusted_device_revoked` (with the session id of the caller; a second revocation writes no row, except that two revocations racing each other can both write one), each with `{"trustedDeviceId":"..."}` in `Details`. Never the device token: an unusable token presented at login leaves no trace beyond the usual `auth.mfa_challenge_issued`.
- Administration: `auth.admin_user_created`, `auth.admin_user_locked`, `auth.admin_user_unlocked`, `auth.admin_password_reset_forced`, `auth.admin_sessions_revoked`, `auth.admin_roles_assigned`, `auth.admin_mfa_reset` (target in `UserId`, `{"actorId":"..."}` in `Details`; nothing about the removed method, never a secret or a code; written when a method (even a pending one) was removed, not for a user without one).
- Roles: `auth.role_created`, `auth.role_updated`, `auth.role_deleted`, `auth.role_permissions_changed`. A role is not a user, so these have no `UserId`; the actor and the role are in `Details` (see [Role, permission and audit log administration](#role-permission-and-audit-log-administration)).

`AuthAuditEvents.All` lists every constant above (by reflection), which is the allow-list of the audit log's `eventType` filter.

### Audited entities

Four entities carry `[Audited]`, so every save that changes one writes its field changes to the [Audit module](audit.md) (`audit.AuditTrails`, read through `GET /api/v1/admin/audit/trails`; [ADR 0030](../adr/0030-audit-trail-through-the-owning-modules-outbox.md)): `User`, `Role`, `RolePermission` and `UserRole`. (`PasswordHistoryEntry`, which holds hashes, is not audited at all.) The change set is one more row in `auth.OutboxMessages`, added by `AuditTrailInterceptor` in the same save as the change, so it is recorded exactly when the change is. The trail records **field changes**, with old and new values; `auth.AuthAuditLogs` ([Audit events](#audit-events)) stays the **security log** (sign-ins, lockouts, token reuse and administrator actions, with address and user agent). They are two logs that answer different questions and neither replaces the other: "who tried to sign in from where" is in the security log, "what did this role look like before the change" in the trail. Auth does not depend on the Audit module and the Audit module does not reference Auth.

| Entity | Audited | `[AuditIgnore]` |
|---|---|---|
| `User` | `Email`, `EmailConfirmed`, `Status`, `DisplayName`, `Locale`, `TimeZone`, `PasswordChangedAt`, `LockoutEnd`; soft delete and restore | `NormalizedEmail` (derived from `Email`), `LastLoginAt` and `AccessFailedCount` (high frequency; the security log has the sign-ins), `PasswordHash` and `SecurityStamp` (secrets) |
| `Role` | `Name`, `Description`, `IsSystem`; soft delete and restore | `NormalizedName` (derived) |
| `RolePermission` | `RoleId`, `PermissionId` (composite key; created and hard-deleted) | none |
| `UserRole` | `UserId`, `RoleId`, `AssignedBy`, `AssignedAt` (composite key; created and hard-deleted) | none |

`RowVersion` and the audit and soft-delete stamps are skipped by rule, not by attribute. `PasswordChangedAt` is audited: a password change shows as a change of that field without recording what it changed to, and an administrator's suspension as `{ "Status": { "old": "Active", "new": "Suspended" } }`. Nothing in Auth needs `[AuditMask]` today.

- **The seeder writes trails with no user.** The first run of the seeder saves with no signed-in user, so the seeded roles (`Role` `Created`), their grants (`RolePermission` `Created`) and, when the first administrator is created, that `User` and its `UserRole` are trail rows whose `UserId` and `SessionId` are null. That is correct: the seeder is not a person. A later run that changes nothing audited writes nothing.
- **A sign-in writes no trail.** It only changes `LastLoginAt`, which is ignored, and a save that changes only ignored properties writes no change set.
- **Raw statements are never audited.** The atomic failed-sign-in count, the statements that consume a token or a code (a refresh token, a verification code, a recovery code, a sign-in challenge) and every cleanup delete bypass the change tracker, so the trail does not see them; the security log covers failed sign-ins, lockouts, token use and reuse.
- **Outbox rows.** Every save that changes an audited entity adds an audit row to `auth.OutboxMessages` next to the module's own events. The integration tests that count or take Auth's own outbox rows filter the audit rows out (`AuditOutboxFilter`); `AuditTrailEndToEndTests` ([Audit](audit.md#testing)) follows a role's permission change, a suspension, a sign-in and the seeder's first run into the trail.

### Integration events

The public surface of the module is the `TemplateName.Modules.Auth.Contracts` project (`src/Modules/Auth/TemplateName.Modules.Auth.Contracts/`), the only Auth project another module may reference (ADR 0001). It references `TemplateName.SharedKernel` and nothing else, and holds only public sealed records, enums and interfaces (`ContractsTests`). Every integration event is a `public sealed record {Noun}{PastTenseVerb}IntegrationEvent` in `TemplateName.Modules.Auth.Contracts.IntegrationEvents` that implements `IIntegrationEvent`: `Id` is the Auth outbox message id of the domain event behind it (the same on every republish, so a consumer's inbox recognizes a retry) and `OccurredAt` is when that event happened (UTC). Integration events are published in process and never stored, so they carry no version; a breaking change is a new record type (ADR 0018).

| Integration event | Carries | Meaning |
|---|---|---|
| `EmailVerificationRequestedIntegrationEvent` | `UserId`, `Email`, `ProtectedActionUrl`, `ExpiresAt` | A confirmation link was issued. `Email` is the address the link was issued for (where it must go); `ProtectedActionUrl` is the full link encrypted with `ISecretProtector`: single-use and secret, stored only as ciphertext, decrypted only in memory (the consumer's URL check and the rendering of the email), never logged |
| `PasswordResetRequestedIntegrationEvent` | `UserId`, `Email`, `ProtectedActionUrl`, `ExpiresAt`, `Reason` | A reset link was issued, with the same address and ciphertext rules; `Reason` is `PasswordResetReason.SelfService` (the user asked), `CreatedByAdmin` (set the first password of an administrator-created account) or `ForcedByAdmin` |
| `RegistrationAttemptedIntegrationEvent` | `UserId` | Someone registered an address that already has an account; `UserId` is its owner |
| `PasswordChangedIntegrationEvent` | `UserId` | A password was changed or reset |
| `UserLockedOutIntegrationEvent` | `UserId`, `LockoutEnd` | Failed sign-ins locked the account until `LockoutEnd` |
| `RefreshTokenReuseDetectedIntegrationEvent` | `UserId`, `SessionId` | A used or revoked refresh token was presented again and the session was revoked |
| `MfaChangedIntegrationEvent` | `UserId`, `Change` | A user's two-step verification changed or a recovery code was used. `Change` is an `MfaChangeKind`, serialized by its number: `Enabled = 0`, `Disabled = 1`, `RecoveryCodesRegenerated = 2`, `ResetByAdmin = 3`, `RecoveryCodeUsed = 4`; a new kind is appended and none is renumbered. It carries no authenticator secret, recovery code, token or device name |
| `NewDeviceSignedInIntegrationEvent` | `UserId`, `SessionId`, `IpAddress` | The user signed in from a device none of their earlier sessions used ([New device](#new-device)). `IpAddress` is the address the server observed, null when it observed none. ### Publishing

Each published event has one outbox handler in `Application/IntegrationEvents/` (`internal sealed`, an `IDomainEventHandler<T>`) that builds the integration event and hands it to `IIntegrationEventPublisher` (ADR 0018). The event's `Id` and `OccurredAt` are `IOutboxMessageContext.MessageId` and `OccurredAt`, those of the outbox message the handler runs for, so a retry republishes the same id and a consumer's inbox recognizes it. When a consumer fails, the publisher rethrows, the handler fails and the outbox retries it on its backoff schedule; consumers that already succeeded skip the repeat through their inbox, so a retried publish never sends an email twice. The Notifications consumer only writes rows; the email is sent later by its delivery worker, so an SMTP outage never fails a publishing handler: it delays the email, which the worker retries on its own schedule.

- `PublishRegistrationAttemptedDomainEventHandler`, `PublishPasswordChangedDomainEventHandler`, `PublishUserLockedOutDomainEventHandler`, `PublishRefreshTokenReuseDetectedDomainEventHandler`, `PublishMfaChangedDomainEventHandler` and `PublishNewDeviceSignedInDomainEventHandler` map one to one: the user id, plus `LockoutEnd` for a lockout, `SessionId` for token reuse, `Change` (an `MfaChange` mapped by name to `MfaChangeKind`; an unmapped value throws `InvalidOperationException`, so a new change cannot be dropped silently) for an MFA change, and `SessionId` and `IpAddress` for a new device. They log nothing.
- `PublishVerificationCodeIssuedDomainEventHandler` loads the code by id (`IVerificationCodeRepository.GetByIdAsync`) and then its user. It decrypts the token, builds the link with `Auth:Links` (Auth keeps owning link formats) and encrypts the whole link again with `ISecretProtector` as `ProtectedActionUrl` (ADR 0020): `EmailVerificationRequestedIntegrationEvent` for `EmailVerify`, `PasswordResetRequestedIntegrationEvent` for `PasswordReset` with the `Reason` mapped from the event's trigger (`SelfService` for forgot-password, `CreatedByAdmin` for an administrator-created account, `ForcedByAdmin` for a forced reset). `Email` is the user's current `Email` (the address the code was issued for, see below) and `ExpiresAt` the code's. The plaintext token and link exist only inside that method: they are never logged, stored or put in an exception message.
- **Stale codes are not published.** When the code is unknown or no longer pending at dispatch time (a newer code replaced it, it was used, or it expired), its user no longer exists (or is soft-deleted), or the user's `NormalizedEmail` is no longer the code's `Target`, the handler publishes nothing and logs one Information line with the code id only. A link replaced before the outbox ran, or before a retry, is therefore never published.

### New device

A sign-in is from a **new device** when it is successful (password only, or after an MFA challenge), is **not** through a trusted device, and its `(DeviceName, UserAgent)` pair matches none of the user's stored sessions, in any state (active, expired or revoked), the account's first sign-in ever excluded (plan decision D15). `SessionStarter.StartAsync` asks `ISessionRepository.GetDeviceFamiliarityAsync(userId, deviceName, userAgent, ct)` **before** it adds the new session, with the values as stored (cut to their columns), and calls `UserSession.NoteNewDevice()` for `DeviceFamiliarity.New`. The answer is one query over the user's sessions: none at all is `NoStoredSession`; one with the same `DeviceName` and `UserAgent` is `Known`; otherwise `New`. No stored session is the account's first sign-in only when the user has never signed in before: `SessionStarter` reads `User.LastLoginAt` before it records this sign-in, and a user who signed in before but has no session left (an account dormant longer than the session lifetime plus `Auth:Retention:Sessions`, whose sessions [Cleanup](#cleanup) deleted) is on a new device too, so a credential-stuffed sign-in to a dormant account still sends the notice (`SessionStarterTests.A_user_who_signed_in_before_but_has_no_stored_session_left_is_on_a_new_device`, `IntegrationEventPublishingTests.A_dormant_account_whose_sessions_were_cleaned_up_still_publishes_new_device`). The comparison is ordinal (the pair is compared with the `Latin1_General_100_BIN2` collation, so `Phone` and `phone` are two devices) and a missing user agent equals only a missing user agent. A sign-in through a trusted device is never new and does not even ask. A browser update changes the user agent and so sends one notice, which is acceptable for a security notice. The event, and the email Notifications builds from it, carry no client-supplied text (D15): time, time zone and the server-observed address only, because a device name typed by an attacker would otherwise land in the owner's inbox.

### Contracts

`IUserContactDirectory.FindAsync(userId, cancellationToken)` returns a `UserContact(UserId, Email, DisplayName, Locale, TimeZone)` or null, so a module that notifies users never reads `auth.Users`. Auth implements it with `UserContactDirectory` (`Infrastructure/Contracts/`, scoped, registered by `AddAuthModule`): one Dapper query on `auth.Users` that reads only those columns (no hash, stamp or status) and repeats the soft-delete filter in its SQL (`IsDeleted = 0`, ADR 0006), so a deleted or unknown user is null. A suspended user is returned, because security notices still reach them. `Locale` and `TimeZone` are passed on as stored: the columns are not nullable, so neither is null, but a locale can be an empty string (registration does not require one) and the caller applies its own fallback (an unsupported or empty locale means its default language, an unknown or empty time zone means `UTC`). The caller takes a snapshot of what it needs; the directory is always current. `UserContactDirectoryTests` covers the contact, a soft-deleted user (the row exists, the filter hides it), an unknown user, a suspended user and an empty locale.

**Emails.** Auth has no email code of its own: no sender, no message builder and no SMTP settings (Plan 2's `IEmailSender`, `AuthEmails`, the two `Send*EmailDomainEventHandler`s and `Auth:Email` moved to, or were replaced by, the Notifications module in Plan 3). The address, display name and language an email uses come from `IUserContactDirectory` and, for a link, from the event's `Email` (the address the code was issued for). A link replaced or used before the outbox ran is never published, so it is never emailed ([Publishing](#publishing)).

## Registration

<!-- The registration, confirmation and resend flows, and what they guarantee against account enumeration. -->

The handlers live in `Application/Registration/{Register,ConfirmEmail,ResendConfirmation}/`, each with its command and validator. The validator runs in the validation decorator, **before** the handler, so nothing below happens for an invalid request.

**Validation** (`RegisterCommandValidator`; each rule stops at its first failure):

- `email`: required, at most 256 characters (`User.MaxEmailLength`), an email address. Surrounding white space and case do not matter for the account (`User.NormalizeEmail`: `Alice@Example.com ` and `alice@example.com` are one account, enforced by the unique index on `NormalizedEmail`).
- `password`: not empty and not only white space, `Auth:Password:MinLength` to `MaxLength` characters (12 to 128 by default, counted in UTF-16 characters as everywhere in the module; any Unicode is accepted, no composition rules), and not the email itself (ignoring case and surrounding white space). The length is checked before any breach lookup or hashing, so a 1 MB password is refused cheaply (the host also caps a request body at `Kestrel:Limits:MaxRequestBodySize`, 10 MB). The password is never trimmed.
- `displayName`: not blank, at most 200 characters; it is stored trimmed.
- `locale`: a predefined .NET culture name (`CultureInfo.GetCultureInfo(name, predefinedOnly: true)`) of at most 16 characters, stored in its canonical spelling (`ZH-hans` becomes `zh-Hans`). The endpoint fills it from the request's language when the body has none.
- Confirm: `token` not blank, at most 256 characters. Resend: `email` as for registration.

The custom messages (password equal to the email, unknown culture) are English; the built-in FluentValidation messages are translated (`ValidationMessageTranslations`).

**Register** (`RegisterCommandHandler`), in this order:

1. Breach check (`IBreachedPasswordChecker`, fail-open): a breached password is 400 `auth.password_breached`. The answer depends on the password only, never on the account.
2. Hash the password (`IPasswordHasher.Hash`) **before** looking the address up, so a known and a new address both pay the hashing cost.
3. Look the address up by `NormalizedEmail`.
4. **Known address:** `NoteRegistrationAttempt` (raises `RegistrationAttemptedDomainEvent`, changes nothing), audit `auth.register_duplicate` (not succeeded, the user id and the masked address), one save. The existing account is untouched: its password, name and locale stay as they are.
5. **New address:** `User.Register`, the `User` system role (looked up with `IRoleRepository.GetByNormalizedNameAsync`; if the seeder has not created it, the handler throws `InvalidOperationException` instead of creating a role-less user), an `EmailVerify` `VerificationCode` (token from `ISecureTokenService.Generate`, only its SHA-256 hash stored, the token protected with `ISecretProtector` into the issued event, lifetime `Auth:Verification:EmailLifetime`, the client address as `CreatedIp`), audit `auth.registered`, and **one** save that also writes the outbox rows of `UserRegisteredDomainEvent` and `VerificationCodeIssuedDomainEvent`. The save is `SaveChangesUnlessDuplicateAsync(UniqueIndexNames.UserEmail, ...)`: when the email index refuses the insert (a simultaneous registration of the address won), nothing of this request is saved and the handler looks the address up again and continues as in step 4.

**Confirm** (`ConfirmEmailCommandHandler`): hash the presented token, find the code by hash, check it (`CanConsume(EmailVerify, now)`), load the user, consume the code atomically in the database (`TryConsumeAsync`, with no cancellation token), `Consume` the loaded code, `ConfirmEmail(now)`, audit `auth.email_confirmed`, save (with no cancellation token: the claim has already committed). Of two simultaneous confirmations with one token exactly one gets 204 and the other the usual 400 `auth.invalid_token`, never a 409 or a 500 (`RegistrationTests.Concurrent_confirm_with_same_token_succeeds_once`). Any failure (unknown token, used, invalidated by a resend, expired, another purpose such as a reset token, or a user that no longer exists) is 400 `auth.invalid_token` and is audited as `auth.email_confirm_failed` with the failure reason and the code's user id when known, never the token; a refused token changes nothing, only the audit entry is saved.

**Resend** (`ResendConfirmationCommandHandler`): an unknown or already confirmed address does nothing; so does a code issued less than `Auth:Verification:ResendCooldown` ago (`GetLastIssuedAtAsync` against `TimeProvider`, review 2.11: the per-account cooldown is enforced here because the limiter cannot see the body). Otherwise every pending `EmailVerify` code is invalidated, a new one is issued as at registration, audit `auth.confirmation_resent`, one save.

**Enumeration guarantees.**

- Register and resend answer 202 with no body and the same headers for a known and an unknown address (`RegistrationTests.Register_response_is_identical_for_new_and_existing_email`); every 400 depends only on the request itself.
- The only difference a caller could see is the email, which only the owner of the address receives: a confirmation link for a new account, a "sign-up attempt" notice (no link) for an existing one.
- Registration hashes on both paths. Resend does no hashing; its known-address path costs a few more queries than the unknown one.
- Two registrations of the same new address at the same moment both pass the lookup; the unique index `IX_Users_NormalizedEmail` lets one insert win, and the others are answered exactly as for a known address (202, the attempt noted on the winning account, `auth.register_duplicate`), never a 500 (`RegistrationTests.Concurrent_registrations_of_one_new_address_create_one_account_and_never_a_500`). No duplicate account can exist.

**Secrets.** The token reaches the outbox only encrypted (ADR 0017); `auth.VerificationCodes` stores its hash; the commands and request bodies print only their type name, so a logged command never carries the password or the token.

## Login and current user

<!-- The login flow, its lockout and enumeration rules, and GET /me. -->

The handlers live in `Application/Authentication/Login/` (`LoginCommand`, `LoginCommandHandler`, `LoginCommandValidator`, `LoginResponse`) and `Application/Me/GetMe/` (`GetMeQuery`, `GetMeQueryHandler`, `MeResponse`); the settings, the answer `LoginResult` and the shared success path `SessionStarter` (with `StartedSession`) in `Application/Authentication/` (`RefreshTokenOptions`, `LockoutOptions`).

**Validation** (`LoginCommandValidator`, in the validation decorator, before the handler): `email` required, at most 256 characters, an email address; `password` not empty and at most `Auth:Password:MaxLength` characters (UTF-16 characters, not trimmed, not normalized; Ruling R14), so an over-long password (a 1 MB string included) is refused with 400 before any lookup or hashing. There is no minimum at login: a password an older, shorter minimum accepted must still work, and only the hash can tell whether it is right. `deviceName` at most 200 characters (`UserSession.MaxDeviceNameLength`); `trustedDeviceToken` at most 256 characters (a real one has 43; any other value is simply not found).

**Login** (`LoginCommandHandler`), in this order:

1. Normalize the email (`User.NormalizeEmail`) and load the user (`GetByNormalizedEmailAsync`; a soft-deleted user is not found).
2. **Always one verification.** A user with a hash: `IPasswordHasher.Verify`. An unknown email, or a user without a password (created by an administrator, Ruling R3): `SpendVerificationCost`, which costs the same, and the attempt counts as a wrong password.
3. **Wrong password or no such account:** for a user with a password, `IUserRepository.RecordFailedSignInAsync(userId, now, Auth:Lockout:MaxFailedAttempts, Auth:Lockout:Duration)` counts the failure in one atomic statement by the rules of `User.RecordFailedSignIn` (nothing changes while the account is already locked); when that failure locked the account, `User.NoteLockedOut(lockoutEnd)` raises `UserLockedOutDomainEvent` on the tracked user without changing it; audit `auth.login_failed` (failure reason `auth.invalid_credentials`, the user id when there is a user, the masked email), plus `auth.locked_out` (with `{"lockoutEnd":"..."}` in `Details`) when this failure locked the account; save (inserts only); 401 `auth.invalid_credentials`. An unknown email and an account without a password change no counter.
4. **Correct password, account locked** (`IsLockedOut(now)`): audit `auth.login_failed` with failure reason `locked`, save, 401 `auth.invalid_credentials`. The counters and `LockoutEnd` stay as they are: the lockout neither grows nor ends early. Decision D10: there is no distinct "locked" answer, because it would reveal that the email exists.
5. **Correct password, account cannot sign in** (`EnsureCanSignIn`): a suspended account is 403 `auth.account_inactive`, an unconfirmed email 403 `auth.email_not_verified` (suspension is checked first); audited as `auth.login_failed` with the code as the reason, saved. These answers come only after the right password, so they tell nothing to someone who does not know it.
6. **Correct password, account may sign in.** When the verifier answered `SuccessRehashNeeded`, the password is hashed again and stored with `User.UpgradePasswordHash`, which changes only the hash: not the security stamp, the history or `PasswordChangedAt`, and it raises no event (the password is the same). Then, and only then, the first read of anything two-step: `IMfaMethodRepository.HasConfirmedAsync(userId)`.
7. **No confirmed method: success, as in Plan 2.** `SessionStarter.StartAsync(user, "pwd", deviceName ?? "Unknown", viaTrustedDevice: false, now)`: `RecordSuccessfulSignIn(now)` (failures and lockout cleared, `LastLoginAt` set); a refresh token from `ISecureTokenService.Generate` (43 characters; only its SHA-256 hash is stored); `UserSession.Start(userId, "pwd", deviceName, userAgent, ipAddress, user.SecurityStamp, refreshHash, SlidingLifetime, AbsoluteLifetime, now)` with the user agent and address from `IClientContext`; the access token from `IAccessTokenIssuer.Issue(new AccessTokenRequest(userId, sessionId, securityStamp, "pwd", now, user.Locale))`. The handler adds the audit `auth.login_succeeded` with the session id; one save. The answer is `LoginResult` with `mfaRequired: false`, both tokens, their expiries (`refreshTokenExpiresAt` is the first token's, `now + SlidingLifetime`, never past the session's absolute expiry) and the session id, which is also the token's `sid`. `SessionStarter` saves and audits nothing itself; the verify of a challenge uses it too.
8. **A confirmed method: a challenge instead of tokens** ([Challenge and verify](#challenge-and-verify)). No session, and **no** `RecordSuccessfulSignIn`: the failure count and `LastLoginAt` stay as they are until a second factor is verified (plan decision D7). A token from `ISecureTokenService.Generate`, `MfaChallenge.Issue(userId, tokenHash, user.SecurityStamp, deviceName ?? "Unknown", Auth:Mfa:ChallengeLifetime, now)` (only the hash is stored), audit `auth.mfa_challenge_issued` (succeeded, the user id and the masked email), one save; the counter `auth.logins` with `mfa_required`. The answer is `LoginResult` with `mfaRequired: true`, `challengeToken` (shown only here), `challengeExpiresAt` and `methods` (`["totp","recovery_code"]`).

   **Unless a trusted device stands in** ([Trusted devices](#trusted-devices)): when `Auth:Mfa:TrustedDevicesEnabled` is on and the request has a `trustedDeviceToken` whose device belongs to this user and is usable, the device is marked used and the session starts as in step 7 (`amr` `pwd`, the failure count reset), audited as `auth.login_succeeded` with `{"trustedDeviceId":"..."}`. The token is hashed and looked up only here, after the password and every check above, so it is no way around them; any other token gets the challenge exactly as without one.

`LoginResult` (`Application/Authentication/`) has every member of both shapes; each nullable member is `[JsonIgnore(Condition = WhenWritingNull)]`, so the JSON of one shape carries none of the other's (`LoginTests.Login_succeeds_and_the_access_token_authenticates_get_me` and `MfaLoginTests.Mfa_login_returns_a_challenge_and_verify_returns_tokens` pin the exact member names). It is made by `LoginResult.Signed(LoginResponse)` or `LoginResult.Challenge(token, expiresAt)`. The OpenAPI document lists every member of its schema as required, as it does for `CursorPage.totalCount`; a client treats a missing member as null. Refresh still answers `LoginResponse`.

Every failure path saves, so the failure count survives the failure result (`LoginTests.Failed_login_counter_survives_the_failure_result`). The lockout ends exactly at `LockoutEnd`: one tick earlier the right password is still refused (`LoginTests.Lockout_ends_exactly_at_the_lockout_time`).

**Enumeration guarantees.**

- An unknown email, a wrong password, an account without a password and a locked account all answer 401 `auth.invalid_credentials` with the same headers and the same body (only `traceId` differs): `LoginTests.Unknown_email_and_wrong_password_return_identical_responses`, `User_without_password_hash_gets_the_same_response_as_unknown_email`.
- Each path does exactly one password verification, and each saves (an audit row at least), so the expensive work is the same. A known account's failure also runs the one-row counting statement before the save; that is a difference of one short round trip.
- **Concurrent attempts.** Wrong passwords that arrive together must each count, or parallel guessing would get far more than five tries per lockout. The failure is therefore counted by one `UPDATE auth.Users ... OUTPUT inserted.AccessFailedCount, inserted.LockoutEnd` (`UserRepository`, `WHERE Id = @id AND IsDeleted = 0` and the account not locked at `@now`): simultaneous failures queue on the row lock, and each sees the count the previous one left. The tracked user is not changed for a failure, so the save that follows only inserts (the audit rows and the lockout event's outbox row) and cannot conflict: every failed request keeps its `auth.login_failed` row, and exactly one request (the one that crossed the threshold) writes `auth.locked_out` and the event. With the default settings, ten wrong passwords at once leave the count at 5, `LockoutEnd` set, ten `auth.login_failed` rows and one `auth.locked_out` row; the other five found the account locked, which counts nothing (`LoginTests.Parallel_wrong_passwords_are_all_counted_and_lock_the_account`). The statement is a copy of the domain rule in SQL, so `AuthPersistenceTests.Atomic_failed_sign_in_count_matches_the_domain_rule` runs both over the same states (never failed, one failure, one below the threshold, at a lowered threshold, locked, locked until one tick from now, lock ended exactly now, lock ended long ago) and requires identical results; `User.RecordFailedSignIn` stays the specification. Only a **successful** login still changes the user through the change tracker (`LastLoginAt`, the reset, a rehash); two at once conflict on `RowVersion`, and the handler saves that path with `IUnitOfWork.TrySaveChangesAsync`, which answers false instead of throwing: the loser gets 401 `auth.invalid_credentials` (a 409 `concurrency.conflict` could only ever happen to an existing account) and simply signs in again. The challenge path saves the same way (it writes the user row only for a rehash).
- **Two-step verification changes none of this.** Nothing two-step is read or decided before the password is verified, the account is not locked and it may sign in (`LoginCommandHandlerTests.Mfa_lookup_happens_only_after_a_correct_password` proves `HasConfirmedAsync` is never called for an unknown email, a wrong password, an account without a password, a locked, an unconfirmed or a suspended account). So an unknown email, a wrong password for an MFA account and a locked MFA account with the right password answer the same 401 (`MfaLoginTests.Unknown_email_and_wrong_password_for_an_mfa_account_return_identical_responses`, through the same comparison of status, headers and body as Plan 2's tests, `ProblemResponseComparison`). A challenge is only ever answered to the right password, which tells the caller the password was right: inherent to any second step, and the same disclosure the 403s already make.
- The audit log is internal and does tell the cases apart (user id, failure reason), for administrators.

**Current user** (`GetMeQueryHandler`, `GET /api/v1/auth/me`): one Dapper round trip reads the user (`IsDeleted = 0` and `Status = Active`) and the names of its roles (`IsDeleted = 0`), because Dapper bypasses the EF Core soft-delete filters (ADR 0006; `MeTests.Get_me_returns_roles_and_permissions_and_hides_soft_deleted_roles`). The permissions come from `IPermissionReader`, the same cached set (`auth:perm:{userId}`) that every permission check uses (see [Permission checks](#permission-checks)), so the list shows exactly what the user may do. Roles and permissions are sorted ordinally. **Fail closed:** the access token stays valid until it expires (decision D9), but when its user no longer exists, is soft-deleted or is suspended, the handler fails and the endpoint answers the same body-less 401 a request without a valid token gets (`http.401`), not a 404.

**Caching.** Login, the challenge verify, refresh and `GET me` answer with `Cache-Control: no-store` and `Pragma: no-cache` (`.WithNoStore()`, an endpoint filter from Web.Common's `NoStoreEndpointExtensions`), refusals included, so no browser or intermediary keeps a token or the user's data (`LoginTests.Token_responses_and_me_are_marked_no_store`). The header is set per route, not globally. A request refused before the endpoint runs (the limiter's 429, the bearer check's 401) carries no token and does not get it.

**Secrets.** `LoginCommand`, `LoginRequest` and `LoginResponse` print only their type name (the response also its session id), and `LoginResult` its type name and `MfaRequired`, so a logged command or response never carries the password, a token or a challenge; no audit row, log line or metric tag holds the password, a token or an email address (the audit keeps the masked email only).

## Refresh and logout

<!-- Refresh-token rotation with reuse detection, logout and logout-all. -->

The handlers live in `Application/Authentication/Refresh/` (`RefreshTokenCommand`, `RefreshTokenCommandHandler`, `RefreshTokenCommandValidator`; the response is the login's `LoginResponse`), `Application/Authentication/Logout/` and `Application/Authentication/LogoutAll/`; the request body is `Endpoints/RefreshTokenRequest.cs`.

**Validation** (`RefreshTokenCommandValidator`): `refreshToken` not blank and at most 256 characters (a real token is 43). Any other value reaches the handler, so garbage gets the same 401 as a real token of an ended session.

**Refresh** (`RefreshTokenCommandHandler`), in this order (Ruling R7):

1. Hash the presented token (`ISecureTokenService.Hash`) and load its session with the **whole** chain (`GetByRefreshTokenHashAsync`). No session: audit `auth.refresh_failed` (no user), 401 `auth.invalid_refresh_token`.
2. Load the session's user. Gone (soft-deleted) or suspended: the session is revoked with `AdminRevoked` (only an administrator deletes or suspends an account), audit `auth.refresh_failed` with reason `account_unavailable`, 401 `auth.invalid_refresh_token`.
3. `ValidateRefresh(hash, user.SecurityStamp, now)` on the loaded session, with the rules of `Rotate` (see [Domain model](#domain-model)): an ended session gives `auth.invalid_refresh_token`; a changed security stamp revokes it (`PasswordChanged`, audit reason `security_stamp_changed`) and gives `auth.invalid_refresh_token`; a token already used or revoked revokes it (`TokenReuse`, handled as in step 4) and gives `auth.refresh_token_reused`; an expired token (sliding or absolute) gives `auth.refresh_token_expired` and changes nothing. None of these claims anything, so an expired token presented twice stays "expired".
4. **Claim** the token in the database (`TryClaimRefreshTokenAsync`, one conditional `UPDATE`) **before** rotating. Of two requests that present the same token at the same moment, both pass step 3 on their own copy, but only one claim changes the row. A failed claim means the row changed after step 1, so the handler reads the token's stored `UsedAt` and `RevokedAt` (`GetRefreshTokenStateAsync`, untracked, with no cancellation token; the loaded session is not reloaded) to learn why:
   - **Used** (`UsedAt` set: another refresh claimed it first): reuse. `ReportTokenReuse` revokes the session (`TokenReuse`, every token it loaded, `RefreshTokenReuseDetectedDomainEvent`), audit `auth.token_reuse_detected` with the session and user id, the counter `auth.token_reuse_detected`, 401 `auth.refresh_token_reused`. Reuse found in step 3 is audited and counted the same way.
   - **Revoked but never used** (a logout, logout-all, lock or password change revoked the session in the meantime), or the token is gone: an ended session, exactly as in step 3. The session is left untouched, so the revocation keeps its time and reason; audit `auth.refresh_failed` with reason `auth.invalid_refresh_token`, no event, no counter, 401 `auth.invalid_refresh_token` (`AuthPersistenceTests.Refresh_that_loses_its_claim_to_a_logout_keeps_the_logout_and_reports_no_reuse`).
5. `Rotate` the **already loaded** instance (never reloaded: a reload would show the token used and report false reuse): a new token from `ISecureTokenService.Generate` (only its hash is stored) expiring at `min(now + SlidingLifetime, session.ExpiresAt)`, the old one marked used and replaced, `LastSeenAt = now`.
6. Issue the access token for the same session with the session's `amr` (`AuthMethods`) and `auth_time` (`AuthenticatedAt`: the sign-in, or the latest [step-up](#step-up); a refresh never renews it), the stamp snapshot and the user's current locale; audit `auth.token_refreshed`; save; 200 with the new pair and the same `sessionId`.

**Concurrency and persistence.** Exactly one of two simultaneous refreshes with one token gets 200 and the other 401 `auth.refresh_token_reused`, never a 500, and afterwards the session is revoked, so the winner's new refresh token fails too (`RefreshTests.Concurrent_refresh_with_same_token_succeeds_once`). This is deliberate: a token presented twice may be a stolen copy, and the owner signs in again. No save in these handlers can lose to a concurrency conflict, because sessions and refresh tokens carry no `RowVersion` (see [Data](#data)); a revocation is therefore saved with plain `SaveChangesAsync` and needs no retry. Every save in the refresh, logout and logout-all handlers, and the claim itself, runs with `CancellationToken.None`: a client that disconnects cannot stop a revocation, a reuse audit or a claimed rotation from being stored. Known limits: if the save after a successful claim fails (a database error, so a 500), the token stays claimed and its next use is reported as reuse; a transient retry of the claim after a lost reply finds the token used and is reported as reuse too (both err towards ending the session). A refresh that loses its claim to a logout (or any other revocation) running at the same moment is not reuse: it answers `auth.invalid_refresh_token` and the logout's reason stays (step 4).

**Enumeration.** An unknown token, garbage, and a token of an ended session (logout, logout-all, password change, suspension) all answer the same 401 `auth.invalid_refresh_token` with the same body but `traceId` (`RefreshTests.Refresh_with_garbage_returns_401_not_500`). `auth.refresh_token_expired` and `auth.refresh_token_reused` are only given for a token that did exist, which only its holder can present. The audit log tells the cases apart (failure reasons `auth.invalid_refresh_token`, `auth.refresh_token_expired`, `security_stamp_changed`, `account_unavailable`; event `auth.token_reuse_detected`).

**Logout** (`LogoutCommandHandler`, `POST /api/v1/auth/logout`): revokes the session named by the access token's `sid` (`ICurrentUser.SessionId`) with `Logout`, which revokes every token in it; audit `auth.logout` with the session id; save. It always answers 204: a token without `sid`, an unknown session, one of another user, and one that has already ended change nothing and write no audit entry.

**Logout all** (`LogoutAllCommandHandler`, `POST /api/v1/auth/logout-all`): revokes every active session of the caller (`GetActiveByUserAsync`) with `LogoutAll`; one audit entry `auth.logout_all` with the current session id and `{"sessionCount":n}` in `Details`; save; 204. Other users' sessions are untouched.

**Access tokens after logout (decision D9).** Logging out ends the refresh tokens at once, but an access token already issued keeps working until its `exp` (at most `Auth:Jwt:AccessTokenLifetime`, 10 minutes, plus the 30-second skew), because access tokens are not checked against the session on each request (ADR 0015; `RefreshTests.Access_token_of_a_logged_out_session_still_validates_until_it_expires`). Clients drop both tokens on logout.

**Secrets.** `RefreshTokenCommand` and `RefreshTokenRequest` print only their type name; no audit row, log line or metric tag holds a refresh token or its hash.

## Sessions and profile

<!-- The session list, revoking a session and the profile update. -->

**Listing sessions** (`GET /api/v1/auth/sessions`, `ListSessionsQueryHandler`). A Dapper query, so it repeats the rules the EF model would apply: it keeps to the caller's own rows (`UserId = @UserId`; the owner always comes from the access token's `sub`, never from the request) and to the sessions that can still refresh. A session is listed when it is not revoked (`RevokedAt IS NULL`), has not reached its absolute expiry (`ExpiresAt > @Now`) **and** still holds a live refresh token (one that is unused, not revoked and not past its own expiry). The last condition is the sliding idle expiry: `UserSession.IsActive` checks only the first two, so a session idle for longer than `Auth:RefreshToken:SlidingLifetime` would still be "active" in the domain although it can no longer refresh; the list leaves it out. `@Now` is the injected `TimeProvider`'s instant, and the boundaries are the domain's (a session or token is over from its expiry instant on). `isCurrent` is true for the session whose id equals the access token's `sid`. The response carries no token, token hash or security stamp, and its times are UTC (`DateTime`, like every cursor key; `SessionResponse` follows the Sample module's list response). Paging follows ADR 0010: the sort allow-list is `lastSeenAt` and `createdAt` (default `-lastSeenAt`), `Id` is appended as the tie-breaker (several sessions can share a timestamp), and a cursor is tied to the caller, so one issued to another user is `pagination.cursor_mismatch`. Each sort has an index `(UserId, Column, Id)` (migration `AddSessionListIndexes`, review P7).

**Revoking a session** (`DELETE /api/v1/auth/sessions/{id}`, `RevokeSessionCommandHandler`). A session that does not exist and a session that belongs to another user both answer 404 `auth.session_not_found` with the same body shape (only the id the caller sent, in `params` and in the message, differs), never 403, so session ids cannot be probed. For the caller's own session the handler calls `UserSession.Revoke(Logout, now)`, which ends the session and every token it holds, so its refresh token stops working at once (`SessionTests.Revoking_a_session_stops_its_refresh_token`); the access token already issued keeps working until it expires (D9). Revoking the current session is allowed and is the same as logging out. A session of the caller that is already revoked answers 204 and changes nothing, like logging out twice (a session past its expiry that was never revoked is revoked now). The reason is `Logout` whichever device the session was on, and `auth.session_revoked` is audited with the session id when a revocation actually happens. Like logout, the save runs with `CancellationToken.None`, and no concurrency conflict is possible because sessions carry no `RowVersion`.

**Updating the profile** (`PUT /api/v1/auth/me`, `UpdateProfileCommandHandler`). All three fields are required. `UpdateProfileCommandValidator`: `displayName` not blank and at most `User.MaxDisplayNameLength` (200) characters (stored trimmed); `locale` a predefined culture name (`CultureInfo.GetCultureInfo(name, predefinedOnly: true)`, at most `User.MaxLocaleLength` (16) characters, not the invariant culture), stored in its canonical spelling (`MS-my` becomes `ms-MY`); `timeZone` an IANA id that `TimeZoneInfo.TryFindSystemTimeZoneById` finds (at most 64 characters, no white space: this also refuses the Windows ids that Windows would resolve, so a value accepted on a developer's machine is never refused on Linux). The language is not limited to the supported UI cultures: a saved language the API cannot answer in simply leaves the choice to `Accept-Language`. The handler saves the user (an optimistic `RowVersion` conflict is the usual 409), audits `auth.profile_updated`, and returns the profile through the same query handler as `GET me`, so roles and permissions are included and the response always equals what `GET me` reads. A caller whose account is gone or suspended gets the same body-less 401 as `GET me`.

**When the new language applies.** The pipeline reads the language from the access token's `locale` claim (decision D7) and does not look the user up per request, so the access token issued **before** the change keeps answering in the old language until it expires (at most 10 minutes) or the client refreshes: a refresh issues a new access token with the user's current locale. This is the same trade-off as D9 and keeps every request free of a database read. A client that wants the change at once calls `POST /api/v1/auth/token/refresh` after `PUT me` (`ProfileTests.Update_profile_changes_locale_and_localizes_the_next_error_response` pins both halves: the old token still answers in English, the refreshed one in Malay).

**Runtime requirements.** Culture and time zone data need ICU and, on Linux, the tz database (`tzdata`); a container image with `InvariantGlobalization` on, or without `tzdata`, would reject every locale and time zone other than the invariant ones and `UTC`. The repository does not turn invariant globalization on (see `SupportedUICultures` in `docs/services/api.md`), and the CI runner and the Docker-based tests have both.

## Passwords

<!-- Forgot, reset and change password, and what they guarantee. -->

The handlers live in `Application/Passwords/{Forgot,Reset,Change}/`, each with its command and validator; `PasswordHasherExtensions.IsRecentPassword` (`Application/Passwords/`) is the reuse check both reset and change use. The request bodies are `Endpoints/{ForgotPasswordRequest,ResetPasswordRequest,ChangePasswordRequest}.cs`.

**Validation** (in the validation decorator, before the handler; each rule stops at its first failure):

- Forgot: `email` as for registration (required, at most 256 characters, an email address).
- Reset: `token` not blank and at most 256 characters; `newPassword` with the registration limits: not empty and not only white space, `Auth:Password:MinLength` to `MaxLength` characters (12 to 128 by default, UTF-16 characters, not trimmed, not normalized; Ruling R14). The length is checked before any lookup, breach check or hashing, so a 1 MB password is refused cheaply.
- Change: `currentPassword` not empty and at most `MaxLength`, with no minimum (as at login: a password an older, shorter minimum accepted must still prove the caller); `newPassword` as for reset.

**Reuse check.** A new password may not match any entry of the user's password history (`IPasswordHasher.Verify(entry.PasswordHash, newPassword)` against every entry; a rehash-needed match counts). The newest entry is the current hash and `ChangePassword` keeps `Auth:Password:HistoryCount` entries (5), so the current password and the four before it are refused with 400 `auth.password_reused`; an older one may come back. Every entry is verified, with no early exit.

**Forgot** (`ForgotPasswordCommandHandler`): load the user by `NormalizedEmail`. An unknown address, a suspended account, or a `PasswordReset` code issued less than `Auth:Verification:ResendCooldown` ago (`GetLastIssuedAtAsync`, review 2.11) issues nothing. Otherwise `PasswordResetLinkIssuer` (`Application/Passwords/`, the one issuer of reset links, which the user administration uses too) invalidates every pending `PasswordReset` code of the user and issues a new one (token from `ISecureTokenService.Generate`, only its SHA-256 hash stored, the token protected with `ISecretProtector` into the issued event, lifetime `Auth:Verification:PasswordResetLifetime` of 30 minutes, the client address as `CreatedIp`, and the trigger the caller names: `SelfService` here); `PublishVerificationCodeIssuedDomainEventHandler` then publishes the `Auth:Links:ResetPasswordUrl` link as `PasswordResetRequestedIntegrationEvent` (see [Publishing](#publishing)), which the Notifications module emails as `auth.password_reset` in the user's language. An account without a password (created by an administrator) is a known account here: the reset is how it sets its first password (Ruling R3). Every path writes one `auth.password_forgot_requested` audit entry with the masked address (succeeded with the user id when a code was issued; otherwise not succeeded with the reason `unknown_email`, `auth.account_inactive` or `cooldown`) and saves once.

**Reset** (`ResetPasswordCommandHandler`), in this order:

1. Hash the token, find the code by hash and check it (`CanConsume(PasswordReset, now)`): unknown, used, invalidated (replaced by a newer forgot), expired or another purpose (an email-confirmation token) is 400 `auth.invalid_token`.
2. Load the user. Gone (soft-deleted) or suspended: the same 400 `auth.invalid_token`; a reset never reactivates an account.
3. Breach check (400 `auth.password_breached`). It depends on the password alone and reveals nothing about the account, so it runs before the code is consumed and a breached password leaves the link usable.
4. **Consume the code atomically:** `IVerificationCodeRepository.TryConsumeAsync` is one conditional `UPDATE` (see [Data](#data)). Of two simultaneous resets with one token exactly one changes the row; the other answers 400 `auth.invalid_token`, never a 409 or a 500 (`PasswordTests.Concurrent_reset_with_same_token_succeeds_once`). Then `Consume` the loaded code.
5. Reuse check (400 `auth.password_reused`), **after** the code is consumed. The history holds the current hash, so a check before the claim would let whoever holds the link test candidate passwords for free and silently, and learn the current password (a working credential that outlives the link, with no takeover for the owner to notice) or old ones. A reused password therefore uses up the link, and the owner asks for a new one (`PasswordTests.Reset_to_a_recent_password_uses_up_the_link`).
6. Hash the new password, `ChangePassword` (new hash, a new security stamp, the history trimmed to `HistoryCount`, failures and lockout cleared, `PasswordChangedDomainEvent`), `ConfirmEmail` (the token proves control of the mailbox), invalidate every other pending `PasswordReset` code of the user (a second forgot's link, or a leaked one, dies with the reset; `PasswordTests.Reset_kills_every_other_pending_reset_link`), revoke **every** active session with `PasswordChanged`, audit `auth.password_reset` with `{"revokedSessionCount":n}` in `Details`, one save. The claim, the session lookup and the save run with no cancellation token: once the code is consumed, a client that goes away cannot leave it spent with the password unchanged.

Every failure is audited as `auth.password_reset_failed` with the error code as the reason and the code's user id when known, never the token or the password.

**Change** (`ChangePasswordCommandHandler`, authenticated), in this order:

1. Load the caller (`ICurrentUser.UserId`). Unknown, soft-deleted or suspended: the endpoint answers the same body-less 401 `http.401` as a request without a valid token (fail closed, as `GET /me`).
2. **The MFA rule** (plan decision D11, ADR 0023). When the account has a confirmed MFA method (`IMfaMethodRepository.HasConfirmedAsync`; a pending setup does not count), `StepUpPolicy.Check(hasConfirmedMfa: true)` must pass: the access token needs a fresh `auth_time` and an `amr` of `otp` or `rcvr` (see [Step-up](#step-up)), otherwise 403 `auth.step_up_required`. It runs **before** the current password is verified, so a refused request spends no hashing and learns nothing about the password; it is audited as `auth.password_change_failed` with that code as the reason and, like a wrong current password, **not** counted toward the lockout. A password-only account skips this step entirely and is unchanged: its current password in the body is the re-verification (`PasswordTests` and `MfaManagementTests.Change_password_of_a_password_only_account_needs_no_step_up`). The client calls `POST /api/v1/auth/step-up` with a code, then retries with the new access token (`MfaManagementTests.Change_password_of_an_mfa_account_needs_a_fresh_otp_step_up`).
3. Verify the current password: exactly one verification (`Verify`, or `SpendVerificationCost` for an account without a password, which never matches). Wrong: 400 `auth.current_password_incorrect`. It is audited but **not** counted towards the login lockout (`AccessFailedCount` is a login counter); the `auth-strict` limiter bounds the guessing instead.
4. Breach check (400 `auth.password_breached`), then the reuse check (400 `auth.password_reused`); both only after the current password is proven.
5. `ChangePassword` (as for reset), and every pending `PasswordReset` code of the user is invalidated, so a link emailed before the change no longer works (`PasswordTests.Change_kills_pending_reset_links`). Every active session of the user except the current one (the access token's `sid`, `ICurrentUser.SessionId`) is revoked with `PasswordChanged`; the current one takes the new stamp with `AdoptSecurityStamp`, so its refresh token keeps working (spec 12.2) while every other session's next refresh would fail on the stamp anyway. Audit `auth.password_changed` with the current session id and `{"revokedSessionCount":n}`; one save.

Failures are audited as `auth.password_change_failed` with the error code as the reason and the current session id. Access tokens already issued, the other sessions' included, keep working until they expire (decision D9).

**Enumeration guarantees.** Forgot answers 202 with no body and the same headers for a known and an unknown address (`PasswordTests.Forgot_returns_identical_202_for_known_and_unknown_email`), and every path writes one audit row and saves once. The known-address path still costs a few queries and one Data Protection encryption more; there is no hashing on either path. The only observable difference is the email, which only the owner of the address receives. Reset and change answer only to someone who holds a reset link or a signed-in session, so their distinct errors reveal nothing about other accounts.

**Known limits.** The claim commits on its own, before the handler's save: if that save then fails (a database error, so a 500), the link is spent and the password unchanged, and the user asks for a new link. A reset or change that races another write to the same user row (a login, a confirmation) loses on the user's `RowVersion` and answers 409 `concurrency.conflict`; nothing was saved, and the request can be repeated (for a reset, with a new link when the claim had committed).

**Secrets.** `ResetPasswordCommand`, `ChangePasswordCommand` and their request bodies print only their type name; no audit row, log line or metric tag holds a password, a token or an unmasked address. The reset token reaches the outbox only encrypted (ADR 0017).

## User administration

<!-- The administration of user accounts: list, read, create, lock, unlock, forced reset, session revocation and role assignment. -->

The handlers live in `Application/Admin/Users/{List,Get,Create,Lock,Unlock,ForcePasswordReset,RevokeSessions,ResetMfa,AssignRoles}/`, the routes in `Endpoints/AdminUserEndpoints.cs` with their bodies in `Endpoints/AdminUserRequests.cs`. Every command carries the acting administrator's id, taken by the endpoint from the access token's `sub` (a principal without one gets the body-less 401, though the permission policy never lets one through). Every successful action writes one audit entry with the **target** in `UserId` and the **actor** in `Details` as `{"actorId":"…"}`, serialized by `System.Text.Json` (`AdminAudit`), and saves once: `auth.admin_user_created`, `auth.admin_user_locked`, `auth.admin_user_unlocked`, `auth.admin_password_reset_forced`, `auth.admin_sessions_revoked`, `auth.admin_mfa_reset`, `auth.admin_roles_assigned`. Refused actions are not audited.

**Listing** (`ListUsersQueryHandler`, Dapper). The query writes `IsDeleted = 0` itself (ADR 0006), so a soft-deleted user is never listed or counted. `search` is a literal prefix of the email: it is trimmed and upper-cased like `User.NormalizeEmail`, its `LIKE` wildcards (`%`, `_`, `[`) and the escape character are escaped, and it is matched against `NormalizedEmail` (`a_b` finds only addresses starting with `A_B`). `status` is `Active` or `Suspended` (a number outside the enum is 400). Paging follows ADR 0010: the sort allow-list is `createdAt` and `email` (which sorts by `NormalizedEmail`), default `-createdAt`, with `Id` as the tie-breaker; a cursor is tied to its `search` and `status`. The selected columns hold no secret. `isLockedOut` is a login lockout in force now (`LockoutEnd > now`), not a suspension.

**Reading one** (`GetUserQueryHandler`) goes through the repositories, whose soft-delete filters hide a deleted user (404 `auth.user_not_found`, like an unknown id) and deleted roles. `hasPassword` is false for an account created by an administrator until its user sets a password. `mfaEnabled` is `IMfaMethodRepository.HasConfirmedAsync`: true only with a confirmed method (`AdminMfaTests.Get_user_shows_mfa_enabled`); it tells the administrator whether a reset would change anything.

**Creating** (`CreateUserCommandHandler`). The validator applies the registration rules to `email` (required, at most 256 characters, an address), `displayName` (not blank, at most 200, stored trimmed) and `locale` (a predefined culture, stored canonical; the endpoint fills it from the request's language); `roleIds` holds at most 50 ids and no empty one. Then:

1. The address is normalized as at registration (case and surrounding white space do not matter, Review Focus 1); one in use answers 409 `auth.email_taken`. This route is for administrators, so telling them an address exists is no enumeration risk. When two creates of the same new address race past this lookup, the unique index `IX_Users_NormalizedEmail` refuses the second insert and `IUnitOfWork.SaveChangesUnlessDuplicateAsync(UniqueIndexNames.UserEmail, ...)` turns that into the same 409 (nothing is saved), never a 500 (`AdminUserTests.Concurrent_creates_of_one_address_yield_one_account_and_never_a_500`).
2. Roles: none given (null or empty) gives the seeded `User` role. Given ids need `auth.user.assign_roles` as well (403 `auth.role_assignment_not_allowed`): `Admin` may create accounts but not assign roles, and could otherwise create accounts holding roles it cannot grant. Each id must be an existing role that is not soft-deleted (404 `auth.role_not_found` names the first one that is not), and only an active SuperAdmin may grant `SuperAdmin` (403 `auth.cannot_manage_super_admin`). The actor must also hold every permission the given roles grant (deprecated ones excepted; 403 `auth.permission_grant_not_allowed`, the rule of role permission sets), so an account cannot be created with more than its creator has. The default `User` role is not checked.
3. `User.Register` with **no password hash** (no random hash is invented), the same factory self-registration and the seeder use, so it raises `UserRegisteredDomainEvent` like them (Plan 3 consumers see one kind of new user). The account is `Active` with an unconfirmed email; login treats it like an unknown address until it has a password (Ruling R3). The roles are assigned with the actor as `AssignedBy`.
4. A **set-password link**: a `PasswordReset` code issued by the same `PasswordResetLinkIssuer` forgot-password calls (only the hash stored, the token encrypted into the issued event, ADR 0017), so the same publishing handler publishes its link from the outbox. The trigger is `CreatedByAdmin`, so the published `PasswordResetRequestedIntegrationEvent` has the reason `CreatedByAdmin` (a forced reset below: `ForcedByAdmin`), and the Notifications module emails it as `auth.account_created` (`auth.password_reset_required` for a forced reset), in the language the administrator gave the account. The link works for `Auth:Verification:PasswordResetLifetime` (30 minutes). The reset sets the first password and confirms the email (see [Passwords](#passwords)). **A user who misses the 30 minutes asks for a new link with forgot password** (`POST /api/v1/auth/password/forgot`), which treats an account without a password as a known one (R3).
5. Audit and one save; 201 with the new id and its `Location`.

**Locking** (`LockUserCommandHandler`). A caller cannot lock their own account (400 `auth.cannot_lock_self`, checked first). `User.Suspend` sets `Suspended` and rotates the security stamp; every active session is revoked with `AdminRevoked`, so no refresh token of the user works any more; audit; one save with no cancellation token (a revocation is stored even when the client goes away; the user's `RowVersion` still guards the row, so a simultaneous write to it answers 409 `concurrency.conflict`); then the user's cached permissions are removed (`IPermissionCache.InvalidateUsersAsync`), so a suspended user has no permission from their next request on this instance. Access tokens already issued pass the bearer check until they expire (at most 10 minutes, D9), but grant no permission. Login then answers 403 `auth.account_inactive` after a correct password. Locking a suspended account answers 204 again.

**Unlocking** (`UnlockUserCommandHandler`). `User.Reinstate` makes the account active and also clears the failed-sign-in count and any login lockout, so the user can sign in at once; sessions revoked by the lock stay revoked. Audit, save, cache invalidation. Unlocking an active account answers 204 (and clears its failures).

**Forcing a password reset** (`ForcePasswordResetCommandHandler`). Issues a reset code exactly as above (pending reset codes are invalidated, no cooldown: the permission is the limit), revokes every active session with `AdminRevoked`, audits and saves once (no cancellation token); 202 with no body. The token never appears in a response, a log or the audit row: only encrypted, in the outbox. The current password keeps working until the user resets it; to stop sign-ins at once, lock the account. A suspended account is refused with 403 `auth.account_inactive`, because its reset would be refused anyway.

**Revoking sessions** (`RevokeUserSessionsCommandHandler`). Every active session of the user is revoked with `AdminRevoked`; the account is untouched and the user can sign in again. Audited also when there was nothing to revoke; 204.

**Resetting two-step verification** (`ResetUserMfaCommandHandler`, `Application/Admin/Users/ResetMfa/`; `POST /api/v1/admin/auth/users/{id:guid}/reset-mfa`, permission `auth.user.reset_mfa`, no body; plan decision D17). For the user who lost the authenticator and every recovery code, so neither the self-service `DELETE` nor a recovery-code step-up is possible ([Managing MFA](#managing-mfa)). In this order:

1. **Not oneself:** a caller cannot reset their own two-step verification here (400 `auth.cannot_reset_own_mfa`, checked first and before the user is loaded); the self-service route, with its step-up, is for that. An administrator who lost their own device asks another administrator.
2. **The user:** an unknown or soft-deleted id is 404 `auth.user_not_found`; a SuperAdmin target needs an active SuperAdmin actor (403 `auth.cannot_manage_super_admin`, [SuperAdmin protection](#user-administration) below). The last-SuperAdmin rule does not apply: nothing is demoted or locked.
3. **No method at all** is a no-op: 204, nothing changed, nothing audited, nothing saved (`AdminMfaTests.Reset_without_mfa_answers_204_and_changes_nothing`). The reset is idempotent: a second call answers 204.
4. **Otherwise** the method (`IMfaMethodRepository.GetTotpAsync`: TOTP is the only type) and **every** recovery code, used or not, are removed. When the method was **confirmed**, `MfaChangeEffects.ApplyAsync(user, MfaChange.ResetByAdmin, keepSessionId: null, SessionRevokedReason.AdminRevoked, now)` rotates the security stamp, revokes every active session of the user (none is kept: the actor is another person) and raises `MfaChangedDomainEvent(ResetByAdmin)`; the stamp is the single revocation rule (D13), so the pending sign-in challenges and the remembered devices of the user die with it (`Reset_forgets_trusted_devices_and_pending_challenges`). A **pending** setup alone protects nothing: it is only removed, with no new stamp, no revoked session and no event, as when its owner cancels it (`Reset_of_a_pending_setup_only_removes_it`). `auth.admin_mfa_reset` is audited in both cases, then **one save** with no cancellation token (a reset is stored even when the client goes away; the user's `RowVersion` and the method's concurrency tokens guard the rows, so a simultaneous change answers 409 `concurrency.conflict` and nothing is saved); 204.

The user then signs in with the password alone, no challenge, and can set up a new authenticator from the self-service routes (`Reset_lets_the_user_sign_in_with_the_password_alone_and_ends_every_session`). The user is not asked to prove anything. The handler sends no email itself: the `MfaChangedDomainEvent` becomes a `MfaChangedIntegrationEvent` (`ResetByAdmin`) and the Notifications module emails the user an `auth.mfa_changed` notice in their language, so the person learns that an administrator removed their second factor ([Notifications](#notifications)). **Review the permission like a role change:** a holder can strip the second factor from any non-SuperAdmin account, so the account is then only as safe as its password; the audit row (`Audit_row_records_actor_and_target`) and the notification are the control.

**Assigning roles** (`AssignRolesCommandHandler`). The body is the complete new set (duplicates ignored; empty removes every role). Each id must be an existing, undeleted role (404 `auth.role_not_found`). Roles not in the set are removed and new ones assigned with the actor as `AssignedBy`; audit; one save; then the user's cached permissions are removed, so the change applies to the user's **next request** on this instance (other instances within 30 seconds, ADR 0016; `AdminUserTests.Assigning_a_role_grants_access_on_the_next_request`). A role the user does not hold yet can be added only by an actor who holds every permission it grants that is not deprecated (`PermissionGrantRules`, checked with `IPermissionChecker` in code order; 403 `auth.permission_grant_not_allowed`, nothing saved), the same rule as for role permission sets: without it a holder of `auth.user.assign_roles` could give themselves, or anyone, a role that grants more than they hold. Roles the user keeps and roles removed are not checked, and a SuperAdmin, who holds every permission that is not deprecated, always passes. The check runs after the SuperAdmin rules below and uses the actor's cached permission set (up to 30 seconds old on another instance).

**SuperAdmin protection** (`SuperAdminRules`, `SuperAdminScope`). `Admin` holds `auth.user.lock`, `auth.user.reset_password`, `auth.user.revoke_sessions` and `auth.user.reset_mfa` by default, so without these rules an Admin could lock out, sign out, strip the second factor from or take over (through a forced reset) every SuperAdmin, and whoever may assign roles could make themselves SuperAdmin:

- Lock, unlock, forced reset, session revocation, MFA reset and role assignment on a user who holds the `SuperAdmin` role answer 403 `auth.cannot_manage_super_admin` unless the actor is an **active** SuperAdmin (`IUserRepository.IsActiveInRoleAsync`: a suspended or deleted SuperAdmin whose cached permissions still let a request through does not count).
- Only an active SuperAdmin may grant `SuperAdmin`, through role assignment or creation, to anyone, themselves included (the same 403).
- The last active SuperAdmin can be neither demoted nor locked: 409 `auth.last_super_admin` when the target is an active SuperAdmin and no other active, undeleted user holds the role (`IUserRepository.AnyOtherActiveInRoleAsync`; a suspended SuperAdmin does not count). A locked last SuperAdmin would leave nobody able to administer SuperAdmin accounts. Locking needs a SuperAdmin actor other than the target, so through the API this guard is met when a SuperAdmin demotes themselves; for locking it is a backstop.
- The SuperAdmin role is found by its normalized name and must be the seeded system role (`Role.IsSuperAdmin`); a missing role is a seeding error (`InvalidOperationException`).

**Known limits.** Two SuperAdmins demoting or locking each other at the same moment can both pass the last-SuperAdmin check (each sees the other) and leave none; the checks and the writes are not serialized. Recovery then needs either a **new** seed administrator address (`Auth:Seed:AdminEmail` set to an address no account has used, soft-deleted ones included, with `Auth:Seed:AdminPassword`, then a restart), because the seeder skips any email that already exists, even a soft-deleted account (see [Background processing](#background-processing)), or a direct database edit. A lock or unlock changes the user row, so racing another write to the same row (a login, a reset) loses on `RowVersion` and answers 409 `concurrency.conflict`; nothing was saved and the request can be repeated. A role change is **not** guarded that way: `AssignRole` and `RemoveRole` only add and remove `auth.UserRoles` rows and never touch the user row, so it does not conflict with a simultaneous write to the user, and two simultaneous changes of one user's roles both apply (the later one does not see the earlier). Two simultaneous assignments that add the same role to the same user can collide on the `UserRoles` primary key and answer a 500; this is rare and limited to administrators.

**Enumeration.** These routes answer only to signed-in administrators with the permission, so they say plainly whether an address or id exists (409 `auth.email_taken`, 404 `auth.user_not_found`); the self-service routes keep their identical answers.

## Role, permission and audit log administration

<!-- The administration of roles and their permissions, the permission list and the audit log. -->

The handlers live in `Application/Admin/{Roles,Permissions,AuditLogs}/`, the routes in `Endpoints/AdminRoleEndpoints.cs` (roles and permissions) and `Endpoints/AdminAuditLogEndpoints.cs`, their bodies and query strings in `Endpoints/AdminRoleRequests.cs` and `Endpoints/AdminAuditLogRequests.cs`. Every write names the acting administrator (the token's `sub`, see `AdminActor`) and every success saves once.

**Roles** (`Roles/{List,Get,Create,Update,Delete,SetPermissions}/`).

- **Create** (`CreateRoleCommandHandler`). The name is trimmed and unique ignoring case (`Role.NormalizedName`): a lookup answers 409 `auth.role_name_taken`, and when two creates of one name race past it the unique index `IX_Roles_NormalizedName` refuses the second insert and `IUnitOfWork.SaveChangesUnlessDuplicateAsync(UniqueIndexNames.RoleName, ...)` turns that into the same 409 (nothing is saved). The new role has no permissions. The system role names (`SuperAdmin`, `Admin`, `User`) are taken too. Validation (`RoleRules`): name not blank and at most 100 characters, description present (it may be empty) and at most 500, so a missing `description` is a 400.
- **Update** (`UpdateRoleCommandHandler`). Renames and replaces the description; a system role answers 409 `auth.system_role_protected` (the rule is `Role.UpdateDetails`), a name used by another role 409 `auth.role_name_taken` (also on the index race); renaming a role to its own name in another case is allowed. A rename changes no grant, so no cached permission set is touched.
- **Delete** (`DeleteRoleCommandHandler`). `Role.MarkDeleted()` refuses a system role (409 `auth.system_role_protected`) and drops the grants (they are deleted for good; `RolePermissions` has no soft delete), the role is removed from the repository and the save interceptor turns that into the soft delete: the row stays with `IsDeleted = 1`, its name is free again. Users keep their `UserRoles` row, which no longer counts (every read filters deleted roles). After the save the cached permissions of every user who held the role are removed, so they lose its permissions on their next request. A role that is already deleted is a 404 like an unknown one.
- **Set permissions** (`SetRolePermissionsCommandHandler`). The body is the complete new set (duplicates ignored; empty removes every grant). In order: every id must exist (400 `auth.permission_not_found`); a **deprecated permission cannot be newly granted** (the same 400; one the role already holds may stay in the set, so the set `GET` returned can be written back); an administrator can **newly grant only a permission they hold themselves** (403 `auth.permission_grant_not_allowed`, checked by `PermissionGrantRules` with `IPermissionChecker` for each permission added, the rule role assignment shares; withdrawing a permission or leaving one in place is never checked), because without it whoever holds `auth.role.manage` could put any permission on a role and assign it (or have a colleague assign it) and so hold what they were never given. `SuperAdmin` holds every permission that is not deprecated, so the rule never stops one. `Role.SetPermissions` then refuses the `SuperAdmin` role (409 `auth.system_role_protected`, also when the set would not change); the sets of `Admin`, `User` and custom roles can be edited, and the seeder never rewrites `Admin`'s set after the role exists (see [Background processing](#background-processing)). A set equal to the current one saves and audits nothing and answers 204. Otherwise one save writes the grants and the audit entry, then `RolePermissionCacheInvalidator` removes the cached permissions of every user in the role (`IRoleRepository.GetUserIdsInRoleAsync` + `IPermissionCache.InvalidateUsersAsync`, after the save, with no cancellation token), so the change applies to those users' **next request** on this instance (other instances within 30 seconds, ADR 0016; `AdminRoleTests.Revoking_a_role_permission_takes_effect_on_the_next_request`). The invalidator also reaches suspended and deleted users, whose set is empty anyway.
- **Get** (`GetRoleQueryHandler`) goes through the repositories, whose soft-delete filter hides a deleted role (404 `auth.role_not_found`, like an unknown id). Its permissions include grants of deprecated permissions, marked `isDeprecated`.
- **List** (`ListRolesQueryHandler`, Dapper). The query writes `IsDeleted = 0` itself (ADR 0006). The sort allow-list is `name` (the `NormalizedName` column, so it is case-insensitive) and `createdAt`, default `name`, with `Id` as the tie-breaker. `permissionCount` counts the grants, deprecated ones included.

**Permissions** (`Permissions/List/ListPermissionsQueryHandler`, Dapper). Sorted by `code` (the only sort; unique, so the id tie-breaker never decides an order). Rows with `IsDeprecated = 1` are left out unless `includeDeprecated=true`; a cursor is tied to that flag. Read-only, no personal data. The table has no soft-delete column.

**Audit log** (`AuditLogs/List/ListAuditLogsQueryHandler`, Dapper). Read-only. Paging follows ADR 0010: the only sort is `occurredAt` (default `-occurredAt`) with the entry's unique `bigint` `Id` as the tie-breaker, so entries written at the same instant are neither skipped nor repeated (`AuditLogTests.Pages_by_cursor_without_duplicates_when_rows_share_a_timestamp` inserts rows with identical `OccurredAt`); the page size is capped at 100. Filters: `userId`; `eventType`, which must be one of `AuthAuditEvents.All` compared exactly (400 `validation.failed` otherwise), so no free text reaches the query; `succeeded`; `from` and `to`, **inclusive**, parsed by `AuditLogTimestamp` as ISO 8601 (`2026-10-09`, `2026-10-09T08:30Z`, `2026-10-09T08:30:00.5+08:00`): a value with an offset is converted to UTC, one without is read as UTC (never in the server's time zone). A date without a time is midnight at the **start** of that day, so `to=2026-10-09` ends at the beginning of 9 October and leaves out nearly all of it: to include a whole day, send `to=2026-10-09T23:59:59.9999999Z` or the next day's date (its midnight entry is included too). Another spelling is a 400, and so is `to` before `from` (compared as instants). A blank `eventType`, `from` or `to` is no filter. There is no cap on the span of `from` to `to`: leaving both out is the widest range anyway and the `(OccurredAt, Id)` indexes serve any range; the page size is what bounds a response. A cursor is tied to its filters. The response members are exactly those of the table in [Endpoints](#endpoints): no secret is ever written to the log, `attemptedIdentifier` was masked when it was written (`a****@example.com`), `details` is the JSON text of the entry. The log can show IP addresses and user agents, which is why it has its own permission.

**Audit entries.** A role is not a user, so the role events keep `UserId` empty (the log's `userId` filter finds what happened **to** a user, as for the user administration) and put the facts in `Details`, written by `System.Text.Json` (`RoleAudit`), never containing a secret:

| Event | `Details` |
|---|---|
| `auth.role_created` | `{"actorId":"…","roleId":"…","name":"Support"}` |
| `auth.role_updated` | `{"actorId":"…","roleId":"…","name":"Helpdesk","previousName":"Support"}` |
| `auth.role_deleted` | `{"actorId":"…","roleId":"…","name":"Support"}` |
| `auth.role_permissions_changed` | `{"actorId":"…","roleId":"…","name":"Support","added":["auth.user.view"],"removed":[]}` (permission codes in code order) |

Refused actions are not audited, and neither is a permission set that did not change.

**Permissions of the routes.** Reads: `auth.role.view` (roles), `auth.permission.view`, `auth.audit.view`; writes: `auth.role.manage`. The seeder gives `SuperAdmin` all of them and `Admin` the three read permissions (not `auth.role.manage`), when it creates the role; administrators can change `Admin`'s set afterwards.

**Known limits.** Setting a role's permissions writes only `auth.RolePermissions` rows and never touches the role row, so it has no `RowVersion` conflict: two simultaneous changes of one role's set both apply (the later one does not see the earlier), and two that add the same permission can collide on the `RolePermissions` primary key and answer a 500; this is rare and limited to administrators. A rename or delete changes the role row and loses a race with another write to it as 409 `concurrency.conflict` (nothing saved, the request can be repeated). A load racing a change may keep the old permission set of a user for up to 30 seconds (see [Permission checks](#permission-checks)). The `eventType` list is the constants of `AuthAuditEvents`; an event type that older rows hold but the code no longer defines cannot be filtered (event types are never renamed).

### TOTP and recovery codes

`Totp`, `Base32`, `TotpUri` and `RecoveryCodeFormat` are `internal static` classes over `System.Security.Cryptography` (no package, D2). They take the time as an argument and read no clock.

| Parameter | Value |
|---|---|
| Algorithm | RFC 6238 over RFC 4226 (HOTP) with HMAC-SHA-1 (`HMACSHA1.HashData`), dynamic truncation |
| Digits | 6 (`Totp.Digits`), zero-padded |
| Time step | 30 seconds (`Totp.StepSeconds`); `Totp.TimeStepAt(instant)` is `floor(unixSeconds / 30)`, whatever the instant's offset |
| Tolerance | the current step `t`, `t - 1` and `t + 1`; two steps away is refused |
| Secret | 20 random bytes (`Totp.SecretLength`, `Totp.NewSecret()` from `RandomNumberGenerator`), kept as bytes, never in a `string` |
| Replay | a code counts only for a step greater than the method's last used step; the highest matching step wins |

**Checking a code.** `Totp.FindMatchingStep(secret, code, now, lastUsedTimeStep)` returns the matching step or null. A code that is not exactly 6 ASCII digits is null before anything is computed: a leading or trailing space, full-width digits (`１２３４５６`), letters, 5 or 7 digits. Otherwise it computes the codes of all three candidate steps and compares each with `CryptographicOperations.FixedTimeEquals` (the ASCII bytes of two 6-digit codes), and looks at the results only after all three comparisons, so the time taken does not say which step matched. A matching step at or below `lastUsedTimeStep` does not count. The step is only a candidate: the caller (`MfaFactorVerifier`) must claim it with one conditional update of the stored last used step, so that two requests with one code cannot both succeed.

**Provisioning URI.** `TotpUri.Build(issuer, accountName, secret)` returns

```text
otpauth://totp/{issuer}:{accountName}?secret={BASE32}&issuer={issuer}&algorithm=SHA1&digits=6&period=30
```

with `issuer` and `accountName` escaped by `Uri.EscapeDataString` in the label and in the query (so `Acme Hr` is `Acme%20Hr`, `alice+mfa@example.com` is `alice%2Bmfa%40example.com`, and a colon in either is `%3A`, never a second label separator). The client draws the QR code from it. `Base32` is RFC 4648 base32 (`A-Z2-7`): `Encode` writes upper case without `=` padding (a 20-byte secret is 32 characters); `Decode` also reads lower case and ignores spaces, and throws `FormatException` on any other character (`=`, `0`, `1`, `8`, `9` included) and on a length no encoding produces.

**Recovery codes.** `RecoveryCodeFormat`:

- `Count` 10 codes per user, `Length` 16 characters from `Alphabet` `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (no `0`, `1`, `I`, `O`): 32 symbols, 5 bits each, 80 bits per code. `Generate()` picks them with `RandomNumberGenerator.GetItems`.
- `Normalize(input)` trims, upper-cases ASCII letters, removes `-` and spaces, and returns null unless exactly 16 alphabet characters remain. So `abcd-efgh-jkmn-pqrs`, `ABCDEFGHJKMNPQRS` and ` abcd efgh jkmn pqrs ` followed by a newline are one code; 15 or 17 characters, an `O`, a `1`, a tab or an underscore are refused. Only ASCII `a`-`z` are upper-cased (by arithmetic, not by a culture), so a non-ASCII letter such as the long s (`ſ`) is refused instead of being turned into `S`.
- `Display(normalized)` groups by four: `ABCD-EFGH-JKMN-PQRS`.
- `Hash(normalized)` is the SHA-256 of the UTF-8 bytes of the normalized code (32 bytes), the only form a code is meant to be stored in. 80 bits make an unsalted fast hash safe (ADR 0022). `Display` and `Hash` throw `ArgumentException` for a value that is not already normalized, so a raw input can never be hashed by mistake.

### Step-up

A step-up proves the signed-in user's identity again before a sensitive action, inside the session they already have (plan decisions D9 to D12, ADR 0023). It is not a separate token: it renews the session's `auth_time` and `amr`, which every access token of the session carries, so checking it needs no database read (Plan 2 D9 stays).

**The rule** (`StepUpPolicy`, `Application/StepUp/`, scoped). `Check(hasConfirmedMfa)` succeeds when the caller's access token has an `auth_time` (`ICurrentUser.AuthTime`), `now - auth_time < Auth:StepUp:MaxAge` (10 minutes; at exactly `MaxAge` it has expired, `StepUpPolicyTests.Step_up_expires_exactly_after_max_age`), and, when the account has a confirmed MFA method, `amr` (`ICurrentUser.AuthMethods`) contains `otp` or `rcvr`: a fresh password sign-in, or a sign-in through a trusted device, does not satisfy an MFA account. Otherwise it returns 403 `auth.step_up_required`; the client calls `POST /api/v1/auth/step-up` and retries with the new access token. `now` comes from `TimeProvider`. The caller passes `hasConfirmedMfa` (`IMfaMethodRepository.HasConfirmedAsync`), because only it knows the account. A handler calls the policy, not an endpoint filter, so an action can apply it to some accounts only. TOTP setup and confirm call it ([Enrollment](#enrollment)), and so do removing a confirmed method, regenerating recovery codes and changing the password of an MFA account ([Managing MFA](#managing-mfa), [Passwords](#passwords)); endpoints built later that need a fresh identity reuse it.

**`POST /api/v1/auth/step-up`** (`StepUpCommandHandler`; `.RequireAuthorization()`, `auth-strict`, `.WithNoStore()`). `StepUpCommandValidator` first: exactly one of `password`, `code` and `recoveryCode` is not blank (otherwise 400 `validation.failed` with the error under `proof`), the password at most `Auth:Password:MaxLength` characters (no minimum, not trimmed, as at login), the code at most 16 and the recovery code at most 32 characters. A malformed code is not refused here: it is a wrong code and counts as one. Then, in this order:

1. **The caller and the session.** The access token's `sub` and `sid`: an unknown, soft-deleted or suspended user, or a session that does not exist, belongs to another user, is revoked or past its absolute expiry, or holds an older security stamp than the user's, is the body-less 401 `http.401` of a request without a valid token, as `PUT me` answers (fail closed). The access token itself outlives its session (D9), so this check keeps a step-up from minting a token for a session that has ended. Nothing is audited or counted.
2. **The factor.** `HasConfirmedAsync(userId)`. An account with two-step verification must step up with a TOTP or recovery code and one without it with its password; any other combination is 400 `auth.step_up_method_not_allowed`, audited, **not** counted (D12: a session thief with a phished password cannot switch MFA off).
3. **Locked** (`User.IsLockedOut(now)`): the failure answer of the method (`auth.current_password_incorrect` for a password, `auth.invalid_mfa_code` for a code) without verifying anything and without counting, audited with the failure reason `locked`.
4. **Verify.** A password through `IPasswordHasher.Verify` (an account without a password does the dummy verification and fails). A code through `MfaFactorVerifier` (below), which spends it in the database when it is right.
5. **Failure:** `IUserRepository.RecordFailedSignInAsync` counts it in the lockout counter by the same atomic statement as a wrong password at login (D7), and the failure that locks raises `UserLockedOutDomainEvent` (`NoteLockedOut`, which Plan 3 turns into the lockout email) and writes `auth.locked_out`; audit `auth.step_up_failed` with the error code as the reason; save; 400 `auth.current_password_incorrect` or `auth.invalid_mfa_code`. The count and this save ignore the request's cancellation, so a guesser who disconnects is still counted.
6. **Success:** `UserSession.StepUp(methods, now)` **replaces** the session's `AuthMethods` with what was proved (`pwd`, `otp` or `rcvr`) and sets `AuthenticatedAt` to now; a recovery code also calls `User.NoteRecoveryCodeUsed()` (`MfaChangedDomainEvent` with `RecoveryCodeUsed`); a new access token of the same session with `session.AuthMethods` and `session.AuthenticatedAt`; audit `auth.step_up_succeeded`; one save (with no cancellation token: a code may already be spent); 200 `{ accessToken, accessTokenExpiresAt, stepUpExpiresAt }`, where `stepUpExpiresAt` is the token's `auth_time` (whole seconds) plus `MaxAge`, the instant the policy starts refusing it. The refresh token is unchanged, and every later refresh carries the step-up's `auth_time` and `amr` (refresh reads them from the session).

The success save writes only the session (which has no `RowVersion`), the audit row and an outbox row, never the user row, so it cannot lose a concurrency race. For the same reason a password whose hash asks for a rehash (`SuccessRehashNeeded`) is **not** rehashed here; the next login does it. A successful step-up does not reset the failure count either: only a successful sign-in does (D7), so wrong codes during step-ups still count until then. Every 400 of the handler and every success is counted in `auth.step_ups`.

**The factor verifier** (`MfaFactorVerifier`, `Application/Mfa/`, scoped). `VerifyAsync(userId, MfaProof(code, recoveryCode), now, cancellationToken)` returns the `MfaFactor` (`Totp` or `RecoveryCode`) it accepted, already spent, or null. A TOTP code: the user's confirmed method (`GetTotpAsync`; none or a pending one fails), its secret through `IMfaSecretProtector.Unprotect` (a `CryptographicException` logs one Error line with the method id and fails, so after a key-ring loss the user still gets in with a recovery code), `Totp.FindMatchingStep(secret, code, now, method.LastUsedTimeStep)`, then `TryClaimTimeStepAsync`; the secret's bytes are zeroed after use. A recovery code: `RecoveryCodeFormat.Normalize` (a garbled code fails without a lookup), `FindUnusedAsync(userId, Hash(normalized))`, then `TryUseAsync`. The factor counts only when the claim wins, so one code never succeeds twice, also between simultaneous requests (`StepUpTests.Same_code_cannot_step_up_twice`). Both claims run with `CancellationToken.None`. A proof with both values or neither fails. It never counts a failure: its callers decide what a wrong code costs (step-up counts it in the lockout; the sign-in challenge counts it in the lockout and on the challenge). `MfaProof`, `StepUpCommand`, `StepUpRequest` and `StepUpResponse` print only their type name.

### Enrollment

Turning two-step verification on takes two requests in one fresh step-up (plan decisions D5, D11, D13 and D18). The client's flow:

1. **Step up** if the sign-in is older than `Auth:StepUp:MaxAge` (10 minutes): `POST /api/v1/auth/step-up` with the password, then use the new access token. Both routes below answer 403 `auth.step_up_required` otherwise.
2. **`POST /api/v1/auth/mfa/totp/setup`** (`{ label? }`) answers `{ methodId, secret, otpAuthUri }`. The client **draws `otpAuthUri` as a QR code** for the authenticator app (the server only builds the URI, D2) and offers `secret` (base32) for typing by hand.
3. **`POST /api/v1/auth/mfa/totp/confirm`** (`{ code }`, the 6 digits the app shows) answers `{ recoveryCodes }`. The client shows the ten codes once and asks the user to keep them somewhere safe.
4. `GET /api/v1/auth/mfa/methods` now shows `enabled: true` and 10 codes remaining.

**Shown once, never elsewhere.** The plain TOTP secret appears only in the setup answer (as base32 and inside the URI) and the recovery codes only in the confirm answer. The server keeps the secret only as `IMfaSecretProtector` output and each code only as its SHA-256 hash, so neither can be shown again: a user who loses the QR code starts the setup again, and lost recovery codes are replaced by [regenerating](#managing-mfa) them. Neither appears in a later answer, an audit row (`Details` holds ids and counts), a domain event, the outbox, a log line or an exception message (`MfaEnrollmentTests.Setup_secret_appears_only_in_the_setup_response` and `Recovery_codes_are_shown_once_and_never_stored_or_logged` scan every text column of every table and every log line of every level). `TotpSetupResponse.ToString()` prints the method id only, and `ConfirmTotpCommand`, `ConfirmTotpRequest` and `RecoveryCodesResponse` print only their type name. Both routes are `.WithNoStore()`, so no cache keeps either answer.

**`POST /api/v1/auth/mfa/totp/setup`** (`SetUpTotpCommandHandler`, `Application/Mfa/SetUpTotp/`; `.RequireAuthorization()`, `.WithNoStore()`). `SetUpTotpCommandValidator` first: a `label` that is given is not blank and at most 100 characters (`UserMfaMethod.MaxLabelLength`); the body may be left out. Then, in this order:

1. **Step-up:** `StepUpPolicy.Check(hasConfirmedMfa: false)`. The account has no confirmed method here (a confirmed one is refused next), so a recent sign-in or a password step-up is enough. 403 `auth.step_up_required` otherwise; nothing is read.
2. **The caller and the session**, as at step-up: an unknown, soft-deleted or suspended user, or a session that is missing, another user's, ended or holding an older stamp, is the body-less 401 `http.401`.
3. A **confirmed** method is 409 `auth.mfa_already_enabled` (one authenticator per user; replacing it is remove, then set up).
4. `Totp.NewSecret()` (20 bytes), protected by `IMfaSecretProtector`; a **pending** method gets it in place (`RestartSetup`: new secret, label and `CreatedAt`, the same id), otherwise `UserMfaMethod.StartTotp` adds a new pending one; the label is trimmed and defaults to `Authenticator app`. Audit `auth.mfa_setup_started`; save with `SaveChangesUnlessDuplicateAsync(UniqueIndexNames.MfaMethodPerUserAndType)`. The secret's bytes are zeroed after the answer is built.
5. 200 `{ methodId, secret: Base32.Encode(secret), otpAuthUri: TotpUri.Build(Auth:Mfa:Issuer, user.Email, secret) }`.

A setup changes no stamp and no session; a pending method protects nothing (login, step-up and the verifier look at confirmed methods only). When two setups of a user without a method run at once, the unique index refuses the second insert and nothing of it is saved; that request then loads the row the first one inserted and restarts it with its own secret, so every 200 shows a secret that was stored at the time, never a 500 (`Simultaneous_setups_store_one_method_whose_secret_one_of_them_shows`). Of those two first setups only the later secret stays, so the app scanned from the earlier answer cannot confirm; the user starts again (a known limit).

**Races on the method row.** `SecretEncrypted` and `ConfirmedAt` are EF Core **concurrency tokens** of `UserMfaMethod` (no schema change: EF adds their loaded values to the `WHERE` of every `UPDATE` or `DELETE` of a tracked method). So a save that changes a method another request changed since it was loaded throws `DbUpdateConcurrencyException`, answered 409 `concurrency.conflict`, and saves nothing; the request that committed first stands:

- **A confirm and a setup restart.** If the restart commits first, the confirm (which verified its code against the old secret) is 409, and the restarted setup stays pending: a secret nobody verified is never confirmed (`Confirm_racing_a_setup_restart_that_commits_first_is_a_conflict`; `MfaPersistenceTests.Confirm_of_a_secret_a_restart_replaced_meanwhile_is_a_concurrency_conflict`). If the confirm commits first, the restart (which loaded the method while it was pending, so `RestartSetup`'s guard cannot see the confirm) is 409, and two-step verification stays on with the confirmed secret. Without the token the restart would have replaced the secret of an enabled method behind the MFA step-up rule (`Setup_restart_racing_a_confirm_that_commits_first_is_a_conflict`; `Restart_of_a_method_a_confirm_turned_on_meanwhile_is_a_concurrency_conflict`).
- **Two restarts of a pending setup.** The later save is 409; the earlier answer's secret is the stored one.

The tests interleave the two requests deterministically: a save interceptor in a derived test host holds the first request just before its SQL until the other request has finished. `TryClaimTimeStepAsync` is a conditional `UPDATE` outside the change tracker, so the tokens do not affect it (and `LastUsedTimeStep` is not one). **Every new writer of `UserMfaMethods` through the change tracker gets the same check; keep both tokens.** The removal of a method is one such writer ([Managing MFA](#managing-mfa)).

**`POST /api/v1/auth/mfa/totp/confirm`** (`ConfirmTotpCommandHandler`, `Application/Mfa/ConfirmTotp/`; `.RequireAuthorization()`, `.WithNoStore()`). `ConfirmTotpCommandValidator` first: `code` is exactly 6 ASCII digits. Then:

1. **Step-up** (`Check(hasConfirmedMfa: false)`: the account has no confirmed method until this succeeds) and **the caller and the session**, as for setup. The session check matters more here: the kept session adopts the new stamp, so an ended session is never revived.
2. No method, or one that is already confirmed, is 409 `auth.mfa_setup_not_pending`. So is a pending secret that can no longer be read (a key-ring loss since the setup), which also logs one Error line with the method id only: the user starts the setup again.
3. `Totp.FindMatchingStep(secret, code, now, lastUsedTimeStep: null)` (the current step and one either side); no match is 400 `auth.invalid_mfa_code`, **not counted toward `Auth:Lockout`**: the caller created this secret a moment ago and has just proved a fresh identity, so a wrong code guesses nothing of value (a typo or a slow phone clock is the usual cause). Nothing is saved or audited.
4. `UserMfaMethod.Confirm(step, now)` sets `ConfirmedAt`, `LastUsedAt` and **`LastUsedTimeStep` to the matched step**, so the code used to confirm cannot then step up or sign in in the same step (D3; the integration test tries it and gets `auth.invalid_mfa_code`).
5. `RecoveryCodeIssuer.ReplaceAsync(userId, now)` stages the removal of every existing code of the user and ten new ones (hash only) and returns their display forms.
6. `MfaChangeEffects.ApplyAsync(user, MfaChange.Enabled, currentSessionId, SessionRevokedReason.MfaChanged, now)`: `User.ChangeMfa` rotates the security stamp and raises `MfaChangedDomainEvent(Enabled)`; every other active session of the user is revoked with `MfaChanged` (its refresh token answers `auth.invalid_refresh_token` from now on) and the current one adopts the new stamp and stays signed in, as after a password change. The new stamp also ends any pending sign-in challenge and remembered device (both are bound to the stamp). It returns the number revoked.
7. Audit `auth.mfa_enabled` with `{"revokedSessionCount":n}`; **one save** commits the method, the codes, the stamp, the sessions, the audit row and the outbox row; 200 `{ recoveryCodes }`.

The save writes the user row, whose `RowVersion` serializes MFA changes (D20), and the method row, whose tokens guard it ([Races on the method row](#enrollment)): of two confirms at the same moment one wins and the other is 409 `concurrency.conflict` (or `auth.mfa_setup_not_pending` when it loaded the method after the first committed), never a second set of codes or a 500 (`Simultaneous_confirms_enable_once_and_never_fail_with_a_500`, with the first confirm held before its save until the second has committed). The access token of the current session keeps its `amr` (`pwd` after a password sign-in) and its old stamp claim; the next sensitive action of this now-MFA account needs a step-up with a code (`StepUpPolicy.Check(true)`).

**`GET /api/v1/auth/mfa/methods`** (`GetMfaMethodsQueryHandler`, `Application/Mfa/GetMethods/`; `.RequireAuthorization()`). Dapper, two statements in one round trip, each filtered by the caller's `UserId` in SQL: the methods (never `SecretEncrypted`) and the count of unused recovery codes. `enabled` is true when a confirmed method exists (a pending setup does not count). A user has at most one method (one per type, D18), so the list is **not paged**, an exception to the cursor-pagination rule. The instants are UTC.

`RecoveryCodeIssuer` and `MfaChangeEffects` (`Application/Mfa/`, scoped) are shared with the removal, regeneration and administrator-reset handlers (`ResetUserMfaCommandHandler`): every MFA change rotates the stamp and treats the sessions through `MfaChangeEffects`, with the session to keep (or none) and the revocation reason as arguments. `CallerSession.ResolveAsync` (`Application/Mfa/`, a static method) is the one fail-closed lookup of the caller's user and session that step-up, setup, confirm, removal and regeneration share.

### Managing MFA

Turning two-step verification off and replacing the recovery codes are the sensitive MFA actions that follow enrollment (plan decisions D5, D11, D12 and D13). Both need a fresh step-up **with a code**: `StepUpPolicy.Check(hasConfirmedMfa: true)` wants an `auth_time` younger than `Auth:StepUp:MaxAge` and an `amr` of `otp` or `rcvr`, so a password (a fresh sign-in, or a password step-up, which an MFA account is not even offered) is refused with 403 `auth.step_up_required` (`MfaManagementTests.Disable_with_a_password_step_up_is_refused`, `Disable_after_the_step_up_has_aged_out_is_refused`). The client's flow: `POST /api/v1/auth/step-up` with `{ code }` (or `{ recoveryCode }`), then the call below with the new access token.

**`DELETE /api/v1/auth/mfa/methods/{id:guid}`** (`RemoveMfaMethodCommandHandler`, `Application/Mfa/RemoveMethod/`; `.RequireAuthorization()`, no body). In this order:

1. **The caller and the session** (`CallerSession.ResolveAsync`), as for setup: otherwise the body-less 401 `http.401`.
2. **The method, scoped to the caller** (`IMfaMethodRepository.GetForUserAsync(id, userId)`): an unknown id and another user's id are the same 404 `auth.mfa_method_not_found` with the same body (the requested id aside), whatever the caller has proved, so the answer never tells that a method exists (`Another_users_method_and_an_unknown_one_get_the_same_404_whatever_the_step_up`). The step-up is checked only after this lookup, so a foreign id is a 404 even without a step-up.
3. **A pending method** (a setup nobody confirmed) protects nothing: it is removed and **nothing else changes**: no step-up, no new stamp, no revoked session, no recovery code touched, no audit row (`Removing_a_pending_method_needs_no_step_up_and_changes_nothing_else`). It is how a user cancels a setup, and how a lost QR code is dropped.
4. **A confirmed method** needs the step-up (403 `auth.step_up_required`; nothing is changed). Then the method and **every recovery code** are removed (no code outlives two-step verification), `MfaChangeEffects.ApplyAsync(user, MfaChange.Disabled, currentSessionId, SessionRevokedReason.MfaChanged, now)` rotates the security stamp (`MfaChangedDomainEvent(Disabled)`), revokes every other active session and keeps this one with the new stamp, and `auth.mfa_disabled` is audited with `{"revokedSessionCount":n}`. **One save** commits all of it; 204.

From then on the account is password-only: login answers tokens without a challenge (`Disable_with_a_fresh_totp_step_up_turns_mfa_off_and_login_no_longer_challenges`), the pending challenges and the trusted devices of the old stamp are dead with it ([Trusted devices](#trusted-devices)), and removing the same id again is a 404.

**Lost device.** A user without the phone steps up with a recovery code instead: `POST /api/v1/auth/step-up` with `{ recoveryCode }` (any spelling, [Recovery codes](#totp-and-recovery-codes)) answers a token whose `amr` is `rcvr`, which satisfies the rule, and the same `DELETE` then turns two-step verification off (`Lost_device_user_steps_up_with_a_recovery_code_and_disables_mfa`). The user can then set up a new authenticator. A user with neither the device nor a recovery code needs the administrator's MFA reset ([User administration](#user-administration)).

**`POST /api/v1/auth/mfa/recovery-codes/regenerate`** (`RegenerateRecoveryCodesCommandHandler`, `Application/Mfa/RegenerateRecoveryCodes/`; `.RequireAuthorization()`, `.WithNoStore()`, no body). In this order: the caller and the session; **no confirmed method** is 409 `auth.mfa_not_enabled`, answered before the step-up because an account without two-step verification could never satisfy it; the step-up (403); `RecoveryCodeIssuer.ReplaceAsync` removes every existing code, used or not, and stages ten new ones (hash only); `MfaChangeEffects.ApplyAsync(user, MfaChange.RecoveryCodesRegenerated, currentSessionId, SessionRevokedReason.MfaChanged, now)`; audit `auth.recovery_codes_regenerated` with `{"revokedSessionCount":n}`; one save; 200 `{ recoveryCodes }`. Every old code stops working at once (`Old_recovery_codes_stop_working_after_regeneration`), and, as after enabling, the stamp rotates: every other session ends and this one stays (`Regeneration_ends_other_sessions_and_keeps_this_one`). The same rule forgets this user's remembered devices and pending challenges (D13: the stamp is the single revocation rule). The codes are shown once and never stored in clear, logged or audited, as after the confirm (`Regenerated_codes_are_shown_once_and_never_stored_or_logged` scans every text column and every log line).

**Concurrency.** The removal deletes the tracked method, so its concurrency tokens (the secret and `ConfirmedAt`, [Enrollment](#enrollment)) apply to the `DELETE`: a removal that loaded a pending method which a simultaneous confirm turned on cannot delete it without the step-up it skipped, and a second removal of a method already deleted finds no row; both answer 409 `concurrency.conflict` and change nothing (`MfaPersistenceTests.Removal_of_a_pending_method_a_confirm_turned_on_meanwhile_is_a_concurrency_conflict` and `Removal_of_a_method_another_removal_deleted_meanwhile_is_a_concurrency_conflict`). The removal of a confirmed method and the regeneration also write the user row, whose `RowVersion` serializes them against every other MFA change. A client that gets 409 reads `GET /api/v1/auth/mfa/methods` and decides again.

**Change password** of an MFA account follows the same rule ([Passwords](#passwords)). Neither route here counts a failure toward the lockout: the step-up route is where wrong codes are counted ([Step-up](#step-up)).

### Challenge and verify

An account with a confirmed method signs in in two steps (plan decisions D6 to D9 and D19, ADR 0024): the password at `POST /api/v1/auth/login` answers a **challenge** instead of tokens, and `POST /api/v1/auth/mfa/verify` trades the challenge and a code for the tokens.

```mermaid
sequenceDiagram
    autonumber
    participant C as Client
    participant L as POST /auth/login
    participant V as POST /auth/mfa/verify
    participant DB as auth schema
    C->>L: email, password, deviceName
    L->>DB: user by email, one password verification
    Note over L: wrong, unknown or locked: 401 auth.invalid_credentials<br/>(nothing two-step read yet)
    L->>DB: HasConfirmedAsync(user)
    L->>DB: insert MfaChallenge (token hash, stamp, device, expiry)
    L-->>C: 200 { mfaRequired: true, challengeToken, challengeExpiresAt, methods }
    C->>V: challengeToken, code or recoveryCode
    V->>DB: challenge by token hash, its user
    Note over V: unusable challenge or account: 400 auth.invalid_mfa_challenge<br/>(nothing counted)
    V->>DB: claim the code (time step or recovery code)
    alt wrong code
        V->>DB: FailedAttempts + 1, AccessFailedCount + 1 (atomic)
        V-->>C: 400 auth.invalid_mfa_code
    else right code
        V->>DB: consume the challenge (conditional UPDATE)
        V->>DB: session (amr pwd otp mfa or pwd rcvr mfa), failures reset
        V-->>C: 200 { accessToken, refreshToken, sessionId, ... }
    end
```

**The challenge.** A token from `ISecureTokenService.Generate()` (32 random bytes, 43 base64url characters), shown once in the login answer; `auth.MfaChallenges` keeps only its SHA-256, the user, a snapshot of the user's security stamp, the device name, `ExpiresAt` (`Auth:Mfa:ChallengeLifetime`, 5 minutes), `ConsumedAt` and `FailedAttempts`. Only the verify route looks it up: it is not a JWT, so the bearer handler refuses it (401 `http.401`), and it is no refresh token, so the refresh route refuses it (401 `auth.invalid_refresh_token`); a refresh token presented as a challenge is `auth.invalid_mfa_challenge` (`MfaLoginTests.Challenge_token_as_bearer_or_refresh_token_is_refused`, `Refresh_token_as_challenge_is_invalid_challenge`). A rotation of the stamp (a password change or reset, an MFA change, an administrator's lock) ends every open challenge of the user.

**`POST /api/v1/auth/mfa/verify`** (`VerifyMfaCommandHandler`, `Application/Mfa/Verify/`; `.AllowAnonymous()`, `auth-strict`, `.WithNoStore()`). `VerifyMfaCommandValidator` first: `challengeToken` not blank and at most 256 characters; exactly one of `code` and `recoveryCode` not blank (otherwise the error is under `proof`); `code` exactly 6 ASCII digits; `recoveryCode` at most 32 characters (its spelling is the verifier's business). A refused request reads and counts nothing. Then, in this order:

1. **The challenge and its user.** Hash the token, `GetByTokenHashAsync`, then the user (`GetByIdAsync`; a soft-deleted user is not found). A challenge that is unknown, consumed, expired (`now >= ExpiresAt`), exhausted (`Auth:Mfa:MaxChallengeAttempts` wrong codes) or bound to an older stamp (`MfaChallenge.CanUse`), and a user who is gone, cannot sign in (`EnsureCanSignIn`: suspended), is locked (`IsLockedOut(now)`) or has no confirmed method any more, are one answer: 400 `auth.invalid_mfa_challenge`, audited as `auth.mfa_failed`, saved. **Nothing is verified or counted**: no code is spent, and a dead challenge is no guess against the account.
2. **The factor:** `MfaFactorVerifier.VerifyAsync` ([Step-up](#step-up)), which spends a right code (claims the TOTP time step, or marks the recovery code used).
3. **A wrong code** (wrong, reused, older than the last used step, unreadable secret, wrong or used recovery code, or a claim lost to a simultaneous request): `IMfaChallengeRepository.RecordFailedAttemptAsync(challengeId)` **and** `IUserRepository.RecordFailedSignInAsync(...)`, each one atomic statement, both with no cancellation token; the failure that locks raises `UserLockedOutDomainEvent` (`NoteLockedOut`, which Plan 3 turns into the lockout email) and writes `auth.locked_out`; audit `auth.mfa_failed`; save; 400 `auth.invalid_mfa_code`.
4. **A right code:** `TryConsumeAsync(challengeId, now, MaxChallengeAttempts)` (one conditional `UPDATE`, no cancellation token). Lost (a simultaneous verify consumed it, or the cap or the expiry was reached meanwhile): 400 `auth.invalid_mfa_challenge`, and the code **stays spent**: the user signs in again with the next code.
5. **The session:** a recovery code also calls `User.NoteRecoveryCodeUsed()` (`MfaChangedDomainEvent` with `RecoveryCodeUsed`, no stamp change); `SessionStarter.StartAsync(user, "pwd otp mfa" or "pwd rcvr mfa", challenge.DeviceName, viaTrustedDevice: false, now)` resets the failure count (the verified second factor is the successful sign-in) and issues the access token with that `amr` and `auth_time` now (the session's `AuthMethods` and `AuthenticatedAt` hold the same, so a refresh keeps them); audit `auth.mfa_verified` (`{"factor":"totp"}` or `"recovery_code"`) and `auth.login_succeeded`, both with the session id; `TrySaveChangesAsync` with no cancellation token; 200.

**Guess limits, three layers (D7).**

- **Per challenge:** at most `Auth:Mfa:MaxChallengeAttempts` (5) wrong codes; the next try is `auth.invalid_mfa_challenge` before any code is looked at, even the right one, which is therefore not spent (`MfaLoginTests.Challenge_is_capped_at_five_wrong_codes`, on a host whose lockout threshold is 20).
- **Per user:** every wrong code counts in `Auth:Lockout` exactly like a wrong password, and the password step of an MFA account does **not** reset the count (`LoginCommandHandlerTests` and `MfaLoginTests.Password_step_does_not_reset_the_failure_count_of_an_mfa_account`). So "password, four wrong codes, password again" ends after five wrong codes in total, across any number of challenges and addresses: the account is locked for 15 minutes, the right password gets the generic 401, open challenges are dead, and the owner gets the lockout email (`MfaLoginTests.Wrong_codes_across_challenges_lock_the_account_after_five`).
- **Per client address:** `auth-strict` (`MfaLoginTests.Verify_is_anonymous_rate_limited_and_no_store`).

**Simultaneous and repeated codes.** A code claims its time step with one conditional `UPDATE`, and the challenge is consumed by another, so of two verifies with one code exactly one gets a session (`MfaLoginTests.Concurrent_verifies_with_one_code_succeed_once`, Review Focus 2). The other loses the code's claim, which counts as a wrong code on the user row; that update can land between the winner's read of the user and its save, so the winner's `TrySaveChangesAsync` would lose on `RowVersion`. The handler therefore **retries the success save once**, on the user read again, if that user still holds the challenge's stamp, may sign in and is not locked (the code and the challenge are already this request's); a second conflict is answered `auth.invalid_mfa_challenge` (the challenge is spent; the user signs in again). Without that retry both requests of a double tap failed in every run of the test. A code used once is refused on a later challenge (`Code_used_once_is_refused_on_a_second_challenge`), and so is an older code after a newer one (`Older_code_after_a_newer_one_is_refused`); both count as wrong codes. A recovery code works once in any spelling the normalization accepts (`Recovery_code_works_once_in_any_spelling`, Review Focus 4).

**Remember this device.** With `rememberDevice: true` a successful verify also remembers the device ([Trusted devices](#trusted-devices)); without it, or with `Auth:Mfa:TrustedDevicesEnabled` off, `MfaVerifyResponse.TrustedDeviceToken` and `TrustedDeviceExpiresAt` are null and left out of the JSON.

**Secrets.** The challenge token, the codes and the recovery codes appear in no audit row, metric tag or log line (`MfaLoginTests.Audit_and_metrics_never_contain_codes`, on a host whose only logger records every level). `VerifyMfaCommand`, `VerifyMfaRequest` and `MfaVerifyResponse` print only their type name, `LoginResult` its type name and `MfaRequired`.

### Trusted devices

A user who has verified a code on a device may ask to remember it, so the next sign-ins from that device need the password only (plan decisions D9, D11, D13 and D14, ADR 0025). The remembered device is a credential that replaces the code, so it is a hashed bearer token bound to the user and to the security stamp, like the challenge.

```mermaid
sequenceDiagram
    autonumber
    participant C as Client
    participant V as POST /auth/mfa/verify
    participant L as POST /auth/login
    participant DB as auth schema
    C->>V: challengeToken, code, rememberDevice: true
    V->>DB: session (amr pwd otp mfa) and TrustedDevice (token hash, stamp, expiry), one save
    V-->>C: 200 { tokens..., trustedDeviceToken, trustedDeviceExpiresAt }
    Note over C: stores the device token securely (30 days)
    C->>L: email, password, trustedDeviceToken
    L->>DB: user, one password verification, HasConfirmedAsync
    L->>DB: device by token hash
    alt this user's device, not revoked, not expired, same stamp
        L->>DB: LastUsedAt, session (amr pwd)
        L-->>C: 200 { mfaRequired: false, tokens... }
    else anything else, or Auth:Mfa:TrustedDevicesEnabled off
        L->>DB: insert MfaChallenge
        L-->>C: 200 { mfaRequired: true, challengeToken, ... } (as without a token)
    end
```

**Remembering** (`VerifyMfaCommandHandler`, step 5 of [Challenge and verify](#challenge-and-verify)). With `rememberDevice: true` and `Auth:Mfa:TrustedDevicesEnabled` on (the default), after `SessionStarter` (which does not rotate the stamp) and in the same save as the session: a token from `ISecureTokenService.Generate()` (43 base64url characters), `TrustedDevice.Trust(userId, tokenHash, challenge.DeviceName, userAgent, user.SecurityStamp, Auth:Mfa:TrustedDeviceLifetime, now)` (only the SHA-256 is stored; the device name and user agent are cut to their columns), and the audit `auth.trusted_device_added` with the device id and the session id. The answer adds `trustedDeviceToken` and `trustedDeviceExpiresAt` (`now + 30 days`), shown only there (`TrustedDeviceTests.Remembered_device_signs_in_without_a_code_for_thirty_days`). A failed verify remembers nothing. A save retried after a double tap ([Challenge and verify](#challenge-and-verify)) stages a fresh device, so only the saved one's token is answered.

**Using it** (`LoginCommandHandler`, step 8 of [Login and current user](#login-and-current-user)). The client sends the token as `trustedDeviceToken` with the email and the password. It is looked at **only** for an account with a confirmed method, after the password is verified and the account may sign in (a wrong password, an unknown email or a locked, suspended or unconfirmed account answers as always and never hashes the token, `LoginCommandHandlerTests.Trusted_device_check_happens_only_after_a_correct_password`), and only while the switch is on. The device must belong to this user and be usable (`TrustedDevice.IsUsable`: not revoked, `now < ExpiresAt`, its stamp snapshot equal to the user's stamp, ordinal). Then the device's `LastUsedAt` is set (its expiry stays absolute) and the session starts like a password-only sign-in: `amr` `pwd`, `auth_time` now, the failure count reset, `auth.login_succeeded` with `{"trustedDeviceId":"..."}`. **Every other case is the challenge, exactly as without a token**: an unknown token, an expired, revoked or stale-stamp device, another user's device (`Device_of_another_user_is_ignored`), or the switch off; the answer, the audit row and the metric say nothing about the token (`LoginCommandHandlerTests.Unusable_or_foreign_device_token_gets_the_normal_challenge`). A password-only account ignores the token (there is no challenge to skip). The expiry is exact: at `+30 days - 1 s` the device signs in without a code, at `+30 days` it gets the challenge.

**Not a step-up** (D9). A session started through a device proved the password now and a code some time ago, so its `amr` is `pwd` and it never satisfies an MFA step-up ([Step-up](#step-up)): turning MFA off, regenerating codes and changing the password still answer 403 `auth.step_up_required` until the user steps up with a code (`TrustedDeviceTests.Trusted_device_session_does_not_satisfy_an_mfa_step_up`).

**Forgetting.** Every rotation of the security stamp forgets **every** device of the user, with no revocation call (D13): a password change (`Password_change_forgets_every_device`) or reset, enabling or disabling MFA, regenerating recovery codes, a suspension by an administrator (even when lifted again) and the administrator's MFA reset (`Password_reset_mfa_change_and_suspension_forget_every_device`, `AdminMfaTests.Reset_forgets_trusted_devices_and_pending_challenges`). One device at a time: **`DELETE /api/v1/auth/trusted-devices/{id:guid}`** (`RevokeTrustedDeviceCommandHandler`, `Application/TrustedDevices/Revoke/`; `.RequireAuthorization()`, no step-up, D11): the device is looked up scoped to the caller (`ITrustedDeviceRepository.GetForUserAsync`), so an unknown id and another user's device are the same 404 `auth.trusted_device_not_found`; a device already revoked is 204 with nothing changed; otherwise `Revoke(now)`, audit `auth.trusted_device_revoked` with the device id and the caller's session id, saved with no cancellation token; 204 (`Revoke_stops_the_device_and_is_404_for_others`). Two requests revoking one device at the same moment can both pass the "already revoked" check (it is a read, not a conditional update) and both write an audit row; the stored revocation time is the later save's. **Revoking a device does not end the sessions started through it.** It only stops the device from skipping the challenge next time: the sessions and refresh tokens that were started through it stay valid until they expire or are revoked, because no link records which session came through which device. A client that wants to sign the device out as well also offers `DELETE /api/v1/auth/sessions/{id}` (a session of the same device can be recognised in `GET /api/v1/auth/sessions` by its device name and user agent), or `POST /api/v1/auth/logout-all`.

**`GET /api/v1/auth/trusted-devices`** (`ListTrustedDevicesQueryHandler`, `Application/TrustedDevices/List/`; `.RequireAuthorization()`, Dapper). Paging follows ADR 0010: the only sort is `createdAt` (default `-createdAt`) with `Id` as the tie-breaker, served by `IX_TrustedDevices_UserId_CreatedAt_Id`; the cursor is bound to the caller (`pagination.cursor_mismatch` for anyone else's). The SQL itself writes the rules of `IsUsable`: the caller's rows, `RevokedAt IS NULL`, `ExpiresAt > @Now` and the device's stamp equal to `auth.Users.SecurityStamp` (binary collation), so the list shows exactly the devices that can still skip the challenge; the rows of forgotten devices stay until `AuthTrustedDevicesCleanup` deletes them ([Cleanup](#cleanup)) but are never listed (`List_shows_only_my_usable_devices_paged_by_cursor`, `Revoked_expired_and_stale_stamp_devices_are_not_listed`, which writes the rows straight to the table). Each item is `{ id, deviceName, userAgent, createdAt, expiresAt, lastUsedAt }`.

**The switch.** `Auth:Mfa:TrustedDevicesEnabled` off: verify remembers nothing (`rememberDevice` is ignored) and login ignores every token. Existing rows stay listable and revocable, and work again if the switch is turned back on within their lifetime and stamp (`Switch_off_ignores_tokens_and_remember_device`, unit, for both handlers).

**Secrets.** The device token appears only in the verify answer and the login body: never in a column (only `TokenHash`), an audit row, a log line or a metric tag (`TrustedDeviceTests.Device_token_is_never_logged_or_audited` scans every text column of the test database and every log line of every level). `LoginCommand`, `LoginRequest` and `MfaVerifyResponse` print only their type name (`LoginResult` its type name and `MfaRequired`).

**Clients.** The token is a 30-day credential that replaces the code: a native app keeps it in the platform's secure storage (Keychain, Keystore); a browser SPA has only its own storage, where injected script can read it (a cookie variant comes with the backend-for-frontend). A stolen token alone signs in nobody: it still needs the password.

### Administration

An administrator with `auth.user.reset_mfa` removes the second factor of a user who lost the authenticator **and** every recovery code: `POST /api/v1/admin/auth/users/{id}/reset-mfa` ([User administration](#user-administration) has the order of the checks). It deletes the method and every recovery code, rotates the security stamp (which kills the pending challenges and the trusted devices), ends every session of the user (`AdminRevoked`) and audits `auth.admin_mfa_reset`; the user then signs in with the password alone and sets up a new authenticator. It is refused on the caller themselves (400 `auth.cannot_reset_own_mfa`: use the self-service route), a SuperAdmin target needs a SuperAdmin actor, and a user without two-step verification answers 204 and changes nothing. `Admin` holds the permission by default. `GET /api/v1/admin/auth/users/{id}` shows `mfaEnabled`, so an administrator can tell whether a reset applies. That is all an administrator can do with a user's second factor: there is no route to set one up, confirm it or read a secret or a code.

### Notifications

Two-step verification causes two kinds of email, both sent by the Notifications module from Auth's integration events ([Events](#events), [notifications.md](notifications.md#auths-types)); Auth sends nothing itself. Both types are category `Security`, priority `Critical` (quiet hours never defer them), email only and mandatory, and are rendered in the recipient's saved language (`en`, `ms`, `zh-Hans`):

- **`auth.mfa_changed`** (from `MfaChangedIntegrationEvent`): one sentence per kind: two-step verification turned on (`Enabled`), turned off (`Disabled`), new recovery codes (`RecoveryCodesRegenerated`), turned off by an administrator (`ResetByAdmin`), or a recovery code used to sign in or step up (`RecoveryCodeUsed`). It says when (in the user's time zone) and tells the reader to reset the password and contact the administrator if it was not them. A sign-in or a step-up with a recovery code is a notice because it means the device was not at hand.
- **`auth.new_device_login`** (from `NewDeviceSignedInIntegrationEvent`): a successful sign-in, with the password alone or after a challenge but not through a trusted device, from a device none of the user's earlier sessions came from ([New device](#new-device)). It carries the time, the time zone and the address the server observed, and no text a client supplied.

Neither email, nor the events behind them, holds a secret, a code or a device name. `MfaFlowTests` pins the whole set for one user's life (five `auth.mfa_changed` emails and no new-device email, because every sign-in used the one device name), and `IntegrationEventPublishingTests` the events one by one.

### The decisions that shape behaviour

The plan's decisions (D1 to D20) are in the Plan 4 implementation plan; these are the ones a reader of the code or an API client will run into.

| Decision | What it means |
|---|---|
| D1, D18 | **Scope.** One TOTP authenticator per user, recovery codes, challenge, step-up, trusted devices, self-management, administrator reset and notifications. Email and SMS codes, magic links, passkeys, several authenticators, a role or tenant policy and step-up on admin actions are deferred ([Known limits](#known-limits)). Replacing a phone is: remove the method, then set up the new one. |
| D2, D3, D4, D5 | **TOTP and recovery codes.** No package: SHA-1, 6 digits, 30 seconds, one step either side, 20-byte secret. A code counts for a time step greater than the last one used (one conditional `UPDATE`), so the same code twice, and an older code after a newer one, fail. The secret is encrypted by an Auth-only Data Protection purpose, never by the shared one Notifications can read. Ten recovery codes of 80 bits, stored as SHA-256, single use, regenerated as a whole set ([TOTP and recovery codes](#totp-and-recovery-codes)). |
| D6, D7, D19 | **The challenge.** An opaque token over a hashed row, valid 5 minutes and for one purpose. Three guess limits: `auth-strict` per client address, 5 wrong codes per challenge, and every wrong code counts in the account's lockout (the password step never resets it). Wrong codes and dead challenges are 400, never 401, so a client asks for a new code instead of refreshing its token. |
| D8 | **Login answers 200 `LoginResult`.** `mfaRequired: false` with the tokens, or `mfaRequired: true` with `challengeToken`, `challengeExpiresAt` and `methods`. A client branches on `mfaRequired`. |
| D9, D10, D11, D12 | **Step-up** is a fresh `auth_time` in the access token (10 minutes, `Auth:StepUp:MaxAge`) and, for an MFA account, an `amr` of `otp` or `rcvr`. `amr` is `pwd` after a password, `pwd otp mfa` or `pwd rcvr mfa` after a challenge, and a step-up replaces it with what it proved. Setup, confirm, removing a method, regenerating codes and changing the password of an MFA account need it; an MFA account must prove a code, never a password; every wrong proof counts in the lockout. |
| D13 | **The security stamp is the one revocation rule.** Enabling, disabling, regenerating and the administrator's reset rotate it: pending challenges and trusted devices die at once, other sessions end (`MfaChanged`, or `AdminRevoked` for the reset) and the caller's session adopts the new stamp. A password change or reset and a suspension rotate it too. Signing in with a recovery code does not. |
| D14 | **Trusted devices** are opt-in at verify (`rememberDevice`), a hashed token returned once, valid 30 days absolute, bound to the user and the stamp, revocable one by one (a revocation stops the device only; sessions it already started stay valid). They skip the code, never the password, and their sessions never satisfy an MFA step-up. |
| D15, D16 | **Notifications** carry ids, kinds and server-observed values only ([Notifications](#notifications)). |
| D17 | **Administrator reset** exists because a user can lose the device and the codes ([Administration](#administration)). |
| D20 | **No `RowVersion` on the new tables.** The user row serializes MFA changes; counters and single-use flags change only through conditional `UPDATE`s, and the tracked writes of a method are guarded by two concurrency tokens ([Data](#data)). |

### Recovering access

Two-step verification must never lock out the legitimate owner for good. Who can get back in, and how:

**A user who lost the phone but has a recovery code.** At `POST /api/v1/auth/login` the password answers a challenge as usual. Answer it at `POST /api/v1/auth/mfa/verify` with `{ challengeToken, recoveryCode }` (any spelling, [Recovery codes](#totp-and-recovery-codes)); the code is spent, the session's `amr` is `pwd rcvr mfa` and the owner gets an `auth.mfa_changed` email (`RecoveryCodeUsed`). That token already satisfies the step-up rule for `Auth:StepUp:MaxAge`; after that, `POST /api/v1/auth/step-up` with another `{ recoveryCode }` renews it. The user then either:

- **removes the method** with `DELETE /api/v1/auth/mfa/methods/{id}` (two-step verification is off, every remaining code deleted, and the password alone signs in), then sets up a new authenticator from a fresh step-up with the password; or
- **replaces the codes** with `POST /api/v1/auth/mfa/recovery-codes/regenerate` if the phone is only mislaid (this needs a step-up with a code, so a recovery-code step-up serves) and keeps the method.

The tests are `MfaLoginTests.Recovery_code_works_once_in_any_spelling`, `MfaManagementTests.Lost_device_user_steps_up_with_a_recovery_code_and_disables_mfa` and `MfaFlowTests.Enroll_sign_in_step_up_trust_and_recover`. A user should keep the codes somewhere other than the phone and regenerate them once few are left (`GET /api/v1/auth/mfa/methods` shows `recoveryCodesRemaining`).

**A user with neither the device nor a recovery code.** An administrator resets their two-step verification ([Administration](#administration)): `POST /api/v1/admin/auth/users/{id}/reset-mfa`. The user is signed out everywhere, signs in with the password alone and sets up again. An administrator who is the one locked out needs another administrator (the route refuses oneself); if none is left, the way back is a database edit or a new seed account ([Known limits](#known-limits)).

**The Data Protection key ring is lost or replaced.** TOTP secrets are encrypted with the key ring in `auth.DataProtectionKeys` (an Auth-only purpose, ADR 0022). If the table is emptied, restored from a backup that predates the keys, or read with another `Auth:DataProtection:ApplicationName`, **every stored TOTP secret becomes unreadable**. What happens:

- Every TOTP code fails with 400 `auth.invalid_mfa_code`, at sign-in and at step-up, and the server logs one Error line per attempt: `Could not read the TOTP secret of MFA method {MethodId}` (the method id only). Those failures **count toward the lockout**, so users who keep typing codes lock themselves out for 15 minutes; tell them to use a recovery code.
- **Recovery codes still work**, because they are stored as hashes and need no key. The user signs in with one and removes the method and sets up a new authenticator as above; the new secret is protected with the new ring.
- Everyone who has no recovery code left needs an administrator's reset, which also reads no secret. After a total loss that is every enrolled user who cannot use a recovery code.
- A setup that was pending when the ring was lost cannot be confirmed (409 `auth.mfa_setup_not_pending`, with the same Error line): the user starts the setup again.
- Trusted devices, challenges, sessions and recovery codes are hashes and keep working. Links in the outbox that were encrypted with the old ring (ADR 0017) are lost too, which is a notifications problem rather than a sign-in one.

**Prevent it:** the ring is stored in the application database, so the ordinary database backup holds it. Back the database up as a whole and restore it as a whole; never truncate `auth.DataProtectionKeys` or restore the rest of the schema without it, and keep `Auth:DataProtection:ApplicationName` fixed. The ring is not encrypted at rest until Plan 6 (ADR 0017), so treat a database backup like the secrets it contains. A runbook for both incidents follows in Plan 6.

## Security services

<!-- The services that hash, generate, protect and check secrets. -->

The abstractions are `internal` in `Application/Abstractions/` (the application layer does not depend on the infrastructure); the implementations are `internal sealed` in `Infrastructure/Security/`. All are registered as singletons by `AddAuthModule` (`IMfaSecretProtector` through its `AddMfa` step), except `ISecretProtector`, which `AddInfrastructureCommon` registers.

| Service | Implementation | What it does |
|---|---|---|
| `IPasswordHasher` | `Pbkdf2PasswordHasher` | `Hash` makes a PBKDF2 hash with a random salt through the Identity `PasswordHasher` (ADR 0014). `Verify` returns `PasswordVerification.Failed`, `Success` or `SuccessRehashNeeded` (the hash used a lower iteration count than today's, so the caller stores a new hash); a malformed hash is `Failed`, never an exception. `SpendVerificationCost` verifies against a dummy hash made once on first use, so the unknown-account path costs the same as a wrong password. An empty stored hash (a user created by an administrator, who has no password yet) and a stored value that is not base64 do the same dummy verification before answering `Failed`, so no stored state answers faster than a wrong password. |
| `ISecureTokenService` | `SecureTokenService` | `Generate` returns a `GeneratedToken(Value, Hash)`: 32 bytes from `RandomNumberGenerator`, base64url without padding (43 characters), and its hash. `Hash` is the SHA-256 of the token's UTF-8 bytes (32 bytes), the form stored in `varbinary(32)` columns and used for lookups. |
| `IBreachedPasswordChecker` | `HibpBreachedPasswordChecker` | `IsBreachedAsync` asks Have I Been Pwned with k-anonymity: it requests `https://api.pwnedpasswords.com/range/{first 5 hex characters of the uppercase SHA-1}` with `Add-Padding: true` and looks for the suffix itself; padding rows (count 0) are ignored. It uses the named client `hibp`, registered with `AddExternalHttpClient` on the **`hibp` resilience pipeline** ([ADR 0029](../adr/0029-standard-http-resilience-pipelines.md), [infrastructure-common](../building-blocks/infrastructure-common.md#http-resilience)): an attempt of 1 second, one retry after a short jittered delay (about 0.2 s) for a 5xx, 408, 429, a network error or an attempt timeout (any other 4xx is final), 2 seconds in all, and a circuit breaker that opens when half of the last 30 seconds of attempts (at least 10) failed and then rejects every check for 30 seconds without a request. The settings are `Resilience:Pipelines:hibp:*` ([api](../services/api.md#resilience)). The whole lookup (request, headers and reading the body) keeps its own budget of 2 seconds (`HibpBreachedPasswordChecker.RequestBudget`), the same as the pipeline total and the outer limit of the check, and the body is capped at 1 MB (a padded answer is some 40 KB); the client has no timeout of its own, so nothing outlives the 2 seconds. It is **fail-open**: a non-success status, the budget or the pipeline timeout running out, an **open breaker** (no request is sent), a body over the cap or any transport error logs a warning (status code, exception type or the cap only, never the password, hash or prefix) and answers `false`. A cancelled caller token is not a failure and propagates. With `Auth:Password:CheckBreached` off it makes no request. |
| `ISecretProtector` | `DataProtectionSecretProtector` | Not an Auth type: it lives in the building blocks (`TemplateName.Application.Common.Security`; implementation and registration in [Infrastructure.Common](../building-blocks/infrastructure-common.md)) so that another module can unprotect what Auth protects. `Protect` and `Unprotect` encrypt a secret that must leave the process, with the Data Protection purpose `TemplateName.Secrets.v1` (ADR 0017). The same value protected twice differs; a changed value throws `CryptographicException`. Auth keeps the key ring: `AddAuthModule` sets the application name and stores the keys in `auth.DataProtectionKeys`. The purpose was `TemplateName.Auth.Secrets.v1` before it moved, so a value protected under the old purpose (a pending outbox message in a developer database) can no longer be read; nothing was released with the old purpose. |
| `IMfaSecretProtector` | `DataProtectionMfaSecretProtector` | Encrypts the TOTP secret of an authenticator app for `auth.UserMfaMethods.SecretEncrypted`: `Protect(ReadOnlySpan<byte>)` returns base64url text (about 155 characters for a 20-byte secret with the default algorithms, within the column's 512), `Unprotect(string)` returns the bytes. It has a Data Protection purpose of its own, **`TemplateName.Auth.MfaSecrets.v1`** (plan decision D4), not the shared `TemplateName.Secrets.v1`: other modules can read what the shared purpose protects (ADR 0020), and a TOTP secret must be readable by Auth only. Each purpose refuses the other's values (`MfaSecretProtectorTests.Purpose_is_isolated_from_the_shared_secret_protector`). The same secret protected twice differs; a changed value, text that is not base64url, a value of another purpose and a value whose key is not in the ring all throw `CryptographicException` (never `FormatException`). It uses the same key ring, `auth.DataProtectionKeys`: **losing the ring makes every stored TOTP secret unreadable**, so back the table up with the database (plan Part A5); the ring is not encrypted at rest until Plan 6 (ADR 0017), so a full database dump exposes the secrets (known limit). Changing the purpose string would turn off every authenticator app. The copy of the secret it encrypts is zeroed after use. |

### Access tokens

`IAccessTokenIssuer` (`Application/Abstractions/`) issues the access token: `Issue(AccessTokenRequest(UserId, SessionId, SecurityStamp, AuthMethods, AuthTime, Locale))` returns `AccessToken(Value, ExpiresAt)`. `AccessTokenIssuer` (`Infrastructure/Tokens/`) signs it with `JsonWebTokenHandler`, ES256 only (ADR 0015), with the active key's `kid` in the header and the default `typ` (`JWT`). The times come from `TimeProvider`, truncated to whole seconds: `iat` = `nbf` = now, `exp` = now + `Auth:Jwt:AccessTokenLifetime`, and `ExpiresAt` is exactly the `exp` instant.

| Claim | Value |
|---|---|
| `sub` | The user id. |
| `sid` | The session id (`UserSession`). |
| `sst` | The session's snapshot of the user's security stamp. |
| `amr` | The session's authentication methods as a JSON array (`AuthMethods` split on spaces, for example `["pwd"]`): what the user proved at `auth_time`. |
| `auth_time` | When the user last proved their identity in the session (`UserSession.AuthenticatedAt`: the sign-in or the latest step-up; Unix seconds, a number), not when this token was issued. |
| `locale` | The user's saved language. |
| `jti` | A new random id per token. |
| `iat`, `nbf`, `exp`, `iss`, `aud` | Issue time, not-before, expiry, `Auth:Jwt:Issuer`, `Auth:Jwt:Audience`. |

There is no permission list, no email and no display name in the token (ADR 0016): permissions are resolved on the server.

**Validation.** `JwtValidation.CreateParameters(JwtOptions, ISigningKeyProvider, TimeProvider?)` is the one definition the bearer handler uses: the algorithm allow-list is exactly `ES256` (so `none`, `HS256` signed with the public key's bytes and every other algorithm fail), `iss` and `aud` must match, `exp` is required, `exp` and `nbf` are checked with `Auth:Jwt:ClockSkew`, and signed tokens are required. The signing key is looked up by the header's `kid` among the configured keys; an unknown or missing `kid` finds no key and fails, and other keys are never tried (`TryAllIssuerSigningKeys = false`). Lifetime is checked against the application's `TimeProvider` through a `LifetimeValidator` (IdentityModel's own clock setting is not public), so a test clock moves token expiry too. `AddAuthModule` registers the bearer handler as the default scheme (`AddAuthentication(JwtBearerDefaults.AuthenticationScheme).AddJwtBearer()`) with `MapInboundClaims = false`, so claims keep their names (`sub`, `sid`, ...); `sub` is the identity's name claim. Access tokens are not checked against session revocation per request (ADR 0015, D9).

**In the host.** `UseAuthentication` runs at pipeline slot 1a and `UseAuthorization` at 10, after the rate limiter at 9a ([API host](../services/api.md#pipeline)). A request without a valid token stays anonymous; every endpoint that does not say `.AllowAnonymous()` then answers 401 `http.401` (the fallback policy), whatever was wrong with the token: missing, malformed, `alg: none`, `HS256`, an unknown `kid`, a tampered payload, a wrong audience, expired. None of these reaches the exception handler or produces a 500. `ICurrentUser.UserId` and `ICurrentUser.SessionId` read the `sub` and `sid` claims, and the `locale` claim picks the response language ahead of `Accept-Language` (an unsupported value falls through to the header). Anonymous today: the health checks, OpenAPI, Scalar, `GET /.well-known/jwks.json` and the registration, login, refresh, forgot-password and reset-password routes under [Endpoints](#endpoints).

**Keys.** `ISigningKeyProvider` (`Infrastructure/Tokens/`, `SigningKeyProvider`: a singleton, also registered as a hosted service that does nothing, so the host builds it when it starts) loads `Auth:Jwt:SigningKeys` once, at start, with `ECDsa.ImportFromPem`. Every key must be EC P-256. The first entry with a `PrivateKeyPem` signs (`Active`); every entry, active or retired, validates (`ValidationKeys`) and is published (`PublicKeySet`), both through public-only copies, so neither can carry a private part. Start-up validation (`ValidateOnStart`) refuses: a missing or duplicate `KeyId`; an entry with neither PEM; a `PrivateKeyPem` that is not a `PRIVATE KEY` or `EC PRIVATE KEY` block (an encrypted key, a public key, an RSA key, text that is not PEM); a `PublicKeyPem` that is not a `PUBLIC KEY` block; any other curve (P-384, P-521, brainpool); a `PublicKeyPem` that does not match the `PrivateKeyPem` next to it; and a list with no private key. Every message names the entry (`Auth:Jwt:SigningKeys:{index}:PrivateKeyPem ...`) and never quotes key material. With **no** key configured, Development and Testing generate one ephemeral P-256 key at start (kid `ephemeral-{random}`) and log a warning; tokens it signed stop validating when the process restarts, and other instances do not accept them. Every other environment refuses to start with a message that names `Auth:Jwt:SigningKeys`.

**Generating a key.** Once per environment, on a trusted machine, and straight into the secret store, never into a file in the repository:

```bash
openssl ecparam -name prime256v1 -genkey -noout | openssl pkcs8 -topk8 -nocrypt
```

The output (`-----BEGIN PRIVATE KEY-----` ...) is the `PrivateKeyPem` of `Auth:Jwt:SigningKeys:0`; choose a `KeyId` that says when it was made (for example `2026-10`). Locally: `dotnet user-secrets set "Auth:Jwt:SigningKeys:0:KeyId" "2026-10" --project src/Host/TemplateName.Api`, and the same for `Auth:Jwt:SigningKeys:0:PrivateKeyPem`. As environment variables: `Auth__Jwt__SigningKeys__0__KeyId` and `Auth__Jwt__SigningKeys__0__PrivateKeyPem`; the PEM may lose its line breaks on the way (a one-line PEM is accepted). The public part, for a retired entry, is `openssl pkey -pubout` of the private key.

**Rotating.** Put the new key first (index 0, with its `PrivateKeyPem`) and move the old one to index 1 with only its `PublicKeyPem`, so it no longer signs but still validates and stays in the JWKS. Keep it for at least `AccessTokenLifetime + ClockSkew` (10 minutes 30 seconds by default), then remove it. Every instance must have the new list before any of them signs with the new key. When other services verify tokens through the JWKS (which they may cache for 5 minutes), publish the new key first: add it at the end of the list with its `PrivateKeyPem` (published, not yet signing, because an earlier entry has a private key), wait at least 5 minutes, then do the swap above.

### Links

Auth builds the links its emails carry; the Notifications module sends them. `LinksOptions` (`Application/Verification/`) turns the `Auth:Links` templates into links with `ConfirmEmailLink(token)` and `ResetPasswordLink(token)`, replacing `{token}` with the URL-encoded token; a template that is not an absolute `http` or `https` address holding `{token}` stops the host at start. The publishing handler encrypts the whole link before it leaves the module (ADR 0020), and the Notifications scheduler refuses one that does not decrypt to an absolute `http` or `https` URL with a host, no user info and at most 2048 characters. The SMTP settings, the transport and Mailpit are described in the [Notifications module](notifications.md#email-channel).

### Permission checks

Permissions are resolved on the server for every request (ADR 0016); the access token carries none. An endpoint asks for one with `.RequirePermission(code)` ([Web.Common](../building-blocks/web-common.md)), whose handler calls `IPermissionChecker.HasPermissionAsync(userId, code, cancellationToken)`.

- **Checker.** `PermissionChecker` (`Infrastructure/Authorization/`, one singleton registered as both `IPermissionChecker` and `IPermissionCache`) loads a user's effective codes with one Dapper query over `Users`, `UserRoles`, `Roles`, `RolePermissions` and `Permissions`: the user must be `Active` and not soft-deleted, the role not soft-deleted, and the permission not deprecated. Dapper bypasses the EF Core filters, so the query writes `IsDeleted = 0` itself (ADR 0006). The result is the union over all the user's roles. An unknown, suspended or soft-deleted user gets the empty set; a deprecated permission is never granted, even through an old grant. Codes are compared exactly (ordinal), so `AUTH.USER.VIEW` is not `auth.user.view`.
- **Cache.** The set is a sorted `string[]` in `HybridCache` under `auth:perm:{userId}` (`{module}:{entity}:{id}`), with `Expiration` and `LocalCacheExpiration` both 30 seconds (`PermissionCache.Lifetime`); a check is a binary search in it. The empty set is cached too. Where it lives follows `Caching:Provider` ([API host](../services/api.md#caching)): in memory per instance by default; with `redis` also in Redis (key `{Caching:Redis:InstanceName}auth:perm:{userId}`, so `TemplateName:auth:perm:{userId}`), where a set one instance loaded is served to the others without a database read, and with Redis down the checks read the database ([platform-redis](../building-blocks/platform-redis.md)); with `none` every check reads the database. `HybridCache` keeps its local entries in the shared `IMemoryCache`, whose clock `AddAuthModule` sets to the application's `TimeProvider` (`TimeProviderCacheClock`), so the 30 seconds follow the same clock as everything else (and a test clock moves them).
- **Reader.** The same singleton is `IPermissionReader`: `GetPermissionsAsync(userId, cancellationToken)` returns the cached set itself (sorted ordinally, read-only, empty for an unknown, suspended or soft-deleted user), so `GET /api/v1/auth/me` lists exactly what the checks allow and adds no query of its own.
- **Invalidation.** `IPermissionCache.InvalidateUsersAsync(userIds, cancellationToken)` removes each user's key (`HybridCache.RemoveAsync`), so the next check reloads. Every handler that changes a role's permissions or a user's role assignments must call it for the affected users after saving (`IRoleRepository.GetUserIdsInRoleAsync` lists a role's users). The seeder does not: it runs at start-up, before the instance serves requests, when its in-memory cache is empty.

**Security notes.**

- **Staleness across instances.** `RemoveAsync` clears Redis (with `Caching:Provider = redis`) and the local copy of the instance that runs it, not the local copies of the others. Every other instance keeps using the set it holds for up to 30 seconds, with or without Redis: a removed role or permission can still be used there for that long, and a new one may not work there yet (ADR 0016, ADR 0027; `RedisCacheTests.Invalidating_on_A_is_seen_by_B_after_the_thirty_second_L1_lifetime`). If 30 seconds is too long for a deployment, run one instance; pub/sub invalidation of the local copies is post-v1.
- **A load racing a change.** A check that started reading before a change was saved can store the old set just after the invalidation removed the key; that set then lives until its 30 seconds run out. The window is the length of one query.
- **Fail closed.** The handler grants nothing to an anonymous caller or a principal without a user id, and a database error while loading propagates (500) instead of granting. A deprecated permission, a soft-deleted role and a suspended or soft-deleted user grant nothing, whatever the grant rows say.
- **No permissions in the token.** A stolen access token is limited to what the user may do now, not what they could do when it was issued; a revoked session's token still works until it expires (ADR 0015, D9).

## Configuration

<!-- Configuration sections and keys the module reads, with defaults. -->

`AddAuthModule` receives the `IConfiguration`. `Auth:Password`, `Auth:Links`, `Auth:Verification`, `Auth:RefreshToken`, `Auth:Lockout`, `Auth:Mfa`, `Auth:StepUp`, `Auth:Retention` and `Auth:Jwt` are validated at start-up, so an out-of-range value, a negative retention or a bad signing key stops the host. `Auth:Seed` is checked when the seeder runs. Rules the repositories and the context keep:

- **Whole aggregates.** A user is loaded with its password history (oldest first, which `ChangePassword` relies on to drop the oldest) and its roles; a role with its grants; a session with **every** refresh token, used or not, because `Rotate` and `Revoke` are only correct over the whole chain (Ruling R7). `GetByRefreshTokenHashAsync` uses the token only to pick the session; the include is never filtered.
- **Claiming a refresh token.** `TryClaimRefreshTokenAsync` is one `UPDATE ... SET UsedAt = @now WHERE Id = @id AND UsedAt IS NULL AND RevokedAt IS NULL` (`ExecuteUpdateAsync`), true only for the caller whose statement changed the row. It bypasses the change tracker, so the refresh handler loads the session, claims, then rotates the instance it already holds; it never reloads after the claim. It commits on its own, before the handler's save. After a failed claim, `GetRefreshTokenStateAsync` reads the token's `UsedAt` and `RevokedAt` with an untracked projection (the held session keeps its in-memory state), so the handler can tell a used token (reuse) from one whose session was revoked meanwhile.
- **Consuming a verification code.** `IVerificationCodeRepository.TryConsumeAsync` is one `UPDATE ... SET ConsumedAt = @now WHERE Id = @id AND Purpose = @purpose AND ConsumedAt IS NULL AND InvalidatedAt IS NULL AND ExpiresAt > @now` (`ExecuteUpdateAsync`), the rule of `VerificationCode.CanConsume` (`AuthPersistenceTests.Try_consume_verification_code_follows_the_domain_rule`), true only for the caller whose statement changed the row (`Try_consume_verification_code_succeeds_for_exactly_one_of_two_concurrent_callers`). It bypasses the change tracker and commits on its own, before the handler's save; the confirm and reset handlers check the loaded code, claim it, then `Consume` the instance they hold. `VerificationCodes` has no concurrency token, so the later save of that instance (or a forgot that invalidates the same code at the same moment) cannot conflict.
- **Two-step verification claims.** Every counter or single-use flag of the MFA tables changes only through one conditional statement that commits on its own, outside the change tracker, so the database decides between simultaneous requests and none of them ends in a conflict or a 500 (D20: these tables have no `RowVersion`; the tracked writes of a method are guarded by its concurrency tokens instead, see [Enrollment](#enrollment)). A tracked instance keeps its old values, so a handler checks the loaded row, claims, and never reloads.
  - `IMfaMethodRepository.TryClaimTimeStepAsync(methodId, timeStep, now)`: `UPDATE ... SET LastUsedTimeStep = @step, LastUsedAt = @now WHERE Id = @id AND ConfirmedAt IS NOT NULL AND (LastUsedTimeStep IS NULL OR LastUsedTimeStep < @step)` (`ExecuteUpdateAsync`). True only for the caller whose statement changed the row: a code of a step already used, or older than the last used one, never counts twice, also when two verifies of one code arrive together (`MfaPersistenceTests.Try_claim_time_step_succeeds_for_exactly_one_of_two_concurrent_callers`); a pending method claims nothing (`Try_claim_time_step_refuses_an_equal_or_lower_step_and_a_pending_method`).
  - `IRecoveryCodeRepository.TryUseAsync(codeId, now)`: `UPDATE ... SET UsedAt = @now WHERE Id = @id AND UsedAt IS NULL`; one of two simultaneous uses wins (`Try_use_recovery_code_succeeds_once`). `FindUnusedAsync(userId, codeHash)` looks the typed code up by the unique `(UserId, CodeHash)` index; `ListByUserAsync` returns the whole set tracked, so a regeneration removes it and adds the new one in one save.
  - `IMfaChallengeRepository.RecordFailedAttemptAsync(challengeId)`: raw SQL `UPDATE ... SET FailedAttempts = FailedAttempts + 1 OUTPUT inserted.FailedAttempts WHERE Id = @id AND ConsumedAt IS NULL` (like `RecordFailedSignInAsync`), returning the new count, or null for an unknown or consumed challenge. Simultaneous wrong codes queue on the row lock and are all counted (`Failed_attempts_are_all_counted_when_concurrent`: ten at once give 10). The verify route calls it for every wrong code, next to `RecordFailedSignInAsync` ([Challenge and verify](#challenge-and-verify)); like that statement, a retry after a lost reply could count one failure twice, which errs toward the cap.
  - `IMfaChallengeRepository.TryConsumeAsync(challengeId, now, maxAttempts)`: `UPDATE ... SET ConsumedAt = @now WHERE Id = @id AND ConsumedAt IS NULL AND ExpiresAt > @now AND FailedAttempts < @max`, the rule of `MfaChallenge.CanUse` without the stamp, which the handler compares with the loaded user's (`Try_consume_challenge_follows_the_domain_rule`: expired, consumed, exhausted and valid answer as `CanUse` does).
  - The unique `IX_UserMfaMethods_UserId_Type` refuses a second method of a type for one user; the setup saves with `SaveChangesUnlessDuplicateAsync(UniqueIndexNames.MfaMethodPerUserAndType, ...)`, so of two simultaneous first setups the loser gets false instead of a 500 and takes the winner's pending row over ([Enrollment](#enrollment); `Second_totp_method_for_one_user_violates_the_unique_index`).
  - The TOTP secret is stored only as `IMfaSecretProtector` output: neither its base32, hex nor base64 form appears anywhere in the row (`Totp_secret_is_not_stored_in_plain_text`). Recovery codes and bearer tokens are stored only as SHA-256 hashes.
- **Sessions save without conflicts.** `UserSessions` and `RefreshTokens` have no `RowVersion`, so saving a session never raises a concurrency conflict: a rotation, a reuse revocation, a logout and a stamp revocation each write only the columns and rows they changed, in either order, and none undoes another (`AuthPersistenceTests.Winning_rotation_and_losing_reuse_revocation_both_persist_in_either_save_order`). The session row is the authority: once `RevokedAt` is set, every token of the session is refused, including one that a simultaneous winning refresh inserted after the loser loaded the chain (its own `RevokedAt` may stay null).
- **Soft delete keeps children.** Users and roles are soft-deleted by `SoftDeleteInterceptor` (a role's grants are the exception: `Role.MarkDeleted()` drops them first). The context cascades deletes at save time (`CascadeDeleteTiming = OnSaveChanges`), after the interceptor has turned the delete into an update, so a soft-deleted user keeps its history and assignments. Removing an item from a collection (`RemoveRole`, history trimming) still deletes that row.
- **Column lengths.** Every client-supplied value is cut before it reaches a bounded column, so a long `User-Agent` or an IPv6 address with a zone id never fails a save: `HttpClientContext` cuts to the `AuthAuditLog` limits, and `UserSession.Start`, `VerificationCode.Issue` and `AuthAuditLog.SetClientInfo` cut again to their own. The configurations take the lengths from these domain constants.
- **Seeded rows.** `auth.Roles` holds the three system roles (`IsSystem = 1`) and `auth.Permissions` one row per declared code, kept by the seeder (see [Background processing](#background-processing)). Permission rows are never deleted; a code no module declares any more has `IsDeprecated = 1`.
- **Counting failed sign-ins.** `IUserRepository.RecordFailedSignInAsync` is raw SQL on the context's connection (one `UPDATE ... OUTPUT`, retried by the execution strategy like any command), outside the change tracker. It implements `User.RecordFailedSignIn` (an equivalence test pins it), skips soft-deleted users and locked accounts, compares `LockoutEnd` with `@now` to the tick, and stamps `UpdatedAt` itself (`UpdatedBy` null: the caller is anonymous), because raw SQL skips the save interceptors; `RowVersion` changes as for any update. It commits on its own, before the handler's save: if that save then failed (a database error, so a 500), the count would stay and the audit row be lost, never the other way round.
- **Saving a new row without a 500.** `IUnitOfWork.SaveChangesUnlessDuplicateAsync(uniqueIndexName, ...)` saves like `SaveChangesAsync` but answers false when the named unique index refuses a row (SQL Server errors 2601 and 2627), after which the context drops its pending changes; nothing was saved. SQL Server quotes the index in its message (`... with unique index 'IX_Users_NormalizedEmail'`), whatever the language of the server, and the names are the constants of `UniqueIndexNames` (`UserEmail`, `RoleName`), which `UserConfiguration` and `RoleConfiguration` give the indexes. A violation of any other unique index is still thrown, so it cannot be mistaken for "this address (or role name) is taken" (`AuthPersistenceTests.Save_unless_duplicate_on_an_index_answers_false_only_for_that_index`, `Save_unless_duplicate_answers_false_when_the_unique_email_index_refuses_the_row_and_saves_nothing`). Self-registration and the administrator's create use it with `IX_Users_NormalizedEmail` (the loser answers like a known address, or 409 `auth.email_taken`), the role create and rename with `IX_Roles_NormalizedName`. EF Core still logs the refused command at Error level, with the duplicate key (the address, for the email index) in SQL Server's message.
- **Saving without a 409.** `IUnitOfWork.TrySaveChangesAsync` saves like `SaveChangesAsync` but answers false on an optimistic-concurrency conflict (`DbUpdateConcurrencyException`), after which the context drops its pending changes (`ChangeTracker.Clear`); nothing was saved. The successful login uses it, so a race on the user row cannot turn into a 409 that only an existing account can get.
- **Audit entries.** `IAuthAuditWriter.Record` fills `IpAddress`, `UserAgent` and `TraceId` from `IClientContext` (`HttpClientContext`: the address after the forwarded-headers middleware, the `User-Agent` header, and the trace id that `X-Trace-Id` also carries, each already cut to its audit column) and stages the entry; the handler's `SaveChangesAsync` saves it with the rest.

Migrations (`Infrastructure/Persistence/Migrations/`), in order:

1. `InitialAuth`: creates the schema and every table above.
2. `AddSessionListIndexes`: replaces `IX_UserSessions_UserId` with `(UserId, LastSeenAt, Id)` and `(UserId, CreatedAt, Id)`, one index per sort of the session list (review P7). Indexes only; no data changes.
3. `AddUserListIndexes`: adds `IX_Users_CreatedAt_Id` (filtered `[IsDeleted] = 0`) for the user list's `createdAt` sort (review P7); its `email` sort and prefix search use the existing `IX_Users_NormalizedEmail`. A `status` filter is applied to the rows these indexes return (two states, too few to index). Indexes only; no data changes.
4. `AddRoleAndAuditLogListIndexes`: adds `IX_Roles_CreatedAt_Id` (filtered `[IsDeleted] = 0`) for the role list's `createdAt` sort, and replaces `IX_AuthAuditLogs_UserId_OccurredAt` and `IX_AuthAuditLogs_EventType_OccurredAt` with `(UserId, OccurredAt, Id)` and `(EventType, OccurredAt, Id)` and adds `(OccurredAt, Id)`, one index per filter of the audit list ending in its sort (review P7). The columns are ascending because SQL Server reads an index backwards just as well. `succeeded`, `from` and `to` are applied to the rows these indexes return. Indexes only; no data changes.
5. `AddMultiFactorAuthentication`: creates `UserMfaMethods`, `RecoveryCodes`, `MfaChallenges` and `TrustedDevices` with their indexes and foreign keys (above), and adds `UserSessions.AuthenticatedAt`. That table holds live rows, so the column is added in three steps in the migration's transaction: `ADD [AuthenticatedAt] datetime2(3) NOT NULL` with a temporary default (`0001-01-01`), `UPDATE [auth].[UserSessions] SET [AuthenticatedAt] = [CreatedAt]` (every existing session counts as authenticated when it started), then the default constraint is dropped, so the column has no default, as in the model. The `UPDATE` touches every session row once (a short lock on a large table; run it in a quiet period). `MfaPersistenceTests.Migration_backfills_AuthenticatedAt_from_CreatedAt` checks the order of the three steps in the generated script, and `Upgrading_a_database_with_a_session_backfills_its_AuthenticatedAt` migrates a database of its own to migration 4, writes a session, upgrades it and reads `CreatedAt` back as `AuthenticatedAt`. `Down` drops the four tables and the column. **Rolling back this migration silently turns off two-step verification for every enrolled user** (the method rows are gone, so login answers tokens without a challenge) **and irreversibly destroys the TOTP secrets and the recovery codes**: users must set up again, and a restore from a backup is the only way back.
6. `AddCleanupIndexes`: adds the indexes the cleanup jobs delete by: `IX_VerificationCodes_ExpiresAt`, `IX_RefreshTokens_ExpiresAt`, `IX_UserSessions_ExpiresAt`, `IX_UserSessions_RevokedAt` (filtered `[RevokedAt] IS NOT NULL`), `IX_MfaChallenges_ExpiresAt`, `IX_TrustedDevices_ExpiresAt`, `IX_TrustedDevices_RevokedAt` (filtered) and, for the outbox cleanup, `IX_OutboxMessages_ProcessedAt` (filtered `[ProcessedAt] IS NOT NULL`). Indexes only; no data changes. `AuthAuditLogs` already has an index that leads with `OccurredAt`.

## Background processing

<!-- Hosted services, outbox handlers and scheduled jobs the module runs. -->

**Seeding.** `SeedAuthModuleAsync(cancellationToken)` (an extension of `IServiceProvider` on `AuthModule`; `AuthSeeder` in `Infrastructure/Authorization/`) brings the database to the declared state. The host calls it once at start, after the migration step, when `Auth:Seed:RunOnStartup` is on (the default); the integration test harness calls it after migrating and again after every database reset. It is idempotent, and one run is one transaction under an exclusive SQL Server application lock (`sp_getapplock` on `auth.seed`, 60-second wait), so instances that start together seed one after the other and a failed run leaves nothing half done. It is retried as a whole on transient SQL errors. In order:

1. **Permissions.** `PermissionSynchronizer` validates every definition of every registered `IPermissionSource` and fails the run with an `InvalidOperationException` naming the code and the source when one is wrong: the code must match `^[a-z]+(\.[a-z_]+){2}\z`, the module must equal the code's first segment, the name must not be blank, code, name and description must fit their columns (128, 200, 500 characters), and no code may be declared twice, in one source or across sources. Then it inserts new codes, updates the name and description of known ones (and clears `IsDeprecated` if a code comes back), and deprecates every stored code that no source declares. It never deletes a permission.
2. **System roles.** `SuperAdmin`, `Admin` and `User` are created when missing (`Role.CreateSystem`). A non-system role that already has one of these names stops the run, because it would otherwise receive the system role's grants without its protection.
3. **Grants.** `SuperAdmin` is set to every non-deprecated permission on each run, so a newly declared permission reaches it at the next start and a deprecated one leaves it; this goes through `Role.SyncPermissions`, the seeder-only entry point (`SetPermissions` refuses `SuperAdmin`). `Admin` gets the permissions flagged `AdminDefault` (see [Permissions](#permissions)) when the role is created, and later each flagged code only in the run that first inserts it (`PermissionSynchronizer` reports which codes it inserted, in `PermissionSyncResult`, and `AuthSeeder.GrantAdminDefaults` adds them to the grants `Admin` holds); it never takes a grant away or adds one back, so the rest of its set belongs to the administrators. `User` gets nothing.
4. **First administrator.** When `Auth:Seed:AdminEmail` and `Auth:Seed:AdminPassword` are both set (a blank value counts as unset; exactly one set logs an information line and seeds no account) and no user has that normalized email, it registers a user with display name `Administrator`, locale `en`, the hashed password, a confirmed email and the `SuperAdmin` role. The settings are checked before the transaction: an address that is not a plain email, or a password outside the `Auth:Password` length limits, fails the run with a message that names the setting and never the password. An existing account with that email, in any spelling and **soft-deleted or not**, is left exactly as it is and the run logs a warning instead (`IUserRepository.ExistsByNormalizedEmailIncludingDeletedAsync` ignores the soft-delete filter): a seed administrator that someone deleted is never re-created, even though the unique email index would allow a new row. The registration raises the usual `UserRegisteredDomainEvent` and `EmailConfirmedDomainEvent`. **Remove `Auth:Seed:AdminPassword` from the configuration after the first start**: the account exists from then on, and the password should not stay in the secret store or the environment.

**Outbox.** The `Publish*DomainEventHandler`s run from the module outbox and publish the module's integration events (see [Publishing](#publishing)); a failing consumer makes the outbox retry the publishing handler with the same event id. Sending is not the outbox's job: the Notifications delivery worker sends the emails and retries a failed send itself, so an SMTP outage delays an email without failing or retrying any Auth outbox message. A queued link stops working when its code expires (60 minutes for a confirmation), whether or not the email has gone out; the delivery worker expires a delivery whose link has expired instead of sending it.

### Cleanup

Six recurring jobs delete what has outlived its retention (ADR 0028; `Infrastructure/Retention/`, registered by `AddAuthModule` through `AuthModule.AddRetention`, run by the scheduler described in [infrastructure-common](../building-blocks/infrastructure-common.md#recurring-jobs)). Each derives from `BatchedCleanupJob` on `AuthDbContext`: a `DELETE TOP (@Batch)` loop of `Retention:BatchSize` rows (1000), at most `Jobs:MaxBatchesPerRun` batches (100) per run, so a backlog drains over several runs. A row goes only when it is strictly older than the cutoff (`now` minus the retention, on `TimeProvider`): a row exactly at the retention stays until the next run. A retention of `00:00:00` or empty turns that job off. A job that fails is recorded `Failed` and tried again at the next interval; the other jobs are unaffected.

| Job | Interval | Deletes | Retention key (default) |
|---|---|---|---|
| `AuthVerificationCodesCleanup` | hourly | `VerificationCodes` with `ExpiresAt` older than the retention, consumed or not | `VerificationCodes` (7 days) |
| `AuthRefreshTokensCleanup` | daily | `RefreshTokens` with `ExpiresAt` older than the retention, whatever the session's state | `RefreshTokens` (30 days) |
| `AuthSessionsCleanup` | daily | `UserSessions` with `RevokedAt` or `ExpiresAt` older than the retention; their tokens go by cascade | `Sessions` (90 days) |
| `AuthMfaChallengesCleanup` | hourly | `MfaChallenges` with `ExpiresAt` older than the retention, consumed or not | `MfaChallenges` (1 day) |
| `AuthTrustedDevicesCleanup` | daily | `TrustedDevices` with `ExpiresAt` or `RevokedAt` older than the retention | `TrustedDevices` (30 days) |
| `AuthAuditLogsCleanup` | daily | `AuthAuditLogs` with `OccurredAt` older than the retention | `AuditLogs` (off) |

- **Reuse detection lasts as long as the used token does.** `AuthRefreshTokensCleanup` looks only at a token's own `ExpiresAt` and deletes the token `Auth:Retention:RefreshTokens` (30 days by default) after it, whatever its session's state. While a used token still exists, presenting it answers `auth.refresh_token_reused` and revokes the session, even after the token's own expiry, because `UserSession.ValidateRefresh` checks used or revoked before it checks expiry ([Refresh and logout](#refresh-and-logout)). That holds only while the session is still active and its security stamp still matches the user's: a session that is already revoked answers `auth.invalid_refresh_token` first and is left as it is, and a changed stamp revokes it as `PasswordChanged` and answers `auth.invalid_refresh_token` before reuse is looked at. Once the cleanup has deleted the token, the same token answers `auth.invalid_refresh_token`: it is still refused, but nothing is revoked. A deployment that wants the theft signal for longer raises `Auth:Retention:RefreshTokens`. The unexpired tokens of a live session stay while its expired ones go (`AuthCleanupJobTests.A_used_refresh_token_answers_reuse_until_its_cleanup_and_invalid_refresh_token_after`).
- **Sessions take their tokens with them.** The foreign key from `RefreshTokens.SessionId` to `UserSessions` cascades (`UserSessionConfiguration`, migration `InitialAuth`), so one `DELETE` of the sessions of a batch removes their tokens in the same statement and the same transaction; nothing else references the session (audit rows keep its id without a foreign key). The job reports sessions, not tokens, and `Retention:BatchSize` bounds sessions, not token rows: one batch of sessions can cascade-delete many more token rows than that (a session refreshed often has one per refresh). A session goes after `Auth:Retention:Sessions` from whichever came first, its revocation or its expiry, so one expired long ago but never revoked goes too. Deleting every session of a dormant account does not make its next sign-in look like its first: that sign-in still counts as a new device, because the first sign-in is told by `User.LastLoginAt`, not by the sessions ([New device](#new-device)).
- **A revoked trusted device goes by its revocation, not its far expiry.** The device's `ExpiresAt` is at most `Auth:Mfa:TrustedDeviceLifetime` (30 days by default) ahead; a device revoked early would otherwise outlive the cleanup that waits for its expiry.
- **Audit logs are kept by default.** The blueprint's "12 months hot, then archive" names no archive, so `Auth:Retention:AuditLogs` is off by default, and the Audit module (Plan 5b) ships no archive either: [ADR 0030](../adr/0030-audit-trail-through-the-owning-modules-outbox.md) settled on a delete window only, so a deployment that must keep these entries longer than its window copies them from the table first. An operator who sets the retention accepts that older entries are lost. The field-level trail of Auth's entities is the Audit module's (`Audit:Retention:Trails`, also off by default; [Audited entities](#audited-entities)). The predicate uses the leading `OccurredAt` of `IX_AuthAuditLogs_OccurredAt_Id`.
- **Not time-based, not cleaned.** `RecoveryCodes` go with the method that issued them (when two-step verification is turned off or the codes are regenerated) and `PasswordHistory` is capped at `Auth:Password:HistoryCount`.
- **Cheap to construct.** The scheduler resolves every job once at start to read its name and interval, so a job's constructor reads its option and opens no connection (`AuthCleanupJobTests.A_job_constructor_opens_no_connection`).
- **Indexes.** Every predicate has the index `AddCleanupIndexes` created ([Data](#data)); `AuthCleanupJobTests.Cleanup_predicates_use_their_indexes` compiles the statements of the two largest tables' jobs, `RefreshTokens` and `UserSessions`, and checks that the plan seeks them and never scans the table.

| Counter | Tags | Counts |
|---|---|---|
| `auth.logins` | `result`: `succeeded`, `invalid_credentials`, `locked`, `unverified`, `inactive`, `mfa_required` | Every login that reached the handler (a 400 or 429 never does). `invalid_credentials` covers an unknown email, a wrong password (also while locked), an account without a password and a successful login (or challenge) that lost a save race; `locked` is a correct password on a locked account; `unverified` and `inactive` are the two 403s; `mfa_required` is a correct password of an account with two-step verification, answered with a challenge (how it ends is `auth.mfa_verifications`). |
| `auth.mfa_verifications` | `result`: `succeeded`, `invalid_code`, `invalid_challenge`; `factor`: `totp`, `recovery_code`, `none` | Every `POST /api/v1/auth/mfa/verify` that reached the handler (a 400 of the validator or a 429 never does). `factor` is the factor accepted (`succeeded`) or tried (`invalid_code`), and `none` for `invalid_challenge`, which is decided before a factor counts (or after it was spent, when the challenge was lost). A completed sign-in of an MFA account is one `auth.logins` `mfa_required` and one `auth.mfa_verifications` `succeeded`. |
| `auth.registrations` | none | Every accepted registration request, new and existing addresses alike, so the metric cannot tell them apart any more than the response can. A breached password or a 400 is not counted. |
| `auth.step_ups` | `result`: `succeeded`, `failed` | Every step-up that reached a decision: `failed` is any 400 of the handler (a wrong proof, a factor the account may not use, a locked account); a 400 of the validator, a 401 and a 429 are not counted. |
| `auth.token_reuse_detected` | none | Refresh tokens presented again after use or revocation, and refreshes that lost the claim of their token to a simultaneous one; each revoked its session. |

## Known limits

<!-- Not a required section: the limits the module's own sections mention, collected so a reviewer or an operator finds them in one place. Each links to the section that explains it. -->

What the module deliberately leaves out, or only approximates. None of these is a vulnerability a request can exploit on its own; each is a trade-off to know before relying on the behaviour.

**Passwords and enumeration**

- Passwords are **not Unicode-normalized** and their length counts UTF-16 code units, in register, login, reset and change alike (Ruling R14). The same password typed in two normalization forms (`é` as one character or as `e` plus an accent) is two different passwords, and an emoji counts as two toward `MaxLength`. Adding normalization later needs a hash-version bump.
- Login does one verification on every path, but an account whose stored hash was made with a lower PBKDF2 cost than today's verifies **faster** than the dummy hash used for unknown emails, until its next successful sign-in rehashes it. That can only happen after the iteration count is raised, and only for accounts that have not signed in since; see [Login and current user](#login-and-current-user).
- Resend and forgot do no hashing, but a known address costs a few more queries (and, for a new link, one Data Protection encryption) than an unknown one: a difference of milliseconds. A known account's failed login also runs one more `UPDATE` than an unknown one. See [Registration](#registration) and [Passwords](#passwords).
- Two registrations (or administrator creates) of the same **new** address at the same moment: one wins and the others answer as for a known address (409 `auth.email_taken` for the administrator), but EF Core still logs each refused insert at Error level with the address inside SQL Server's message ([Data](#data)).
- Two simultaneous forgots can leave two live reset links; a successful reset or change invalidates every pending one ([Passwords](#passwords)).
- The registration-attempt notice (an email to the owner of an address someone tries to register again) has no per-account cooldown: only the per-address `auth-strict` limit bounds it, so requests from many addresses can send many notices to one account ([Registration](#registration)).
- Changing the password with a wrong current password is not counted toward the login lockout; the per-address `auth-strict` limit bounds it instead ([Passwords](#passwords)).

**Tokens and sessions**

- Access tokens are **not typed** `at+jwt` (RFC 9068), so any other JWT signed by the same key with the same issuer and audience would validate. Nothing else in the template signs with these keys; keep it that way, or use separate keys. See [Access tokens](#access-tokens).
- An access token keeps working until it expires after logout, suspension or a password change, because it is not checked against the session per request (D9, ADR 0015): at most `Auth:Jwt:AccessTokenLifetime` plus the clock skew, 10 minutes 30 seconds by default. Permissions are the exception: they are resolved on the server, so a lost permission stops working at once on the instance that made the change and within 30 seconds on the others (ADR 0016).
- A step-up is a fresh `auth_time` in the access token (ADR 0023): an access token minted by a step-up satisfies protected actions until `Auth:StepUp:MaxAge` (10 minutes) after it, even if the session is revoked in the meantime (D9). A step-up from a revoked or expired session is refused, so it cannot extend one ([Step-up](#step-up)). The refusal has a narrow window: a revocation that lands after the step-up resolved the session but before its save still yields one access token, valid for the access-token lifetime and with a fresh `auth_time` for `MaxAge`; that is the same exposure as any access token (Plan 2 D9, ADR 0015).
- Wrong step-up proofs count toward the lockout, so whoever holds a session can lock its owner out with five wrong codes; a successful step-up does not reset the count, only a successful sign-in does ([Step-up](#step-up)).
- A wrong code at the TOTP confirm is not counted toward the lockout (the caller made the secret); only the global per-user rate limit bounds it ([Enrollment](#enrollment)).
- Wrong codes at the sign-in challenge count toward the lockout (D7), so someone who knows the email and the password can lock the owner out for `Auth:Lockout:Duration` with five wrong codes: the same denial of service wrong passwords already allow, and the lockout email tells the owner the password is known ([Challenge and verify](#challenge-and-verify), ADR 0024).
- A verify whose code is right but whose challenge is lost meanwhile (a simultaneous verify, the cap or the expiry) answers `auth.invalid_mfa_challenge` with the code already spent: the user signs in again and waits for the next code ([Challenge and verify](#challenge-and-verify)). The loser of a double tap counts one wrong code.
- Expired and consumed challenges stay in `auth.MfaChallenges` for `Auth:Retention:MfaChallenges` (1 day) after they expire, until the hourly `AuthMfaChallengesCleanup` deletes them ([Cleanup](#cleanup)).
- A trusted device token is a 30-day credential the client stores; in a browser SPA it is readable by injected script (a cookie variant comes with the backend-for-frontend). It replaces the code only, so it still needs the password ([Trusted devices](#trusted-devices), ADR 0025).
- Revoking a trusted device does not end the sessions or refresh tokens started through it: they stay valid until they expire or are revoked, because sessions do not link to the device that started them. A client that wants to sign the device out also calls `DELETE /api/v1/auth/sessions/{id}` ([Trusted devices](#trusted-devices), ADR 0025).
- Two simultaneous revocations of one trusted device can both write an `auth.trusted_device_revoked` audit row: the "already revoked" check is a read, not a conditional update. The device ends revoked either way.
- Every rotation of the security stamp forgets every trusted device, including regenerating recovery codes and a suspension that is lifted again: users verify a code once more on each device. Expired, revoked and forgotten devices stay in `auth.TrustedDevices` until `AuthTrustedDevicesCleanup` deletes them, `Auth:Retention:TrustedDevices` (30 days) after they expired or were revoked; a forgotten device that was never revoked goes 30 days after its expiry ([Trusted devices](#trusted-devices), [Cleanup](#cleanup)).
- The challenge answer tells the caller the password was right (any second step does); the 401 for a wrong password, an unknown email and a locked account is unchanged ([Login and current user](#login-and-current-user)).
- The OpenAPI schemas of `LoginResult` and `MfaVerifyResponse` list every member as required, also those left out when null (as for `CursorPage.totalCount`).
- Of two first TOTP setups of one user at the same moment (no method yet) both answer 200 and only the later secret is stored, so the app set up from the other answer cannot confirm until the user starts again. A confirm racing a setup, and two restarts of a pending setup, answer 409 `concurrency.conflict` to the later save instead; every new writer of `UserMfaMethods` must keep the method's concurrency tokens (`SecretEncrypted`, `ConfirmedAt`) ([Enrollment](#enrollment)).
- One authenticator per user (D18): replacing a phone means removing the method, then setting up the new one (a step-up with a code, `DELETE` the method, then set up again).
- Turning two-step verification off deletes the recovery codes with it, and regenerating replaces them: a user who has lost the device **and** every recovery code has no self-service way back and needs an administrator ([Managing MFA](#managing-mfa)).
- A step-up proved before two-step verification was turned off stays valid until `Auth:StepUp:MaxAge` runs out, as every step-up does; the other sessions end at the change, this one is kept.
- The saved language is a claim of the access token (D7), so after `PUT /api/v1/auth/me` the token issued before keeps answering in the old language for up to 10 minutes, until the client refreshes ([Sessions and profile](#sessions-and-profile), Ruling R16).
- A logout with a token that has no `sid`, or for a session that already ended, writes no audit entry.
- A session's refresh-token chain grows by one row per refresh: a session refreshed often over its 90 days keeps every used token until `AuthRefreshTokensCleanup` deletes it, `Auth:Retention:RefreshTokens` (30 days) after the token's own expiry, or `AuthSessionsCleanup` deletes the session; revoking the session stamps them all ([Cleanup](#cleanup)).
- `auth.AuthAuditLogs` is never cleaned by default: `Auth:Retention:AuditLogs` is off, because the template ships no archive (ADR 0030) and deleting the entries would lose them. The table grows by a few rows per sign-in until an operator sets a retention, after copying what must be kept ([Cleanup](#cleanup)).
- Refresh shares the per-address `auth-strict` budget with login and the other credential routes, so many users behind one NAT address can run out of it ([API host](../services/api.md#ratelimiting) explains the sizing).

**Administration and concurrency**

- The no-escalation rule (assigning a role or editing a role's permissions needs the actor to hold what is newly granted) uses the actor's cached permission set, so on another instance a permission the actor just lost may still count for up to 30 seconds ([Permissions](#permissions)).
- Two SuperAdmins demoting or locking each other at the same moment can leave none; recovery needs a new seed address or a database edit ([User administration](#user-administration)).
- Concurrent changes of one user's roles or one role's permission set both apply, and two that add the same row can collide on the primary key and answer a 500 ([User administration](#user-administration), [Role, permission and audit log administration](#role-permission-and-audit-log-administration)).
- Another instance may keep a removed permission for up to 30 seconds, with or without Redis: invalidation clears Redis and the local copy of the instance that makes the change only ([Permission checks](#permission-checks)). The grant check of a role-permission edit uses the same cached set of the actor.
- The seeder does not clear the permission cache and runs only at start-up.
- Audit `from` and `to` filters read a date without a time as midnight at the start of that day, so `to=2026-10-09` excludes nearly all of 9 October ([Role, permission and audit log administration](#role-permission-and-audit-log-administration)).

**Email and runtime**

- The emails Auth causes are sent asynchronously by the Notifications module: a request returns before its email is sent, and an SMTP outage delays the email (retried for about 81 minutes, then dead-lettered), so a link can expire before it arrives ([Notifications module](notifications.md#background-processing)). The host refuses to start with a `Notifications:Email:Username` and `UseTls=false` unless the SMTP host is a loopback address, so the credentials never travel in clear.
- The base `appsettings.json` has development defaults that every other environment must override: `Notifications:Email:UseTls` is `false` (and the host `localhost`), and `Auth:Links:ConfirmEmailUrl` and `ResetPasswordUrl` point at `http://localhost:3000`, so links would lead nowhere ([Configuration](#configuration)). Nothing refuses to start with them.
- Locales and time zones are validated with the runtime's culture and time-zone data, which needs **ICU** and, on Linux, **tzdata**. An image with `InvariantGlobalization` on, or without `tzdata`, rejects every locale and IANA time zone but the invariant ones and `UTC` (`PUT /api/v1/auth/me` then fails for everyone). The repository does not enable invariant globalization; Plan 6's image must carry ICU and `tzdata` ([Sessions and profile](#sessions-and-profile)).
- The Data Protection key ring in `auth.DataProtectionKeys` is not encrypted at rest yet (Plan 6, ADR 0017).
- The JWKS is not part of the OpenAPI document.

**Two-step verification scope**

- There is **no MFA policy** yet: nothing requires a role (`SuperAdmin`, `Admin`) or a tenant to enroll, so an administrator can run on a password alone. A policy needs an enrollment-only session state, so an account that must enroll gets no full session until it does (backlog item `Auth:Mfa:Policy`, `RequiredForRoles`).
- TOTP is the only factor. Email and SMS codes, magic links and passkeys are deferred (they would reuse the challenge, the lockout coupling, the step-up rule and the notifications), and so are several authenticators per user and the step-up on administrator actions. Social login (Google, Apple, Microsoft, Facebook and a generic OpenID Connect provider) and phone-number OTP login, which needs the SMS channel, are planned as their own plans, with every provider off by default behind an `Enabled` setting. Changing the email, deleting the account, creating an API key and unlinking a login do not exist yet; each must call `StepUpPolicy` when it is built.
- `auth.mfa_changed` and `auth.new_device_login` are email only: the template has no push channel yet.
- A user who loses the device and every recovery code needs an administrator, and an administrator cannot reset themselves, so the last administrator in that position needs a database edit or a new seed account. If the Data Protection key ring is lost, every TOTP code fails until the user signs in with a recovery code or an administrator resets the account ([Recovering access](#recovering-access)).
