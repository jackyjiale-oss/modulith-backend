# Modulith Backend: Action Plan (Plan 2: Auth Core)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-in-user story for the template: register, verify email, log in, refresh, log out, reset and change password, manage sessions, and protect endpoints with role-based permissions. Admins manage users, roles and the audit log. The Sample module moves under authorization.

**Architecture:** One new module, `TemplateName.Modules.Auth` (schema `auth`, own `AuthDbContext` and outbox), following the Plan 1 layout. It uses its **own aggregates** (User, Role, UserSession, VerificationCode) and borrows only Identity's `PasswordHasher` (ADR 0014). Access tokens are ES256 JWTs validated by `JwtBearer`; refresh tokens are opaque, hashed, rotated and reuse-detected. Permissions are resolved server-side per request from a short-lived per-user cache (`perm:{userId}`) and enforced with `.RequirePermission()`. Emails go out through the module outbox, so a mail failure never loses the account.

**Tech Stack:** Plan 1 stack plus `Microsoft.AspNetCore.Authentication.JwtBearer`, `Microsoft.Extensions.Identity.Core` (hasher only), `Microsoft.Extensions.Caching.Hybrid` (in-memory only until Plan 5 adds Redis), `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore`, `MailKit`, Mailpit (dev and tests).

**Spec:** `BACKEND_TEMPLATE_BLUEPRINT.md` Sections 9, 11.2 and 12.2 as amended by `docs/blueprint-review.md` (Sections 2.7, 2.8, 2.11, 2.12, 8.2); the review wins where they disagree. Plan 1 (`docs/superpowers/plans/2026-10-06-foundation-and-core-baseline.md`) is done and merged; its Global Constraints still apply. This plan is row 2 of the review's roadmap.

## Global Constraints

Everything in Plan 1's Global Constraints applies (CPM, Conventional Commits, `TimeProvider`, `Async` suffix, error codes `module.snake_case`, i18n in en/ms/zh-Hans, docs in the same commit, cursor pagination for every list endpoint, `internal` module types, Shouldly, non-parallel integration tests). Plan-specific values, copied from the spec:

- **Workflow:** one branch `feature/auth-core`, **one commit per task**, one PR at the end. Never push to `main`. Agent commits end with `Co-Authored-By: <the model that wrote it> <noreply@anthropic.com>`.
- **Token lifetimes:** access token (JWT) 10 min (`Auth:Jwt:AccessTokenLifetime`); refresh token 14 days sliding, 90 days absolute (`Auth:RefreshToken`); email verification link 60 min and password reset link 30 min (`Auth:Verification`, inside the spec's 15-60 min range); resend cooldown 60 s.
- **JWT:** ES256 (P-256) only; the validator allow-lists `ES256`; validates `iss`, `aud`, `exp`, `nbf`; clock skew 30 s; `MapInboundClaims = false`. Claims: `sub`, `sid`, `sst`, `amr`, `auth_time`, `locale`, `jti`, `iat`, `nbf`, `exp`, `iss`, `aud`. **No permission list and no personal data in the token.** Public keys at `/.well-known/jwks.json`.
- **Persisted secrets:** refresh tokens, verification tokens and any other bearer secret are stored only as SHA-256 hashes (`varbinary(32)`), generated with `RandomNumberGenerator` (32 bytes, base64url, 43 characters).
- **Passwords:** minimum 12 (`Auth:Password:MinLength`), maximum 128 characters, no composition rules, breached-password check through HIBP k-anonymity (`Auth:Password:CheckBreached`, default `true`, **fail-open** with a warning on any network error, only the 5-character SHA-1 prefix leaves the process), no reuse of the last 5 (`HistoryCount`, the current hash counts as one). The length limit is checked **before** hashing.
- **Lockout:** 5 failed attempts, then 15 minutes (`Auth:Lockout`). A locked account answers with the same generic `auth.invalid_credentials` as a wrong password.
- **Enumeration:** login, register, forgot-password and resend-confirmation return identical status and body for existing and unknown emails. Work that costs time (password hashing or verification) happens on both paths.
- **Rate limiting:** policy `auth-strict` (fixed window per client address, default 10 requests per minute, `RateLimiting:AuthStrictPermitLimit` / `AuthStrictWindow`) on every anonymous credential endpoint. The resend and forgot cooldowns are enforced in the handler from `VerificationCodes.CreatedAt` (review 2.11).
- **Permissions:** codes are `module.resource.action` in snake case, declared in code and synced into `auth.Permissions` at startup. The cache key is `perm:{userId}`, local lifetime 30 s, removed explicitly on every role or assignment change (review 2.7).
- **Routes:** self-service `/api/v1/auth/...`; administration `/api/v1/admin/auth/...`; JWKS at `/.well-known/jwks.json`. Anonymous endpoints say `.AllowAnonymous()` explicitly; everything else is protected by the fallback policy.
- **Database:** schema `auth`; tables PascalCase plural; `Guid` keys from `SequentialGuid`; the audit log key is `bigint identity`.

## Decisions this plan takes (confirm before execution)

These differ from, or narrow, the blueprint. Each has a reason; say so before Task 1 if you disagree.

| # | Decision | Why |
|---|---|---|
| D1 | **Own identity model; ASP.NET Core Identity is used only for its PBKDF2 `PasswordHasher`** (ADR 0014). No `UserManager`, no Identity EF stores. | `UserManager` is an anonymous-property model that bypasses aggregates, domain events and the outbox. The `Domain` layer may not depend on `Microsoft.AspNetCore.*` (architecture test), and `IdentityUser` lives in that namespace. |
| D2 | No `FamilyId` column: a refresh-token **family is the session**. | One login creates one session and one chain of tokens; the two ids would always be equal. |
| D3 | Login by **email only**; no separate `UserName`. | One identifier to normalize and protect from enumeration. Usernames can be added with a migration. |
| D4 | Lockout is a fixed 15 minutes (not progressive); CAPTCHA is not included. | Keeps Plan 2 lean; both are additive later. |
| D5 | Deferred schema: `UserPermissionOverrides`, `PermissionsVersion`, `TenantId`, `UserClaims`/`RoleClaims`, session `DeviceType`/`Location`, `SigningKeys` table. | Not needed for the Plan 2 flows (keys come from config, review 2.7 replaces `PermissionsVersion`, tenancy is backlog). |
| D6 | `.RequirePermission(code)` adds a per-endpoint `IAuthorizationRequirement`; there is no dynamic policy provider. | Same behaviour, one less moving part. |
| D7 | `UseAuthentication` moves **before** `UseApiLocalization` in the pipeline. | The saved `locale` claim must win over `Accept-Language` (review 8.2), and request localization has to stay ahead of the exception handler (ADR 0009). |
| D8 | Plan 2 emails are **English only**; the user's `Locale` is stored for Plan 3. Tokens inside outbox events are encrypted with Data Protection (ADR 0017). | Translated templates are Plan 3 (Scriban). A plaintext token in `auth.OutboxMessages` would be a bearer secret at rest. |
| D9 | Access tokens are **not** checked against session revocation on every request, so a revoked session's access token works until it expires (at most 10 minutes). Refresh stops at once. | Per-request session lookups defeat stateless JWTs; documented in ADR 0015 and the module doc. |
| D10 | A **locked account** gets `auth.invalid_credentials` (401), not a special code. | A distinct "locked" answer would reveal that an email exists. |
| D11 | No `TemplateName.Modules.Auth.Contracts` project yet. The shared authorization types live in `Application.Common/Identity`. | Contracts are created when a module first exposes something to another module (Plan 3 adds the integration events). |

## Review Focus

Inputs the spec implies and a person will meet, most likely first. Each is pinned by a named test in the owning task.

1. **Email spelling:** `Alice@Example.com ` (case, surrounding whitespace) must be the same account as `alice@example.com` at registration, login, forgot and resend, and the unique index must enforce it. Owned by Task 13 (`Email_is_case_and_whitespace_insensitive`).
2. **The same refresh token sent twice at once** (a client retry or a double tap) must produce exactly one new token pair, and the loser must get 401 without a 500. Owned by Task 15 (`Concurrent_refresh_with_same_token_succeeds_once`).
3. **A verification or reset token used in the wrong place:** a reset token on the confirm endpoint, a token used twice, an expired token, a token replaced by a resend. All must fail with `auth.invalid_token`. Owned by Task 13 and Task 16 (`Token_of_another_purpose_is_rejected`, `Superseded_token_is_rejected`).
4. **Forged or odd JWTs:** `alg: none`, an HS256 token signed with the public key bytes, an unknown `kid`, a tampered payload, a wrong audience, an expired token. All must be 401, never 500 and never accepted. Owned by Task 9 (unit) and Task 11 (integration).
5. **Unusual passwords:** exactly 12 and exactly 128 characters (accepted), 129 (rejected before hashing), a 1 MB string (rejected cheaply), only spaces, Unicode, and the password equal to the email. Owned by Task 13 (`Password_boundaries_are_enforced`, `Oversized_password_is_rejected_before_hashing`).
