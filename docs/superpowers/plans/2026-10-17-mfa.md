# Modulith Backend: Action Plan (Plan 4: Multi-Factor Authentication)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Users can turn on TOTP two-step verification with single-use recovery codes; a login of such an account answers with a short-lived MFA challenge instead of tokens until a code is verified; sensitive self-service actions require a fresh step-up; a verified device can be remembered for 30 days; administrators can reset a user's MFA; and MFA changes and sign-ins from a new device are emailed through the Plan 3 Notifications pipeline.

**Architecture:** Everything lives in the existing Auth module (schema `auth`) plus two new Auth Contracts events and two Notifications types. TOTP is RFC 6238 over `System.Security.Cryptography.HMACSHA1` (no package); the secret is stored encrypted with Data Protection under its own purpose. The MFA challenge and the trusted-device token are opaque random tokens stored as SHA-256 hashes, like refresh tokens. Step-up is not a new token: it refreshes the session's `auth_time` and `amr`, which the access token already carries (Plan 2 D9 stays: no per-request session lookup). Every MFA change rotates the user's security stamp, which ends the other sessions, the pending challenges and the trusted devices in one rule.

**Tech Stack:** Plan 3 stack, no new package. `System.Security.Cryptography` (`HMACSHA1`, `RandomNumberGenerator`, `SHA256`, `CryptographicOperations.FixedTimeEquals`) and ASP.NET Core Data Protection (already used). QR codes are a client concern: the API returns the `otpauth://` URI only.

**Spec:** `BACKEND_TEMPLATE_BLUEPRINT.md` Sections 9.1 (TOTP MFA + recovery codes, step-up, trusted devices: "always"), 9.3 (MFA challenge token, step-up claim, security stamp), 9.5 (login flow), 9.7 (MFA, step-up and trusted-device endpoints; admin "reset MFA"), 9.9 (TOTP, recovery codes, tokens, sessions, step-up and notification rules), 9.10 (`Auth:Mfa`, `Auth:StepUp`), 10.6 (`auth.new_device_login`, `auth.mfa_changed`), 11.2 (`UserMfaMethods`, `RecoveryCodes`, `TrustedDevices`), 12.2 (MFA must-have row) and Phase 5 (MFA items), as amended by `docs/blueprint-review.md` Sections 2, 4, 5, 6 (row 4), 7, 8 and 11; the review wins where they disagree. Plans 1-3 (`docs/superpowers/plans/2026-10-06-foundation-and-core-baseline.md`, `2026-10-08-auth-core.md` Part D, `2026-10-09-notifications.md` Part D) are the starting point: this branch, `feature/mfa`, starts from `feature/notifications` at `d1497a1` (Plan 3's PR #6 is open; Plan 2 is merged).

## Global Constraints

Everything in Plan 1's, Plan 2's and Plan 3's Global Constraints applies: Central Package Management, lock files and NuGet Audit; allowed licences `MIT`, `Apache-2.0`, `BSD-2-Clause`, `BSD-3-Clause`; Conventional Commits, header at most 72 characters, allowed scopes from `build/scripts/check-commit-msg.sh` (`auth`, `notifications`, `security` are the ones this plan uses); `TimeProvider` only; `Async` suffix and `CancellationToken cancellationToken` last; error codes `module.snake_case` with a message in `en`, `ms` and `zh-Hans` `.resx`; docs in the same commit; cursor pagination for every list endpoint; module types `internal` except the module entry point; `sealed` classes, `record` for messages and DTOs; options `{Section}Options` with `.ValidateDataAnnotations().ValidateOnStart()`; no secrets in files; Shouldly; integration tests non-parallel with `TestContext.Current.CancellationToken`; warnings are errors in Release; never edit an applied migration; never `--no-verify`. Plan-specific values:

- **Workflow:** one branch `feature/mfa`, **one commit per task**, one PR at the end, opened only after Plan 3's PR #6 has merged and the branch is rebased onto `main`. Never push to `main`. Agent commits end with `Co-Authored-By: <the model that wrote it> <noreply@anthropic.com>`.
- **No new package** (D2). An implementer who believes one is needed stops and asks; the licence and fee check of Plan 1 would apply.
- **TOTP (blueprint 9.9):** RFC 6238 with HMAC-SHA-1, 6 digits, 30-second step, time step `floor(unixSeconds / 30)`, ±1 step tolerance, a 20-byte secret from `RandomNumberGenerator`; a code is accepted only for a time step **greater** than the method's `LastUsedTimeStep` (replay refused), claimed with one conditional `UPDATE`; codes are compared with `CryptographicOperations.FixedTimeEquals` over every candidate step, never with an early exit.
- **Recovery codes:** 10 per user, 16 characters from `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (80 bits), shown as `XXXX-XXXX-XXXX-XXXX`; input is normalized (upper-case, `-` and spaces removed) before hashing; stored only as SHA-256 (`varbinary(32)`); single use through one conditional `UPDATE`.
- **Bearer secrets:** the MFA challenge token and the trusted-device token are `ISecureTokenService.Generate()` values (32 random bytes, 43 base64url characters), stored only as SHA-256 hashes.
- **Shown once, never elsewhere:** the TOTP secret appears only in the setup response (as base32 and inside the `otpauth://` URI); recovery codes only in the confirm and regenerate responses. Neither appears in a log line, an audit `Details`, a domain or integration event, the outbox, a notification row, an exception message or a metric tag. Every command, request and response that carries a code, a secret or a token overrides `ToString` to print its type name only (as `LoginCommand` does), and is served with `.WithNoStore()`.
- **Lifetimes and limits (defaults):** challenge 5 minutes, at most 5 wrong codes per challenge; step-up valid 10 minutes from `auth_time`; trusted device 30 days, absolute.
- **Enumeration:** nothing MFA-related is read or decided before the password is verified. Login answers an unknown email, a wrong password and a locked account exactly as in Plan 2, for MFA and non-MFA accounts alike.
- **Routes:** `/api/v1/auth/mfa/...`, `/api/v1/auth/step-up`, `/api/v1/auth/trusted-devices`, `/api/v1/admin/auth/users/{id:guid}/reset-mfa`. Every route says `.AllowAnonymous()` or `.RequireAuthorization()` / `.RequirePermission(...)` explicitly (Plan 2 ruling R13). `POST /api/v1/auth/mfa/verify` and `POST /api/v1/auth/step-up` also have `.RequireRateLimiting(RateLimitPolicies.AuthStrict)`.
- **Database:** schema `auth`; one new migration `AddMultiFactorAuthentication` (Task 4); `datetime2(3)` UTC; hashes `varbinary(32)`; keys from `SequentialGuid.Create(now)`.
- **Naming (ledger lessons):** no type ends in `Manager`, `Helper`, `Helpers`, `Util`, `Utils`, `Utility`, `Impl`, `Dto`, `Settings` or `Info` (`NamingConventionTests.No_type_uses_a_forbidden_suffix`); no identifier or test name contains `TemplateName_` (the template generator rewrites it); no namespace segment equals a type name it would hide (Plan 3's `Delivery` lesson; this plan's folders are `Mfa`, `StepUp`, `TrustedDevices`, and no type is named any of those); the types this plan names are the only names: do not invent synonyms.
- **Files written by tools** may have CRLF endings: run `dotnet format --verify-no-changes` (and fix) before every commit.

## Decisions this plan takes

The human is not available, so these are decided with the spec as the authority. Each has a reason and the cost if it turns out wrong.

| # | Decision | Why | Cost if wrong |
|---|---|---|---|
| D1 | **Scope:** TOTP, recovery codes, the login challenge, step-up, trusted devices, MFA self-management, admin MFA reset, and notifications for MFA changes and new-device sign-ins. **Deferred:** email/SMS OTP and magic links (`--otp`), passkeys (`--passkeys`), the role/tenant MFA policy (`Auth:Mfa:Policy`, `RequiredForRoles`: it needs an enrollment-only session state), more than one authenticator per user, step-up on admin actions, and step-up on email change, account deletion, API keys and unlinking logins (those endpoints do not exist yet). | Review 6 row 4 lists exactly TOTP + recovery codes, challenge, step-up, trusted devices. | An admin can run without MFA until the policy lands (Part C2); documented as a known limit. |
| D2 | **No package.** TOTP (RFC 6238/4226) is ~40 lines over `HMACSHA1`; base32 (RFC 4648) is written by hand; QR rendering is the client's job (`otpauth://` URI only). | Smallest licence and supply-chain surface; RFC test vectors pin correctness. | A bug in our own code; mitigated by the RFC vectors and Review Focus 2-3. |
| D3 | **TOTP parameters:** SHA-1, 6 digits, 30 s, ±1 step, 20-byte secret; **replay:** a monotonic `LastUsedTimeStep` claimed by `UPDATE ... WHERE LastUsedTimeStep IS NULL OR LastUsedTimeStep < @step`. ADR 0022. | What every authenticator app supports; blueprint 9.9. A monotonic step makes "same code twice" and "older code after a newer one" both fail, also across simultaneous requests. | A user who signs in twice within 30 s waits for the next code (documented). |
| D4 | **The TOTP secret is encrypted by `IMfaSecretProtector`** (Data Protection purpose `TemplateName.Auth.MfaSecrets.v1`, same key ring `auth.DataProtectionKeys`), **not** by the shared `ISecretProtector` (`TemplateName.Secrets.v1`). | ADR 0020 made the shared purpose readable by Notifications on purpose; a TOTP secret must be readable by Auth only. Purpose isolation costs one 20-line class. | Losing the key ring makes every TOTP secret unreadable: users sign in with a recovery code or get an admin reset (runbook text in Task 13). The ring is not encrypted at rest until Plan 6 (ADR 0017), so a full database dump exposes TOTP secrets: known limit. |
| D5 | **Recovery codes:** 10 × 16 characters (80 bits), SHA-256 of the normalized code, single use; regenerating **replaces** the whole set in the same save as the user's stamp change, so no batch id is needed (two concurrent regenerations conflict on the user's `RowVersion`). | Blueprint "10 codes, 10+ chars, hashed, single use". 80 bits makes an unsalted fast hash safe (Plan 2's rule for bearer secrets); 50 bits (10 characters) would be crackable offline in about a day. | Longer codes to type; the normalization accepts lower case and missing hyphens. |
| D6 | **The MFA challenge is an opaque token over a server-side row** (`auth.MfaChallenges`: hash, user, stamp snapshot, device name, expiry, `ConsumedAt`, `FailedAttempts`), not a signed JWT. Only `POST /mfa/verify` looks it up, it is not a JWT (the bearer handler refuses it) and it is no refresh token (another table). ADR 0024. | Single use and a per-challenge attempt cap need state anyway; a JWT would need a `jti` table and gives nothing back. Blueprint "signed, single purpose" is met in substance: unforgeable, single purpose, 5 minutes. | One more table to clean up (Plan 5). |
| D7 | **Guess limits, three layers:** `auth-strict` per client address; at most `Auth:Mfa:MaxChallengeAttempts` (5) wrong codes per challenge; **every wrong code counts in the user's lockout counter** (`IUserRepository.RecordFailedSignInAsync`, Plan 2's atomic statement), and the password step of an MFA account does **not** reset that counter (only a verified second factor does). | Without the coupling, "password → 4 wrong codes → password again" gives unlimited guesses from many addresses. With it, 5 wrong codes lock the account for 15 minutes and Plan 3 emails `auth.account_locked`. | Someone who knows the password can lock the owner out for 15 minutes: the same denial of service wrong passwords already allow, and the lockout email tells the owner the password is known. |
| D8 | **Login answers 200 `LoginResult`** with `mfaRequired` as discriminator: `false` with the Plan 2 token members, or `true` with `challengeToken`, `challengeExpiresAt`, `methods` (`["totp","recovery_code"]`); the members of the other shape are omitted (`JsonIgnore(WhenWritingNull)`). Refresh keeps `LoginResponse`; verify returns `MfaVerifyResponse`. | Blueprint 9.5 says 200 with `mfaRequired`; one schema per route keeps the OpenAPI document honest. | The login schema's token members become optional: generated clients change (the template is unreleased). |
| D9 | **`amr` and `auth_time`:** password sign-in `pwd`; TOTP `pwd otp mfa`; recovery code `pwd rcvr mfa` (`rcvr` is not in RFC 8176; documented); trusted device `pwd`. A step-up **replaces** the session's `AuthMethods` with what it proved (`pwd`, `otp` or `rcvr`) and sets the new column `UserSessions.AuthenticatedAt`, which becomes the `auth_time` of every later token of the session (refresh included). | `amr` describes the authentication at `auth_time` (OIDC). A trusted device proved MFA earlier, not now, so it must not satisfy an MFA step-up. | Clients that read `amr` must accept `rcvr` and `mfa`. |
| D10 | **Step-up = a fresh `auth_time` in the access token**, no separate step-up token: satisfied while `now - auth_time < Auth:StepUp:MaxAge` (10 min) **and**, for an account with a confirmed MFA method, `amr` contains `otp` or `rcvr`. `POST /api/v1/auth/step-up` re-verifies and returns a new access token (same session, same refresh token). Handlers check with `StepUpPolicy` (403 `auth.step_up_required`), reading the claims through `ICurrentUser.AuthTime` and `AuthMethods` (new). ADR 0023. | Blueprint 9.3 "step-up claim: auth_time + amr"; stateless like every other token check (Plan 2 D9). A handler check (not an endpoint filter) lets change password apply the rule to MFA accounts only (D11). | A token stolen within 10 minutes of a step-up can perform protected actions until its `auth_time` ages out (same exposure as the access token itself). |
| D11 | **What requires step-up now:** TOTP setup and confirm, removing an MFA method, regenerating recovery codes, and changing the password **of an MFA account** (a password-only account's current password in the body already is the re-verification, Plan 2's flow is unchanged). Trusted-device revocation and admin actions do not. | Blueprint 9.9 list, limited to what exists in Plans 2-4. | Email change, account deletion, API keys and unlinking must call `StepUpPolicy` when they are built (Part D). |
| D12 | **Step-up factor:** an MFA account must step up with a TOTP code or a recovery code (a password gets 400 `auth.step_up_method_not_allowed`); a password-only account with its password. **Every failed step-up counts** in the lockout counter. | Step-up must prove the strongest factor the account has; a session thief with a phished password must not be able to switch MFA off. Counting stops code-guessing through a stolen session. | A session thief can lock the owner out (they could already sign them out). |
| D13 | **Security stamp and sessions:** enabling, disabling, regenerating codes and an admin reset each rotate the stamp (`User.ChangeMfa`). Self-service: every other session is revoked with the new reason `SessionRevokedReason.MfaChanged` (6) and the current one adopts the new stamp (Plan 2's `AdoptSecurityStamp`). Admin reset: every session revoked with `AdminRevoked`. Signing in with a recovery code changes no stamp. Pending challenges and trusted devices are bound to the stamp snapshot, so they die with it. | Blueprint 9.3 "changing ... MFA ... regenerates it and kills existing sessions"; 9.9 "sessions revoked on MFA reset". Stamp binding is one rule instead of a revocation call in every handler. | Regenerating codes also forgets this user's trusted devices (documented). |
| D14 | **Trusted devices:** opt-in at verify (`rememberDevice`), a hashed token returned once, valid 30 days absolute, bound to user and stamp snapshot (so a password change or reset, an MFA change, a suspension or an admin reset forgets every device), revocable one by one; presented as `trustedDeviceToken` in the login body; switch `Auth:Mfa:TrustedDevicesEnabled`. ADR 0025. | Blueprint 9.5 "untrusted device" and 9.7 endpoints; the body (not a cookie) matches the template's bearer-only clients (BFF is backlog). | Native and SPA clients must store the token securely; a cookie variant comes with BFF. |
| D15 | **A new device** is a successful sign-in (password-only or after MFA; not through a trusted device) whose `(DeviceName, UserAgent)` pair matches none of the user's stored sessions, the account's first session excluded. The email carries **no client-supplied text**: time, time zone and the server-observed address only. | Blueprint 9.5/9.9; a device name typed by an attacker would otherwise land in the owner's inbox (phishing text). | A browser update sends one notice; acceptable for a security notice. |
| D16 | **Notifications:** Auth publishes `MfaChangedIntegrationEvent` (with `MfaChangeKind`: `Enabled`, `Disabled`, `RecoveryCodesRegenerated`, `ResetByAdmin`, `RecoveryCodeUsed`) and `NewDeviceSignedInIntegrationEvent`; Notifications declares `auth.mfa_changed` and `auth.new_device_login`, category `Security`, priority `Critical`, **email only and mandatory** (blueprint 10.6: push is not a channel yet). Events carry ids, the kind and the address; never a secret or a code. | Plan 3 Part D; one type per blueprint row, the kind chooses the sentence (`if change == "..."`). | A sixth kind needs a template branch in three cultures (the render test fails until it exists). |
| D17 | **Admin reset:** `POST /api/v1/admin/auth/users/{id:guid}/reset-mfa`, permission `auth.user.reset_mfa` with `AdminDefault = true`, SuperAdmin rules as for lock, refused on oneself (400 `auth.cannot_reset_own_mfa`: use the self-service route with step-up), removes methods and codes, rotates the stamp, revokes every session, publishes `ResetByAdmin`; a user without MFA answers 204 and changes nothing. | Blueprint 9.7 admin list; "user lost MFA device" is the help-desk task `Admin` already does for passwords (`auth.user.reset_password`). | Every `Admin` gains the power (review it like a role change); and by Plan 3's no-escalation rule an actor needs `auth.user.reset_mfa` to assign `Admin` from now on. `Auth_admin_defaults_are_unchanged` pins nine Auth codes. |
| D18 | **One TOTP method per user** (unique index `(UserId, Type)`). A second setup while one is pending replaces the pending secret in place; while one is confirmed it is 409 `auth.mfa_already_enabled`. Replacing an authenticator is "remove, then set up". | Blueprint 9.7 names one TOTP flow; in-place replacement avoids delete-then-insert ordering on a unique index. | Several authenticators later means dropping the index (additive). |
| D19 | **Wrong codes are 400**, like Plan 2's `auth.invalid_token`: `auth.invalid_mfa_code` (wrong, reused or unreadable code, or a wrong recovery code) and `auth.invalid_mfa_challenge` (unknown, expired, used, exhausted, or the account changed, locked or gone: all alike). | A 401 on an authenticated route makes clients refresh their token instead of asking for a new code. | None known. |
| D20 | **No `RowVersion` on the new tables.** The user row serializes MFA changes (each rotates the stamp under the user's `RowVersion`); hot counters (`LastUsedTimeStep`, `FailedAttempts`, `UsedAt`, `ConsumedAt`) change only through conditional `UPDATE`s. | Same pattern as refresh tokens and verification codes (Plan 2). | None known. |

## Review Focus

Inputs the spec implies and a person will meet, most likely first. Each is pinned by a named test in the owning task.

1. **Someone with the password guessing codes** by starting a new challenge after every few wrong codes, from many addresses: after 5 wrong codes in total the account is locked (and the owner emailed), and the password step never resets the count. Owned by Task 7 (`Wrong_codes_across_challenges_lock_the_account_after_five`, `Password_step_does_not_reset_the_failure_count_of_an_mfa_account`).
2. **The same TOTP code used twice:** a double tap (two simultaneous verifies), the code reused on a second challenge, or an older code after a newer one: exactly one success, never a 500. Owned by Task 4 (`Try_claim_time_step_succeeds_for_exactly_one_of_two_concurrent_callers`) and Task 7 (`Concurrent_verifies_with_one_code_succeed_once`, `Code_used_once_is_refused_on_a_second_challenge`).
3. **A phone clock that drifts:** codes one step early or late are accepted, two steps away refused, exactly at step boundaries. Owned by Task 2 (`FindMatchingStep_accepts_one_step_either_side_and_refuses_two`, `TimeStepAt_changes_exactly_on_the_thirty_second_boundary`).
4. **A recovery code typed the way people type it:** lower case, without hyphens, with spaces, or pasted with a trailing newline: accepted once; the same code again, a code from a replaced set, or a garbled one: refused. Owned by Task 2 (`Normalize_accepts_case_hyphens_and_spaces`) and Task 7 (`Recovery_code_works_once_in_any_spelling`).
5. **Account enumeration through MFA:** an unknown email, a wrong password for an MFA account and a locked MFA account answer identically; the challenge appears only after the correct password. Owned by Task 7 (`Unknown_email_and_wrong_password_for_an_mfa_account_return_identical_responses`).

Also pinned, outside the five: challenge misuse (expired, reused, another user's, a refresh token as challenge, the challenge as bearer or refresh token: Task 7), step-up expiry exactly at `MaxAge` (Task 5), the secret at rest and in logs (Tasks 4 and 6), a trusted device after a password change (Task 9), an unreadable secret after a key-ring loss (Task 5).

### Task 1: `auth_time` and `amr` on the current user

`Model: sonnet`

**Files:**
- Modify: `src/BuildingBlocks/TemplateName.Application.Common/Identity/ICurrentUser.cs`, `src/BuildingBlocks/TemplateName.Web.Common/Identity/HttpContextCurrentUser.cs`, `tests/TemplateName.IntegrationTests/Infrastructure/TestCurrentUser.cs`, every other `ICurrentUser` test double (search the test projects), `src/Modules/Auth/.../Application/Authentication/Login/LoginCommandHandler.cs` (uses the constant), `docs/building-blocks/{application-common,web-common}.md`
- Create: `src/Modules/Auth/TemplateName.Modules.Auth/Domain/Sessions/AuthenticationMethods.cs`
- Test: `tests/TemplateName.UnitTests/Web/HttpContextCurrentUserTests.cs` (extend), `tests/TemplateName.UnitTests/Auth/AuthenticationMethodsTests.cs`

**Interfaces:**
- Consumes: the JWT claims of `AccessTokenIssuer` (`amr` as a JSON array, so one `amr` claim per value with `MapInboundClaims = false`; `auth_time` as Unix seconds).
- Produces:
